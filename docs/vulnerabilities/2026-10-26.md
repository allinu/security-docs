### 1.3 今日重点关注

1. **`CVE-2026-115214`：Datawiza Proxy Auth 插件不校验代理来源：两个请求头即可创建管理员（9.8）**  
   该 WordPress 插件（1.1.1 之前）**不验证它所信任的 user-identity 与 role 请求头是否来自可信反向代理**，因此**未认证攻击者可直接构造这两个头，创建并以 WordPress 管理员身份认证**，CVSS 9.8。这是“头信任”缺陷中后果最直接的一种——不需要令牌、不需要会话，只要应用端口可达。它与本轮回溯期内出现的 OTRS／Znuny（`CVE-2026-93582`／`93483`）属同一族，**说明“信任代理头但不校验来源”仍是 2026 年最高频的认证旁路模式之一**。

2. **`CVE-2026-116199`：Snipe-IT Google SSO 回调不校验 activated 标志：停用用户可复活（9.2）**  
   Snipe-IT 8.6.3 之前，`GoogleAuthController::handleGoogleCallback` 在 Google 登录回调中**把用户名与 Google 账号邮箱匹配后直接登录，但不校验 `activated` 标志**。因此**已停用的用户**（例如离职员工）只要“邮箱形式的用户名 + 仍然有效的 Google 身份”即可通过 SSO 重新登录，并**恢复其原有权限（包括管理员）**。这条缺陷的危险性在于**它绕过了“停用账号”这一最基础的处置动作**——离职流程里“禁用 Snipe-IT 账号”并没有真正切断 SSO 入口。同产品另有一条 `CVE-2026-116201`（8.7）：SAML `acs` 处理器中的 **nonce 检查非原子**，攻击者用一个被捕获的断言并发 POST 即可获得多个已认证会话，且能**规避 IdP 侧的吊销**。

3. **`CVE-2026-116163`：Parse Server：AuthAdapter 子类的三个校验方法从未被调用（9.1）**  
   Parse Server 8.6.102 之前、9.0.0–9.10.5-alpha.2 之前，`AuthAdapter` 子类实现的 `validateSetUp`、`validateLogin`、`validateUpdate` **三个方法从未被调用**，而是使用了**继承来的默认实现“接受任意 authData”**。攻击者因此可以提交任意 `authData` 完成注册、绑定身份、**以既有用户身份登录**，或**跳过自定义的额外认证因子**。CVSS 9.1。这条与 Apache Camel 的 `doStart()` 未调用 `super.doStart()`（`CVE-2026-78162`）属同一类问题：**代码里写了安全方法，但执行路径没走到**。

4. **`CVE-2026-115995`：Unitree Go2 机器狗 chat_go 组件 set_volume 命令注入（9.4，厂商已确认）**  
   Unitree Go2（固件 1.1.11.4 及之前）的 `chat_go` 组件中，`gpt_thread.py` 的 `set_volume` 函数对 `Value` 参数处理不当，导致 **OS 命令注入**，攻击可远程发起，CVSS 9.4（`CWE-77`／`CWE-78`）。该编号的特殊之处在于**厂商已明确确认**（内部工单 #474），并提供了 1.1.11.5 固件下载链接。更值得关注的是它的架构含义：`gpt_thread.py` 说明这是一条**把大模型对话与设备控制连起来的通路**——“自然语言 → LLM 解析 → 调用设备函数”。当这条通路上的参数未做严格约束时，**“让机器人执行某个动作”与“让机器人执行任意命令”只差一个引号**。

### 1.4 综合研判

本期 132 条，严重仅 4 条（3.0%）、高危 32 条（24.2%），中危 64 条占主体，整体分数不高，但**“低分高后果”的条目集中**。第一条主线是**认证旁路的四种写法**，可作为通用审计清单：① **头信任**（Datawiza：不校验代理来源 → 直接创建管理员）；② **状态标志遗漏**（Snipe-IT：不校验 `activated` → 停用账号复活并恢复原权限）；③ **一次性凭证非原子**（Snipe-IT SAML：nonce 检查存在竞态 → 断言可重放，且绕过 IdP 吊销）；④ **扩展点未被调用**（Parse Server：`AuthAdapter` 的三个校验方法从未执行，回落到“接受任意 authData”）。这四种写法几乎不依赖具体语言或框架，**任何自研认证系统都值得逐条对照**。第二条主线是**AI 与设备的交界**：Unitree Go2 的 `set_volume` 命令注入（LLM 对话通路上的参数注入）、vLLM 的 `X-Request-Id` 解码地址 SSRF（可让 P2pNcclConnector 的 prefill worker 与攻击者主机建立 ZMQ 连接，**泄露 NCCL `unique_id` 与 KV-cache 张量**）、以及 vLLM 的多条资源耗尽与 gRPC 输入校验问题。vLLM 这一类“推理服务”正在成为新的高价值目标：**KV-cache 内含完整的上下文（可能包括系统提示、用户数据、检索到的文档）**，泄露的后果不只是算力被盗。第三条是常规 Web/工具链（phpMyFAQ 越权、Rclone WebDAV 穿越、SiYuan 的 Windows 敏感路径 denylist 绕过、Dokploy 越权、rotki 弱 KDF）。KEV 无新增，本期不需要应急响应。

    本期分数虽不突出，但**认证逻辑缺陷的“可验证性”极高**——Datawiza 加两个头即可创建管理员，Snipe-IT 用一个停用账号即可复活。建议把本期的四种认证旁路写法直接沉淀为审计清单，对自研与二开的登录/SSO/邀请链路做一次对照检查。设备侧（Unitree Go2）与推理侧（vLLM）的条目按“是否暴露到不可信网络”决定优先级，其中 vLLM 的 KV-cache 泄露风险需要单独评估。

#### 3.1.2 漏洞摘要

Datawiza Proxy Auth Plugin（WordPress 插件，1.1.1 之前）的设计是“由前置反向代理完成认证，再把用户身份与角色通过 HTTP 头传给 WordPress”。但它**没有验证这些头是否真的来自可信反向代理**，因此**未认证攻击者可以直接构造 `user-identity` 与 `role` 类请求头，让 WordPress 认为其已是管理员**，进而创建管理员账号或以管理员身份操作，CVSS 9.8（`CWE-269`）。这条缺陷的利用门槛几乎为零：只要插件启用、站点可达，用一条带自造头部的请求即可完成。它也与本轮回溯期内 OTRS（`CVE-2026-93582`）、Znuny（`CVE-2026-93483`）的“头信任”问题同族——**同一个错误模式在三个不同产品上重复出现，说明它是“代理+应用”架构的通病**：应用假设自己永远在代理之后，而现实是它常常可被直接访问。

> 原文摘要（NVD）：The Datawiza Proxy Auth Plugin  WordPress plugin before 1.1.1 does not verify that the user-identity and role HTTP request headers it trusts originate from a trusted reverse proxy, allowing unauthenticated attackers to create and authenticate as a WordPress administrator.

#### 3.1.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | WordPress 站点 HTTP 入口（插件启用即可） |

| 利用复杂度 | 低 | 低（自造请求头即可） |

**技术原理：**

反向代理认证的常见实现是：代理校验凭据后，把用户名/角色写入请求头（如 `X-Forwarded-User`、`X-Auth-Role`），后端应用直接信任。安全性依赖两个前提：**应用不可被绕过代理直接访问**、**代理会覆写（而非透传）这些头**。任一前提不成立，攻击者即可伪造身份。正确做法包括：应用只监听回环/内网、代理显式清除并重设这些头、或用 mTLS 在代理与应用之间建立可信通道。

**核心利用链：**

```text
攻击者
  └─ 定位暴露的 目标组件（目标产品）
      └─ 发送畸形输入触发缺陷逻辑
          └─ 触发 CWE-269 对应处理逻辑
              └─ 造成信息泄露、拒绝服务或状态破坏
                  └─ 横向利用或持久化（视环境）
```

| 检测项 | 可疑特征 |

## 五、当日处置建议

1. **把四种认证旁路写法做成审计清单**：① 是否信任客户端可设置的头；② 是否在所有登录路径校验账号状态（activated/锁定/删除）；③ 一次性凭证（nonce/断言/code）的消费是否原子；④ 自定义认证扩展点的钩子是否真的被调用。四条都能用“构造一次请求”验证，不需要工具。
2. **停用账号 ≠ 切断访问**：Snipe-IT 的例子说明，只要 SSO 身份仍有效，应用侧的“禁用”就可能被绕过。建议离职流程同时覆盖“企业目录停用 + 应用侧禁用 + 会话吊销”三处。
3. **对“示例/默认即不安全”的扩展点保持怀疑**：Parse Server 的默认实现“接受任意 authData”是为了兼容，但它让缺失调用变得无声。建议对框架扩展点补写“负向测试”（未实现/未调用时应拒绝而非放行）。
4. **机器人/设备侧关注“LLM→执行”通路**：Unitree Go2 的漏洞位于把对话转为设备动作的脚本里。建议对这类通路做参数严格类型化（数字范围、白名单），不要用字符串拼接调用系统命令。
5. **推理服务的 KV-Cache 属于敏感数据**：vLLM 的 SSRF 可泄露 KV-cache 张量，其中可能包含系统提示与用户上下文。建议把推理服务置于独立网段、限制其出站连接、并对 NCCL/ZMQ 端口做访问控制。
