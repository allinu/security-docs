### 1.4 综合研判

本期窗口内出现**"浏览器在野利用零日 + 数据库高龄高危缺陷公开 + 国内文档工具 0day 已复现"**三类高价值事件，均无公开完整 PoC、但利用门槛与影响面差异明显。`CVE-2026-85046` 是唯一确认在野利用的事件：浏览器类 0day 一旦进入 KEV，攻击者往往在数周内将其纳入漏洞利用工具包（如隐蔽浏览器/水坑攻击），对上网终端构成直接威胁，好在此类漏洞修复链路短（升级即修复），难点在受管终端版本核查与"自动更新已生效"的确认。`CVE-2026-6471` 的价值在于**"低危备份账户 = 服务器沦陷"**的认知颠覆：REPLICATION 账户被普遍视为低风险运维通道，而 Cyera 在 VirusTotal 上已发现 114 个恶意 PostgreSQL 插件（木马/挖矿/反弹 Shell），说明该攻击面正被实战利用；官方补丁已发布三周，本期媒体集中报道后预计利用尝试将上升，未升级的 PostgreSQL 实例（尤其 Windows + 出站 SMB 可达环境）应尽快闭环。ShowDoc 事件则延续了"开源国产工具 0day 被安全厂商批量复现"的态势，叠加其历史上多次文件上传/存储型 RCE（`CVE-2021-36440` 等），建议国内文档/知识库类系统运维方提高关注。数据泄露动态（MAG 机场 880 万人、Nexus 1.53 亿驾照扫描件）再次说明身份与行程类 PII 外流的欺诈放大效应。

#### 3.1.2 漏洞摘要

该漏洞存在于 Chrome 的 **V8 JavaScript/WebAssembly 引擎编译器**中。类型混淆指引擎在处理数组等对象时，其内部元素表示类型（Elements Kind）与对象实际 Map 不一致——研究者描述为"包含 `PACKED_ELEMENTS` 的数组被赋予了 `PACKED_SMI_ELEMENTS` 的 Map"，此类不一致可被进一步转化为 **JS 堆上的任意读写（arbitrary read/write）**。该缺陷同时存在于 Maglev 与 TurboFan 两个编译器路径中。远程攻击者只需构造特制 HTML 页面（含恶意 JavaScript），诱导受害者使用受影响版本 Chrome 访问，即可在**浏览器沙箱进程内**执行任意代码（进一步沙箱逃逸需与其他漏洞链式组合，官方未披露）。

> 浏览器是终端最常驻的互联网暴露面，Chrome 在野零日通常被用于水坑攻击与定向攻击链的浏览器入口。Google 按惯例未披露攻击细节、归因或受害者范围；修复随 09-03 Stable 通道更新发布并分阶段推送，用户端生效存在时间差，这是浏览器 0day 处置的核心窗口。

#### 3.1.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 受害者需能访问攻击者控制的恶意页面（或经水坑/广告/邮件投放） |
| 身份认证 | 无需 | 无身份要求 |
| 用户交互 | 需要 | 受害者需使用受影响版本 Chrome 访问特制 HTML 页面（无点击要求，加载即触发） |
| 特定配置 | 否 | 默认配置即可触发 |
| 利用复杂度 | 低 | 官方 CVSS 向量 AC:L；访问页面即可，无额外前置条件 |

**技术原理：**

V8 引擎使用"Elements Kind"描述数组元素存储格式（`PACKED_SMI_ELEMENTS`、`PACKED_ELEMENTS`、`PACKED_DOUBLE_ELEMENTS` 等），优化编译器（Maglev/TurboFan）依赖该元数据生成快速路径代码。当某缺陷路径导致数组的实际 Map 与其 Elements Kind 失配（含小整数标记的数组实际存放了对象引用）时，引擎对数组元素的读写将按错误的类型解释内存，形成 **JS 堆上的类型混淆原语**；攻击者可将该原语升级为任意读写，进而篡改对象布局或代码数据，在沙箱内执行任意代码。Google 未公开从原语到代码执行的完整利用链。

**核心利用链：**

```text
攻击者
  └─ 构造特制 HTML 页面（恶意 JavaScript，触发 V8 类型混淆）
      └─ 诱导受害者使用受影响 Chrome（< 152.0.7977.82）访问
          └─ 数组 Elements Kind 与 Map 失配（Maglev/TurboFan 编译路径）
              └─ 获得 JS 堆任意读写原语
                  └─ 在浏览器沙箱内执行任意代码（RCE）
                      └─ （后续需链式沙箱逃逸组件实现系统级控制，官方未披露）
```

#### 3.2.2 漏洞摘要

该漏洞存在于 PostgreSQL **逻辑复制（Logical Replication）输出插件的加载路径**。逻辑复制用于将数据库变更以事件流形式同步给外部工具（备份、CDC、云迁移、实时分析），客户端创建逻辑复制槽（`CREATE_REPLICATION_SLOT`）时必须指定一个输出插件（如 `pgoutput`、`wal2json`），由 PostgreSQL 服务端加载该插件以格式化变更数据。问题在于：**插件名称未经任何校验即被直接传入共享库加载器**——SQL 侧的 `LOAD` 命令会通过 `!superuser()` 标志触发路径校验（`check_restricted_library_name()`，强制非超级用户只能从管理员指定目录加载、禁止绝对路径与路径穿越），而复制协议路径**完全没有调用该校验**；且复制协议解析器允许双引号插件名内出现斜杠、反斜杠、`../` 穿越乃至 Windows UNC 路径。于是持 REPLICATION 权限（无超级用户权限）的攻击者可提交任意文件系统路径，服务端即以数据库进程身份（操作系统 `postgres` 用户）`dlopen()`（Linux/macOS）或 `LoadLibrary()`（Windows）加载该文件并执行其初始化代码。

> 该漏洞价值在于"备份账户不再可信"：REPLICATION 权限账户（备份工具、只读副本、CDC 管道、监控系统使用）被普遍视为低风险运维通道，而本漏洞将其变为**服务器代码执行入口**。Windows 场景下可通过 UNC 路径（`\\attacker\share\evil.dll`）由服务端主动出站 SMB 拉取 DLL，攻击者无需在目标落盘即可完成远程代码执行；加载恶意插件后攻击者可直写 `pg_authid` 目录表提权为超级用户（绕过 SQL 层 ACL），并可通过改写 `pg_hba.conf`、注册 `shared_preload_libraries` 等方式植入三重持久化后门。

| 网络可达 | 是 | 攻击者需能通过复制协议（默认 TCP 5432）连接目标实例，且目标 `wal_level=logical` 开启逻辑复制 |
| 身份认证 | 需要 | 持有 **REPLICATION 属性**的数据库账户（非超级用户、非管理员）——备份/同步/CDC 账户即满足 |
| 用户交互 | 不需要 | 纯协议交互触发 |
| 特定配置 | 是 | 服务端开启逻辑复制（`wal_level=logical`）；Windows 全远程场景另需数据库服务器可出站访问攻击者 SMB 445；Linux/macOS 需本地可写文件或 NFS automount（autofs）等条件 |
| 利用复杂度 | 中 | 需具备 REPLICATION 账户（CVSS PR:H），但该权限在真实环境普遍授予备份/CDC 账户，实际门槛低于直觉 |

**技术原理：**

PostgreSQL 逻辑解码时，客户端创建复制槽并指定输出插件名；服务端 `LoadOutputPlugin()` 将插件名原样传入 `load_external_function()`，最终到达 `dlopen()`/`LoadLibrary()`。与 SQL `LOAD` 路径不同，复制路径**未调用** `check_restricted_library_name()` 校验（该函数负责限制非超级用户仅能从管理员控制目录加载、禁止绝对路径/穿越/UNC），且复制协议解析器接受双引号插件名中的 `/`、`\`、`.`、`../` 与 Windows UNC 字符，因此攻击者可提交任意路径。插件被加载后其 `_PG_init()`/`_PG_output_plugin_init()` 初始化代码以数据库进程权限立即执行——该进程在操作系统层面以 `postgres` 用户运行，可读写数据库文件与 OS 文件。插件代码与 PostgreSQL 同地址空间运行、无沙箱，可直接调用内部函数：写 `pg_authid` 目录表将自身账户提权为超级用户（绕过 SQL 执行器 ACL），安装权限检查 Hook 使所有权限校验放行。持久化后门三重机制：改写 `pg_hba.conf` 允许任意来源免密连接并热加载、复制自身到稳定位置并注册 `shared_preload_libraries`（重启后自动加载）、后台持续重放超级用户篡改（管理员修复其一仍有两重残留）。

**核心利用链：**

```text
攻击者（持 REPLICATION 账户，如备份/CDC 账户）
  └─ 经复制协议连接目标（TCP 5432，wal_level=logical）
      └─ CREATE_REPLICATION_SLOT ... (PLUGIN = '绝对路径/恶意插件')
          └─ 服务端未校验插件名即 dlopen()/LoadLibrary()（对应 CWE-862）
              └─ 恶意插件 _PG_init() 以 postgres 进程权限执行（RCE）
                  └─ 直写 pg_authid / 安装权限 Hook → 超级用户
                      └─ 改写 pg_hba.conf + shared_preload_libraries → 持久化后门
```

#### 3.2.11 风险影响

漏洞成功利用后，可能导致：

- 以数据库进程（`postgres` 系统用户）权限远程执行任意代码（Windows/Linux/macOS 全平台）；
- 从 REPLICATION 账户提权至数据库超级用户，访问全部库表（客户数据、财务记录、应用密钥、存储凭据）；
- 经超级用户执行操作系统命令（`COPY ... TO PROGRAM`）、读取任意文件（`pg_read_file()`，含 `/etc/shadow`、私钥）、向 `postgres` 可写路径写文件（`lo_export()`）；
- 植入三重持久化后门（`pg_hba.conf` 免密、`shared_preload_libraries` 自启、超级用户重放），管理员难以彻底清除；
- 以数据库服务器为跳板横向移动（凭据收割后进入内网）。

#### 3.2.13 修复与缓解措施

#### 官方修复

1. 将 PostgreSQL 升级至 `18.6`/`17.11`/`16.15`/`15.19`/`14.24`（2026-08-13 季度更新，按当前大版本选择对应修复版本）；
2. 云托管实例（RDS/Aurora/Azure Database/Cloud SQL/Supabase/Neon 等）确认平台侧维护版本已应用修复，必要时手动触发小版本升级；
3. 9.4–13 EOL 分支无法获得修复，制定升级到受支持分支的计划（升级前完成逻辑/物理备份验证）；
4. 升级前完成配置、程序与业务数据备份，在测试环境验证兼容性及回退方案；
5. 升级后核验版本并复查复制槽、复制账户与日志。

#### 临时缓解

无法立即升级时，可采取：

- **收敛 REPLICATION 账户**：移除非必要账户的 REPLICATION 属性；保留账户最小化并仅允许从可信 IP 连接（`pg_hba.conf` 复制规则禁用 `0.0.0.0/0`）；
- **阻断出站 SMB/NFS**：防火墙/安全组阻断数据库服务器出站 TCP 445（SMB）与 2049（NFS），关闭非必要 autofs——消除 Windows 全远程与 NFS automount 利用路径；
- 关闭不使用的逻辑复制（`wal_level` 降为 replica 级别）或限制复制槽创建权限；
- 监控复制槽创建与插件名（含路径字符即告警）；
- 数据库服务器保持最小化出站策略与主机加固（EDR、文件完整性监控）。

#### 3.3.2 漏洞摘要

ShowDoc 是一款广泛使用的开源 API 文档/技术文档在线工具（PHP，GitHub 12,862★，官网 showdoc.com.cn），国内企业常用于内网接口文档管理与分享。微步在线研究响应中心与长亭安全应急响应中心于 2026-09-04 先后发布通告，称其 **`registerByVerify`（注册验证接口）存在未授权 PHP 代码注入漏洞**（两家均已复现）：该接口属于注册流程、无需登录即可访问（"未授权"），攻击者可注入 PHP 代码，进而可能导致远程代码执行。

> **攻击链佐证（官方加固提交）**：ShowDoc 官方仓库于 2026-09-04 推送的加固提交 `5f70b4570b`（"update"）包含：`.htaccess` 新增 `RewriteRule ^Sqlite/ - [F,L]`（提交注释原文："禁止访问 SQLite 数据库目录（防 .db.php 被 PHP 解析执行/下载）"）、新增 `Sqlite/deny.php` 与 `Sqlite/.user.ini`（`auto_prepend_file = deny.php`，403 守卫）、`entrypoint.sh`/`Dockerfile` 同步防护，另对 `ExtLoginController`（SSO/OAuth/CAS 自动注册用户名）与 `PageFeedbackController`（client_id）增加输入白名单校验。由此推断攻击路径与"**SQLite 数据库文件以 `*.db.php` 形式存放于 Web 可达目录，若库内被写入 PHP 代码，直接 HTTP 请求该文件即被 PHP 解析执行**"相关（代码注入点与完整利用链以厂商通告为准，本站不臆断）。注：官方加固提交同时覆盖 SSO 自动注册用户名与反馈接口输入卫生，说明披露触发了一轮系统性加固，具体对应关系以官方后续公告为准。漏洞代码路径同时存在于旧版应用（`server/Application/.../UserController.class.php`，`registerByVerify` 自 2019 年引入，无用户名白名单）与新版应用（`server/app/.../UserController.php`）中，实际受影响入口以厂商通告为准。

| 条件 | 状态 | 说明 |

| 用户交互 | 不需要 | 纯 HTTP 请求触发 |

**技术原理（基于公开信息推断，待官方通告确认）：**

`registerByVerify` 为注册（图形验证码）接口，其处理链中存在 PHP 代码注入点：攻击者注入的代码可被持久化至以 `.php` 结尾、位于 Web 可达目录的存储文件（ShowDoc 默认 SQLite 数据库文件即 `Sqlite/showdoc.db.php`），随后直接 HTTP 请求该文件即可令 PHP 解析执行其中代码。官方 09-04 加固提交（拦截 `/Sqlite/` 的 Web 访问并将 `deny.php` 前置到 Sqlite 目录所有 PHP 文件执行前）与该推断一致。具体注入参数、验证码绕过方式与版本差异以微步/长亭通告及官方公告为准。

**核心利用链（推断，待官方通告确认）：**

```text
攻击者
  └─ 访问 ShowDoc registerByVerify 注册接口（无需登录）
      └─ 在接口参数中注入 PHP 代码片段
          └─ 代码被持久化至 Web 可达的 Sqlite/*.db.php 存储文件
              └─ 直接 HTTP 请求该 .db.php 文件 → 被 PHP 解析执行（RCE）
                  └─ （常见后续：写入 WebShell / 反弹 Shell / 植入后门）
```

> 以上利用链为基于官方加固提交（拦截"Sqlite 目录 .db.php 被解析执行/下载"）与漏洞名称的**推断**，未经验证；严禁按此描述对任何系统执行验证。
