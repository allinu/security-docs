### 3.1 CVE-2026-33824 — Microsoft Windows IKE 服务扩展双重释放远程代码执行漏洞

!!! danger "严重漏洞"

#### 3.1.2 漏洞摘要

该漏洞位于 Windows Internet 密钥交换（IKE）服务扩展组件（ikeext.dll）中，属于**双重释放（Double Free）**类内存破坏漏洞。微软官方描述为"Windows IKE 扩展中的双重释放允许未授权攻击者通过网络执行代码"，NVD 评分为 **9.8（严重）**。IKE 是 VPN（IPsec/IKEv2）等远程接入场景的核心协议，启用 IKE 服务的系统在接收特制网络报文时可能触发双重释放，进而实现任意代码执行。微软已于 **2026-04-14（4 月补丁星期二）**修复。

该漏洞的实战风险由两份独立报告确认：一是 [Unit 42 于 2026-07-30 发布的研究报告](https://unit42.paloaltonetworks.com/autonomous-ai-cyber-attack-campaign/)披露，代号 knaithe/KnYuan 的中文攻击者利用 DeepSeek 等 AI 模型搭建自主攻击体系，在人工确认的利用操作中对**3 个 IKE VPN 端点**发起反向 Shell 回调（`CVE-2026-33824`）；二是 CISA 于 **2026-08-18** 将其收录 KEV（处置期限 2026-08-21）。微软建议通过阻断 UDP 500/4500 端口降低外部暴露面，但内部攻击者仍可借其横向移动，需尽快打补丁。

> 官方公告：[MSRC - CVE-2026-33824](https://msrc.microsoft.com/update-guide/vulnerability/CVE-2026-33824)、[CISA KEV 查询](https://www.cisa.gov/known-exploited-vulnerabilities-catalog?field_cve=CVE-2026-33824)

#### 3.1.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需可达目标系统的 IKE 服务（UDP 500/4500） |
| 身份认证 | 无需 | 未认证即可通过网络触发 |
| 用户交互 | 不需要 | 全程无受害者参与 |
| 特定配置 | 是 | 需系统启用 IKE 服务扩展（VPN/IPsec 场景常见） |
| 利用复杂度 | 低 | 特制网络报文即可触发双重释放 |

**技术原理：**

IKE（Internet Key Exchange）服务扩展在处理协商报文时对同一内存对象存在两次释放路径：当报文处理流程中第一次释放后指针未被置空，后续错误处理路径再次释放同一对象（CWE-415 双重释放），导致堆内存被破坏，攻击者可通过精心构造的报文布局将破坏转化为任意代码执行。漏洞触发点在网络协议栈上层，无需认证即可到达。

**核心利用链：**

```text
攻击者
  └─ 定位启用 IKE 服务的 Windows 系统（UDP 500/4500）
      └─ 构造特制 IKE 协商报文
          └─ 触发 ikeext.dll 报文处理双重释放（CWE-415）
              └─ 破坏堆布局并劫持控制流
                  └─ 以系统服务权限执行任意代码（RCE）
```

#### 3.2.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需可访问自托管 SharePoint Server（HTTP/HTTPS） |
| 身份认证 | 无需 | 未认证即可发起请求 |
| 用户交互 | 不需要 | 全程无受害者参与 |
| 特定配置 | 是 | 影响 SharePoint Server 自托管部署（SaaS 不受影响） |
| 利用复杂度 | 低 | 公开 PoC 可直接生成可被接受的伪造令牌 |

**技术原理：**

SharePoint 的 JWT 验证管线存在四处可串联利用的弱点（Rapid7 披露）：
1. 外层 JWT 头使用 `alg: none`，使签名校验流程可被跳过；
2. 令牌内使用 SharePoint 自身 STS 证书指纹（thumbprint）解析签名密钥，但**不验证密钥来源的真实性**；
3. 传入一个非空但从不被验证的签名字段（如 `AAAA`），绕过"空签名"类防护；
4. 上述弱点组合后，SharePoint 将伪造令牌视为合法身份。

攻击者无需任何凭据即可伪造任意用户（含管理员）的令牌，实现**认证绕过 + 身份冒充**（CWE-1390）。

**核心利用链：**

```text
攻击者
  └─ 定位自托管 SharePoint Server
      └─ 构造外层头 alg:none 的伪造 JWT（引用 STS 证书指纹、附未验证签名）
          └─ 触发 SharePoint JWT 验证管线四弱点串联（CWE-1390）
              └─ 伪造令牌被接受为合法身份
                  └─ 冒充任意用户（含管理员）访问站点与数据
```

#### 3.3.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需可访问 vCenter 管理网络（Syslog 服务端口） |
| 身份认证 | 无需 | Broadcom 公告未要求认证（NVD 向量 PR:N） |
| 用户交互 | 不需要 | 全程无受害者参与 |
| 特定配置 | 是 | 需 vCenter 默认 Syslog 服务（默认部署即含） |
| 利用复杂度 | 低 | 构造路径遍历请求即可触发 |

**技术原理：**

vCenter 内置 Syslog 服务器对日志文件名/路径参数缺少充分的路径规范化与限制（CWE-22），攻击者可构造包含 `../` 等遍历序列的请求，将写入/读取路径逃逸到预期目录之外，结合可写路径实现任意代码执行（以 vCenter 服务权限运行）。NVD 评分 9.8 表明攻击者无需认证且可达到完整机密性/完整性/可用性影响。

**核心利用链：**

```text
攻击者
  └─ 定位 vCenter（管理面/网络可达）
      └─ 向 Syslog 服务器发送含路径遍历序列的特制请求
          └─ 触发目录遍历（CWE-22），路径逃逸受限目录
              └─ 写入恶意内容/读取敏感文件
                  └─ 以 vCenter 服务权限执行任意代码
```

### 3.4 CVE-2026-65400 — Apple macOS 屏幕共享认证绕过漏洞（在野利用，挖矿攻击）

!!! danger "严重漏洞"

#### 3.4.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需可达目标 Mac 的屏幕共享服务（TCP 5900） |
| 身份认证 | 无需 | 无需有效凭据即可认证（漏洞核心） |
| 用户交互 | 不需要 | 全程无受害者参与 |
| 特定配置 | 是 | 需目标启用屏幕共享/远程管理（macOS 常见功能） |
| 利用复杂度 | 低 | 直接连接屏幕共享服务即可触发认证绕过 |

**技术原理：**

macOS 屏幕共享服务在认证握手阶段对**认证状态**的管理存在缺陷：会话状态未按预期在多次认证尝试/特殊握手序列间被正确重置或校验（CWE-287），攻击者可通过精心构造的连接序列，使服务在**未验证有效凭据**的情况下即建立已认证会话。补丁通过"改进认证状态管理"封堵该路径。利用成功后攻击者获得屏幕共享会话（等价于远程桌面），可进一步提权至 root（NCSC 观测到攻击者均获取 root 并安装门罗币挖矿程序）。

**核心利用链：**

```text
攻击者
  └─ 定位启用屏幕共享的 Mac（TCP 5900）
      └─ 构造特殊认证握手序列
          └─ 触发认证状态管理缺陷（CWE-287）
              └─ 未验证凭据即建立已认证屏幕共享会话
                  └─ 获取 root 权限并安装挖矿程序（NCSC 观测）
```

#### 3.5.2 漏洞摘要

原始漏洞（`CVE-2026-23479`）位于 redis-server 的**阻塞客户端（blocked client）处理流程**：当重新执行被阻塞的命令时，代码未处理 `processCommandAndResetClient` 的错误返回；若在此过程中阻塞客户端被逐出（evicted），将触发 **Use-After-Free（CWE-416）**，认证攻击者可通过精心构造的命令序列实现远程代码执行。影响 redis-server **7.2.0–8.6.3**，官方于 **8.6.3** 修复（对应 [GHSA-93m2-935m-8rj3](https://github.com/redis/redis/security/advisories/GHSA-93m2-935m-8rj3)）。百度检索显示[阿里云漏洞库](http://www.baidu.com/link?url=TuApm6EhrAfEQafG77C0-U3wf4jYoBiuRdErgU9yVfZ0H23U1oR6U_ovoOhqpzl69RX8uJwljnanB6YPP4P_o_)已收录该漏洞（披露时间、官方补丁 8.6.3），[FreeBuf 报道](http://www.baidu.com/link?url=ve5YFQ2rGs-cR-5aCOGv2mBL-TZX0SL7yXfbhCKfxeRgmUTNQ5Vj9s7-jN9Uy9lK-YXhK_3zbdK2I_J_PSC-9UqKh1b8RKJcpB6m94tORd3)将其列为 2026 年 7 月披露的多个 Redis RCE 类漏洞之一（报道表述的披露时间与 NVD 2026-05-05 存在差异，**以 NVD 官方为准**）。

**本期动态：** [奇安信 CERT 于 2026-08-19 发布【已复现】安全风险通告](https://mp.weixin.qq.com/s?__biz=MzU5NDgxODU1MQ==&mid=2247507148&idx=1&sn=ab4a29b67662e66d96b9a389b874869b)，披露 `CVE-2026-23479` 存在**未完全修复变种**（奇安信编号 **QVD-2026-55651**）并已复现，即官方 8.6.3 修复可被绕过，仍可导致远程代码执行。变种的具体技术细节未在公开渠道披露（奇安信微信通告页面反爬，本报告未获取到正文细节），**以奇安信 CERT 通告及后续官方公告为准**。

> 官方公告：[Redis GHSA-93m2-935m-8rj3](https://github.com/redis/redis/security/advisories/GHSA-93m2-935m-8rj3)、[Redis 8.6.3 Release](https://github.com/redis/redis/releases/tag/8.6.3)

#### 3.5.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需可访问 Redis 服务（默认 TCP 6379） |
| 身份认证 | 需要 | 需有效的 Redis 认证凭据（NVD 向量 PR:L；未开启认证/未授权访问部署则门槛更低） |
| 用户交互 | 不需要 | 全程无受害者参与 |
| 特定配置 | 是 | 需使用阻塞类命令（如阻塞列表/BLPOP 等）触发阻塞客户端流程 |
| 利用复杂度 | 低 | 构造命令序列即可触发（奇安信已复现） |

**技术原理：**

redis-server 在"重新执行被阻塞的命令"流程中，未检查 `processCommandAndResetClient` 的错误返回值：当阻塞客户端在流程中被逐出（如连接断开、客户端被 kill、超时清理）时，后续代码仍引用已释放的客户端对象，形成 **Use-After-Free（CWE-416）**。攻击者（低权限、已认证）通过堆布局控制可将其转化为任意代码执行，以 Redis 进程用户身份运行。奇安信确认的**未完全修复变种**意味着 8.6.3 的补丁逻辑可被绕过，存在替代触发路径。

**核心利用链：**

```text
攻击者（已认证 Redis 用户）
  └─ 连接 Redis 服务（TCP 6379）
      └─ 构造触发阻塞客户端流程的命令序列（BLPOP 等）
          └─ 诱导阻塞客户端在重执行流程中被逐出
              └─ 触发 Use-After-Free（CWE-416）
                  └─ 堆布局控制实现远程代码执行（奇安信已复现）
```

#### 3.5.11 风险影响

漏洞成功利用后，可能导致：

- 以 Redis 进程用户身份在服务器上执行任意代码；
- 窃取 Redis 中缓存的会话、令牌与业务数据；
- 横向移动至应用服务器与数据库；
- 植入后门、挖矿程序或勒索软件；
- 中断依赖 Redis 的业务（缓存、队列、会话）可用性。

#### 3.5.13 修复与缓解措施

#### 官方修复

1. 原始漏洞：升级至 `Redis 8.6.3` 或更高版本（[Redis 8.6.3 Release](https://github.com/redis/redis/releases/tag/8.6.3)）；
2. 未完全修复变种（QVD-2026-55651）：**关注奇安信 CERT 通告与 Redis 官方后续公告**，获取修复版本后第一时间升级（当前官方修复版本待确认）；
3. 升级前备份数据（RDB/AOF），测试环境验证兼容性。

#### 临时缓解

无法立即升级时，可采取：

- 收敛 Redis 6379 端口，仅允许应用服务器访问（禁止互联网暴露）；
- 强制开启认证（`requirepass` 强口令）并启用 ACL 最小权限；
- 重命名/禁用高危命令（`CONFIG`、`EVAL`、`SCRIPT` 等，评估业务影响后实施）；
- 对开启认证且暴露面大的 Redis 立即核查入侵痕迹；
- 以最小权限用户运行 redis-server 并启用系统审计。
