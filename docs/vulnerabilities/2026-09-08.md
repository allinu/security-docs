#### 3.1.2 漏洞摘要

该漏洞位于 Magento/Adobe Commerce 的**模板（template）系统**中，Sansec 命名为「StyleSmuggler」。攻击者利用 `styles` 属性（模板样式相关数据结构）绕过现有输入校验，将恶意 PHP 代码"走私"进模板渲染链路。攻击分两个阶段：**第一阶段（投毒）**——攻击者触发某条记录创建或生成失败报告（failure report），把 PHP 代码写入将被模板渲染的数据路径；**第二阶段（触发执行）**——平台在渲染例行的"付款失败提醒（Payment Transaction Failed Reminder）"邮件等业务流程时，模板引擎执行被投毒的代码，实现远程代码执行。整个链路**不需要受害者打开附件、点击链接甚至不需要邮件送达成功**（邮件发送失败也不影响代码执行），也不需要任何身份认证与用户交互。

> Sansec 官方表述："StyleSmuggler injects malicious code into Magento's template system. By using the `styles` properties, it can evade existing safeguards. It works in two stages: ① Inject (poison) PHP code, for example by generating a failure report. ② Let Magento execute the poisoned code via a failed payment email." 攻击者已多次切换投递路径（会话存储失败后 8 秒即改用 custom options 文件上传成功），并在 09-05 至 09-07 间多次更换后门进程伪装名（`[kworker/u:8:0]` → `fc-cache` → `chronyd`），显示其为持续迭代的活跃操作者。

#### 3.1.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需可达商店前台/GraphQL 端点（443/80） |
| 身份认证 | 无需 | 未认证即可完成投毒与触发（Sansec 在干净环境复现完整未认证链） |
| 用户交互 | 不需要 | 无需受害者点击链接或打开文件；邮件渲染流程自动触发，邮件投递失败亦可执行 |
| 特定配置 | 否 | 会话存储迁移至 Redis/数据库不能阻止攻击（攻击者会切换投递路径） |
| 利用复杂度 | 低 | 攻击者已在野稳定利用并迭代多种载荷 |

**技术原理：**

漏洞根因是模板系统对 `styles` 属性缺乏充分的特殊元素中和（CWE-1336）：攻击者可将 PHP 代码片段放入经 `styles` 属性承载的数据结构中，绕过对危险输入的常规拦截（现有防护主要针对 `{{ }}`/`$_` 等模板指令与关键字，而 `styles` 路径未被覆盖）。被投毒的数据经失败报告等机制持久化后，进入"付款失败提醒"邮件等模板渲染流程，由模板引擎以 PHP 求值方式执行，形成**存储型模板注入 → 远程代码执行**。由于渲染流程是平台常规自触发逻辑（邮件通知），攻击者无需等待受害者任何动作。

**核心利用链：**

```text
攻击者
  └─ 发现暴露的商店前台（GraphQL / HTTP 端点）
      └─ 构造携带 PHP 载荷的 styles[...] 参数（如 POST /graphql?styles[....]=）
          └─ 投毒数据记录 / 生成失败报告（触发模板数据落库）
              └─ 商店渲染"付款失败提醒"邮件等模板流程
                  └─ 模板引擎求值执行注入的 PHP
                      └─ 实现未认证远程代码执行（写入后门 / WebShell / 窃取数据）
```

#### 资产排查

- [ ] 是否部署 Magento Open Source / Adobe Commerce（含 Commerce B2B）
- [ ] 当前版本及补丁状态（`vendor/bin/magento-patches -n status` 输出与 `security:patch-status`）

- [ ] 商店/GraphQL 端点是否暴露互联网（电商前台天然暴露，按失陷假设排查）
- [ ] 是否将 PHP 会话存储于 Redis/数据库（Sansec：不能阻止攻击）
- [ ] 是否运行可疑进程 `[kworker/u:8:0]`、`fc-cache`、`chronyd`（自 /tmp、缓存目录等非常规路径）

#### 日志与行为排查

重点检查：

- Web 访问日志、GraphQL 请求日志（`POST /graphql?styles[...]=`、`Store:` 请求头异常内容）、邮件发送/失败通知日志（`var/report/` 失败报告目录）；
- 进程列表（`ps -eo pid,comm,args`）与 crontab/`/var/spool/cron` 定时任务（攻击者直写 cron 池文件，`crontab -l` 查不到不代表干净）；
- Web 目录文件（`pub/media/catalog/product/cache/` 下哈希目录中的可疑 PHP、模板与报告文件改动）；
- 异常 DNS/外联：UDP 123 每 60 秒 9 连发 48 字节 NTPv4 **server 模式**数据报（真实 NTP 客户端为单发 client 模式）、对公网 IP 查询服务（ipify/icanhazip/ident.me/ipinfo.io）的 HTTP 请求；
- `TracerPid` 检测：被跟踪时后门仍会安装但不再回连（用于对抗沙箱分析）。

#### 3.1.11 风险影响

漏洞成功利用后，可能导致：

- 在商店服务器上以 Web 服务用户权限执行任意 PHP 代码（无需认证）；
- 窃取订单数据、客户 PII、支付网关凭据、API 密钥及数据库配置（攻击者已读取加密密钥保护的数据）；
- 植入 Rust 后门与 WebShell，建立隐蔽持久化（cron、伪装进程、图片缓存文件）；
- 篡改商店页面/模板，注入 Magecart 类窃卡脚本或供应链投毒内容；
- 以商店服务器为跳板横向移动至同网段支付、仓储、ERP 等业务系统；
- 电商企业因数据泄露面临监管处罚、PCI DSS 合规风险与品牌损失。

#### 3.1.13 修复与缓解措施

#### 官方修复

1. 从 repo.magento.com 下载 `VULN-39341-composer-patches.zip`，按 Adobe APSB26-146 官方指引以 composer patch 方式应用紧急热修复；
2. 核验安装：`vendor/bin/magento-patches -n status | grep "39341\|Status"`；
3. **轮换加密密钥（`app/etc/env.php` 中 `crypt.key`）及该密钥保护的全部凭据**——管理员密码、REST/SOAP/GraphQL 集成令牌、OAuth client secret、支付网关 API 凭据、数据库凭据、SSH 与部署密钥、第三方扩展 API 密钥（须在凭据源头轮换，仅轮换加密密钥不能使攻击者已读取的数据失效）；
4. 升级前完成配置、程序与业务数据备份，并在测试环境验证；
5. 升级后核验补丁状态与业务运行情况，重新执行后门排查并留存修复证据。

#### 临时缓解

无法立即安装热修复时，可采取：

- 如无补偿控制，**临时禁用 GraphQL**（Sansec 建议；可能影响前台与集成功能，需按风险决策执行）；
- 部署 Sansec Shield 等实时拦截方案（Sansec 称已覆盖其观测到的全部 StyleSmuggler 变体）；
- 使用 eComscan（`curl ecomscan.com | sh`）扫描失陷痕迹与二级后门；
- 在 WAF/反向代理侧拦截 `styles[` 数组型参数与 `Store:` 头异常内容（参见 3.1.9 检测特征）；
- 收紧服务器出站策略：默认阻断 UDP 123 之外的非常规外联，审计 NTP 域解析；
- 加强日志审计与进程/文件完整性监控（重点目录：`var/report/`、`pub/media/`、`/tmp`、cron 池）。

### 3.2 `CVE-2026-86218` — N-able N-central 认证前远程代码执行漏洞

!!! danger "严重漏洞（CVSS v4.0 = 10.0）"
    N-able N-central 远程监控管理（RMM）平台在 2026.3 HF4（2026.3.1.14）之前版本存在认证前远程代码执行漏洞（CWE-96）：未经认证的攻击者可对 N-central 服务器执行任意代码，获取平台完全控制权——RMM 平台一旦失陷，攻击者可经 Take Control 等功能批量触达其管理的全部下游端点。N-able 官方于 09-05 发布 2026.3 HF4 修复并定级 critical，称暂无生产环境利用确认；托管实例（NCOD）已自动修复。

#### 3.2.2 漏洞摘要

该漏洞存在于 N-able N-central（面向 MSSP/IT 服务商的远程监控与管理平台，一般自托管于 Windows 服务器）中，允许**未经认证的远程攻击者在 N-central 服务器上执行代码**（N-able 官方称 "critical-CVSS-rated … pre-authenticated remote code execution on the N-central server"）。漏洞经第三方通过 N-able 安全披露计划负责任披露，官方在发布 2026.3 HF4（2026-09-05）修复时未公开技术细节；NVD 将根因归类为 CWE-96（静态保存代码指令中和不当，即存储型代码注入类缺陷）。受影响的服务器版本为 2026.3.1.13（HF3）及更早的全部 on-prem 版本（含 2025.4/2026.1/2026.2/2026.3 各线），托管（NCOD）实例由 N-able 侧直接修复、无需客户操作。

> N-able 官方表述："This hotfix includes security fixes for CVE-2026-86218 which is a critical-CVSS-rated vulnerability that could allow for pre-authenticated remote code execution on the N-central server. … At this time, we have no confirmations that this vulnerability has been exploited in production environments, but unpatched systems remain at risk."（2026.3 HF4 Release Notes）。**背景提示**：本站 08-04 期（第 4 期）3.4 已详录同产品 `CVE-2026-18576`/`CVE-2026-18577`（认证绕过/账户接管，在野利用并被 CISA 于 08-02 纳入 KEV）——N-central 自 7 月底以来约五周内连续发布 HF1→HF4 四轮安全热修复，攻击者对该平台的攻击面研究持续活跃。

**技术原理：**

官方与 NVD 未披露技术细节，仅知根因属 CWE-96（静态保存代码指令中和不当——程序存储了本应作为数据处理、却可被当作代码执行的指令内容）。结合该平台 8 月 `CVE-2026-18576`/`CVE-2026-18577` 系列（认证绕过）与 09-05 同批 `CVE-2026-86206`/`CVE-2026-86207`（内部 API 认证绕过，可完全访问 N-central 平台）的情况，本漏洞可能位于 N-central Web 服务对外可达的请求处理链中，攻击者在未认证状态下向特定接口提交构造数据即可触发服务器端代码执行。**因无官方细节，本节不臆测具体端点**；防御侧重以版本修复与暴露面收敛为主。

**核心利用链：**

```text
攻击者
  └─ 发现暴露的 N-central 服务器（Web 控制台/服务端口）
      └─ 构造恶意请求/数据（未认证，具体端点未公开）
          └─ 触发服务器端静态代码执行缺陷（CWE-96）
              └─ 获取 N-central 服务器代码执行权限（平台管理员等效）
                  └─ 潜在横向：经 Take Control 等功能批量触达受管端点（推定，参考 18577 利用模式）
```

> 标注"推定"的环节基于同产品历史漏洞（`CVE-2026-18577`，KEV，在野利用模式）的合理推断，非官方确认。
