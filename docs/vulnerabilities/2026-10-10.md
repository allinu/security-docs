### 1.3 今日重点关注

1. **`CVE-2026-94503`：WordPress Zombify 插件未授权任意文件上传（CVSS 10.0 满分，已出现公开 PoC）**  
   影响 Zombify ≤ 1.7.7，攻击者无需任何凭据即可上传任意类型文件并在 Web 目录落地，直接获得 WebShell 与站点控制权；CVSS 向量含 `S:C`（范围变更），故基准分达 10.0。**本期唯一在 GitHub 上检得可用 PoC 的编号**（`Wayang1337/CVE-2026-94503`，2026-10-10 创建，Python 实现，自述为未授权任意文件上传）。WordPress 插件型漏洞的暴露面极大，建议对全站插件清单做一次比对。

2. **`CVE-2026-96207`：微软云侧集中披露：Partner Center 证书校验缺陷（10.0）、Bookings 越权（9.9）、Dataverse 反序列化（9.8）**  
   本期微软一次性发布多条云服务高危条目，向量多为 `AV:N/AC:L/PR:N/UI:N`，即**无需认证、无需交互、网络直达**。其中 Partner Center 的证书校验不当（`CWE-295`）可绕过信任链完成越权；Dataverse 的不可信数据反序列化（`CWE-502`）在描述中明确为“可远程执行代码”。云服务多由微软侧统一修复，但**混合部署、私有连接与自建集成组件仍需逐一确认状态**。

3. **`CVE-2026-78401`：IBM 身份与数据平台集群：Verify Access 反序列化 RCE（9.8）+ Guardium 三连（9.8）**  
   `CVE-2026-78401`／`CVE-2026-78406` 影响 IBM Security Verify Access 10.0–10.0.9.2 与 Verify Identity Access 11.0–11.0.3，**未认证远程攻击者可因不可信数据反序列化执行任意代码**，身份认证网关一旦失陷等于单点登录体系失守；同期 Guardium Data Protection 出现路径穿越（`CVE-2026-75875`）、SQL 注入（`CVE-2026-80381`）、关键功能缺失认证（`CVE-2026-84249`）三条 9.8，构成“身份面 + 数据面”双重风险。

4. **`CVE-2026-107722`：fast-jwt JWT 算法混淆致认证绕过（9.8，供应链风险）**  
   6.2.0 至 6.3.0 之前版本中，`src/crypto.js` 的 `performDetectPublicKeyAlgorithms` 仅裁剪空白字符，而 PEM 匹配正则仍锚定字符串起始位置——当 RSA 公钥文本前存在注释、控制字符、零宽字符或包装文本时，公钥会被误判为 HMAC 密钥并回落到 HS256。**知道公钥字节的攻击者即可用公开材料签发任意 HS256 声明**，造成认证／授权绕过。仅在允许 HS256 或算法推断开启时成立，将算法白名单限定为非对称算法可完全规避。

#### 3.1.2 漏洞摘要

该漏洞由 Patchstack 报送，位于 WordPress 插件 Zombify（PX-lab 维护）的文件上传处理逻辑中，影响 1.7.7 及更早版本。插件的上传入口未对文件扩展名、MIME 类型与落地路径实施有效约束（`CWE-434`），导致任意类型文件可被写入服务器 Web 可访问目录。由于上传动作不需要任何身份认证，攻击者无需账号、无需交互即可完成利用；CVSS 向量包含 `S:C`（范围变更），即影响范围可越出 WordPress 应用本身延伸至宿主机，因此基准分达到 10.0。利用成功后最直接的结果是 WebShell 落地——攻击者获得与 Web 服务进程同等权限的持久化执行能力，可进一步读取 `wp-config.php` 中的数据库凭据、横向移动或植入挖矿／后门程序。披露当日，GitHub 上即出现社区 PoC 仓库（`Wayang1337/CVE-2026-94503`），是本窗口内唯一确认具备公开可利用代码的编号。

> 原文摘要（NVD）：Unrestricted Upload of File with Dangerous Type vulnerability in PX-lab Zombify zombify allows Upload a Web Shell to a Web Server.This issue affects Zombify: from n/a through 1.7.7.

#### 3.1.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | HTTP/HTTPS 可达的 WordPress 站点，插件启用即具备攻击面 |
| 身份认证 | 无需 | 无需任何凭据即可触发 |
| 用户交互 | 不需要 | 无需受害者交互 |
| 特定配置 | 是 | 需站点启用 Zombify 插件且版本 ≤ 1.7.7；上传目录具备执行权限时危害最大 |
| 利用复杂度 | 低 | 低（无需凭据、无需交互，工具化成本极低） |

**技术原理：**

根因是上传接口对“文件类型”的判定缺失或可绕过：插件仅依赖前端校验、或仅按扩展名黑名单过滤，未在服务端对内容做二次解析与白名单约束，也未把上传目录置于不可执行上下文。攻击者构造 `multipart/form-data` 请求，将 PHP 载荷伪装成图片，扩展名使用 `phtml`／`php7` 或双扩展名规避黑名单，落地后直接请求该文件即可触发解析执行。叠加“未认证可访问”这一条件，攻击链极短：定位插件 → 找到上传接口 → 上传载荷 → 访问载荷。

**核心利用链：**

```text
攻击者
  └─ 定位暴露的 目标组件（目标产品）
      └─ 上传绕过类型校验的恶意文件
          └─ 触发 CWE-434 对应处理逻辑
              └─ 在服务器落地可执行内容
                  └─ 横向利用或持久化（视环境）
```

### 3.4 CVE-2026-107722 — fast-jwt 算法混淆致 JWT 认证绕过（9.8）

!!! danger "严重漏洞（算法混淆 / 认证绕过，CVSS 9.8）"

#### 3.4.2 漏洞摘要

fast-jwt 是 Node.js 生态中广泛使用的高性能 JWT 实现。该漏洞由 GitHub Security Advisory（GHSA-ww5h-9m49-7xx4）披露，影响 6.2.0 起至 6.3.0 之前的版本。具体缺陷在 `src/crypto.js`：`performDetectPublicKeyAlgorithms` 会对输入做空白裁剪，但 `publicKeyPemMatcher` 正则仍锚定字符串起始位置（start-anchored）。当密钥文本在 PEM 头（`-----BEGIN PUBLIC KEY-----`）之前存在注释、控制字符、零宽字符或包装文本时，PEM 识别失败，代码便回落到 HMAC 分支，把这段**公开可见的** RSA 公钥当成 HS256 的对称密钥使用。攻击者只要拿到服务端公钥（通常通过 JWKS 端点公开），即可用该公钥字节作为 HMAC 密钥签发任意 `HS256` 令牌；若服务端允许 HS256 或开启算法推断，伪造令牌将通过验签，实现**任意用户（含管理员）身份冒充**。这是 JWT 算法混淆（algorithm confusion）家族在 2026 年的又一次复现，说明“按密钥内容推断算法”这一设计本身就是风险源。修复版本 6.3.0 已改为严格校验 PEM 起始边界。

> 原文摘要（NVD）：fast-jwt provides fast JSON Web Token (JWT) implementation. From 6.2.0 until 6.3.0, fast-jwt can misclassify RSA public-key text as an HMAC secret when the key has non-whitespace content before its PEM header. In src/crypto.js, performDetectPublicKeyAlgorithms trims whitespace but publicKeyPemMatcher remains start-anchored, so comments, control characters, zero-width characters, or wrapper text can prevent PEM detection and reach the HMAC fallback. An attacker who knows the public key bytes can sign arbitrary HS256 claims with that public material when HS256 is inferred or allowed, resulting in authentication or authorization bypass. An asymmetric-only algorithm allowlist prevents the attack

#### 3.4.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 任何使用 fast-jwt 验签的 HTTP 接口 |

| 特定配置 | 是 | 需服务端允许 HS256 或未固定算法白名单；仅允许非对称算法时不可利用 |
| 利用复杂度 | 低 | 低（公钥通常公开，伪造令牌可脚本化） |

**技术原理：**

JWT 验签的正确前提是“算法由服务端策略决定，而非由令牌头部或密钥内容推断”。fast-jwt 的实现为了兼容“同一密钥既可能是 PEM 公钥又可能是 HMAC 密钥”，加入了基于文本特征的算法推断：先用正则判断是否 PEM，是则用非对称算法，否则用 HMAC。该正则要求 PEM 头必须出现在字符串第 0 位；一旦前面有任意非空白字符（注释、`#`、零宽空格 U+200B），识别即失败，逻辑错误地落入 HMAC 分支。攻击者控制的是“密钥文本”吗？不是——密钥来自服务端配置，但**公钥本身是公开材料**，攻击者只需知道其字节即可作为 HMAC 密钥签名。因此能否利用取决于两点：服务端是否允许 HS256（或未固定算法），以及公钥文本前是否存在非空白前缀。

**核心利用链：**

```text

      └─ 发送畸形输入触发缺陷逻辑
          └─ 触发 CWE-347 对应处理逻辑
              └─ 造成信息泄露、拒绝服务或状态破坏
                  └─ 横向利用或持久化（视环境）
```

## 五、当日处置建议

1. **先做两条“五分钟判定”**：`wp plugin list | grep zombify` 与 `npm ls fast-jwt`。两条命令即可判定是否存在本期两个最高优先级风险，无需等待资产台账。
2. **WordPress 站点专项**：对全站插件做版本比对，重点排查启用状态的上传类、备份恢复类插件；同时禁止 `wp-content/uploads` 解析 PHP，这一步能在补丁未落地前挡住绝大多数上传型 WebShell。
3. **身份网关不可当作普通应用对待**：IBM Verify Access／Verify Identity Access 位于认证边界，处置时应同步评估签名密钥与后端凭据是否需轮换，而非仅升级版本。
4. **云服务条目要区分“已修”与“待确认”**：微软云侧的 Dataverse、Azure App Service、Bookings 多由服务端修复，但数据网关、自建连接器、私有链路属于租户责任范围，仍需逐项核对。
5. **把 ICS 与嵌入式设备单独建账**：openPDC/openHistorian 与 Netcore、iStoreOS 等设备常被纳入“网络设备”而漏管，建议按业务影响而非设备类型分级。
6. **为尚未完成分析的条目留出复核位**：本期 75.8% 的条目处于 `Deferred`／`Awaiting Analysis`，CVSS 存在上修可能，建议在 T+7 时对本批复核一次等级变更。
