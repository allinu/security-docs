### 1.3 今日重点关注

1. **`CVE-2026-115905`：Rust `zip` 库中央目录与本地头解析不一致：同一压缩包可“检查是白的、解压是黑的”（10.0）**  
   `zip` 9.0.4 及之前，`ZipArchive` 把 **Central Directory File Header 中的文件名当作权威**，而 `ZipStreamReader` 在流式解压时**用 Local File Header 的文件名**、且不核对两份元数据（`src/read/stream.rs`）。于是**一个特制压缩包可以对“检查中央目录的组件”显示为无害，却让流式解压器把攻击者选定的路径与内容写到别处**，可能覆盖下游服务使用的文件。CVSS 10.0，归入 `CWE-20` 与 `CWE-436`（解释冲突）。**这类“同一个格式有两种解析结果”的缺陷（parser differential）在压缩包、归档、镜像、文档格式中反复出现，且天然适合绕过“先扫描后解压”的架构。**

2. **`CVE-2026-112346`：OpenHands Agent SDK 默认绑 0.0.0.0 且密钥列表为空：未认证即 root Shell（9.3）**  
   OpenHands Software Agent SDK 1.52.0 之前，`DockerWorkspace` 与 `Apptainer` 两种 workspace 启动器把**沙箱内的 agent server 绑定到所有网卡（0.0.0.0）且 `session_api_keys` 为空列表——默认关闭认证**。能访问该发布容器端口的攻击者即可通过未认证的 HTTP/WebSocket 请求**在沙箱内以 root 执行任意 shell 命令**、访问挂载的工作区，并**从 secrets store 读取明文密钥**。这是“把执行能力当产品卖”的 AI Agent 平台的通病：**默认值为了易用而关闭了唯一的安全边界**。

3. **`CVE-2026-93328`：Google Cloud MCP Toolbox 路径遍历 + 缺失授权：未认证者把宿主文件外传到自有 GCS 桶（9.3）**  
   `googleapis/mcp-toolbox` 1.2.0–1.4.0 的 cloud-storage 数据源存在路径遍历与缺失授权（`CWE-22`／`862`）：**未认证远程攻击者可通过构造工具调用参数，把宿主文件外传到外部的 Google Cloud Storage 桶，或覆盖任意本地文件**。MCP（Model Context Protocol）工具服务器正在成为 AI 应用的标配组件，其设计假设通常是“调用者已在可信环境内”——**当它被暴露在网络上时，等价于一个未认证的文件读写 + 出网通道**。

4. **`CVE-2026-18450`：Supermicro BMC 未强制 IPMI 完整性与加密：可向活动会话注入命令（9.8）**  
   Supermicro BMC 的 IPMI 实现**未正确强制执行完整性与加密要求**（`CWE-306`），攻击者可**构造数据包在活动会话中执行任意命令**。BMC 是服务器的“带外管理”平面——它独立于操作系统、通常拥有电源控制、虚拟媒体、KVM 与固件更新能力。**BMC 被拿下意味着无论操作系统打得多干净都没有意义**：攻击者可重装系统、植入固件级后门、或直接关机。IPMI 的历史问题（2.0 规范中的明文密码哈希、RAKP 协议缺陷）使这类缺陷尤其危险。

### 1.4 综合研判

本期 820 条（未评分 328 条，占 40.0%），已评分部分中严重 20 条（2.4%）、高危 150 条（18.3%），但因未评分占比过高，**真实严重数应显著高于 20**。三条主线：**第一，解析器差异（parser differential）**——Rust `zip` 的中央目录 vs 本地头不一致（10.0）是本期技术上最有价值的一条：它不需要任何“漏洞原语”，只需要**两个组件对同一份数据得出不同结论**，就能让“安全检查通过、实际执行危险”。同类问题在解压、镜像加载、文档转换、包管理器里普遍存在，值得作为架构级风险登记。**第二，AI 组件的默认不安全**——OpenHands 的 workspace 绑定 `0.0.0.0` 且空密钥列表（9.3，未认证 root）、Google MCP Toolbox 的路径遍历 + 缺授权（9.3，外传宿主文件）、以及前一期的 Langchain-Chatchat／DB-GPT／Letta。**这一族缺陷的共同点是“为易用而关闭安全”，且多部署在内网、缺少评审**。**第三，基础设施与边界设备**——FortiSandbox 的替代路径认证绕过（9.8，可执行未授权代码/命令）、Consul-k8s 跨命名空间授权绕过（9.9）、Supermicro BMC 的 IPMI 完整性问题（9.8）、Mautic 的活动导入任意文件上传（9.9，普通权限即可写脚本到 Web 根）、Esri ArcGIS Server 的 SQL 注入（9.8）、TOTOLINK 缓冲溢出（9.3）。KEV 侧本期新增 PHP 两条（期限 10-29），与 10-26 的报告形成连续跟踪。整体判断：本期属“**高信息量、可利用性分化**”的一天——没有 KEV 级在野爆点，但 `zip` 与 OpenHands/MCP Toolbox 三条提示了两个正在扩散的结构性风险（解析器差异、AI 组件默认配置）。

!!! danger "研判结论：较高风险"
    本期无在野利用的新增证据（KEV 两条为 PHP 的延续跟踪），但建议立即做三件事：① **在解压/归档处理链路上增加“两份元数据一致性校验”**（zip 的教训可推广到 tar、7z、ISO、容器镜像）；② **对内部 AI/Agent 平台做默认配置清查**——绑定地址是否 `0.0.0.0`、认证密钥是否为空、工具服务器是否可从非受信网段访问；③ **BMC 与 IPMI 纳入独立台账**，禁止管理网与业务网混用，并按厂商公告更新固件。

#### 3.1.2 漏洞摘要

Rust `zip` 库（至 9.0.4）存在解析不一致缺陷，CVSS 10.0（`CWE-20` 输入校验不当、`CWE-436` 解释冲突）。技术细节明确：**`ZipArchive` 把 Central Directory File Header 中的文件名当作权威**，而 **`ZipStreamReader` 在流式解压时使用 Local File Header 中的文件名，且不核对这两份重复的元数据**（实现位于 `src/read/stream.rs`）。ZIP 格式本身允许中央目录与本地头各存一份文件名，正常工具应校验二者一致；当实现选择不同来源时，**同一个压缩包就会在不同代码路径上产生不同结果**。攻击者因此可以构造一个包：**对“先扫描中央目录判断是否安全”的组件显示为无害文件，而流式解压器却把攻击者选定的路径与内容写出**，可能覆盖下游服务使用的文件（配置、脚本、模板），进而在下游触发执行。修复版本 9.0.5。这条漏洞的迁移价值远大于它自身：**凡是“先检查、再处理”的架构，只要检查与处理使用不同的解析器，就存在被绕过的可能**。 编制时 GitHub 上已出现一个针对该缺陷的仓库（`foxcornlab/zip-cloaking-scanner`，创建于 2026-10-27），**其自述定位为“仅检测用的分诊扫描器”**，用于识别中央目录与本地头不一致的归档——**目前尚未见破坏性利用代码公开**，但检测工具的出现通常先于武器化，建议把该类归档纳入上传校验。

> 原文摘要（NVD）：zip is a zip library for Rust that supports reading and writing simple ZIP files. Through 9.0.4, ZipArchive treats Central Directory File Header filenames as authoritative while ZipStreamReader extracts using Local File Header filenames without reconciling the duplicate metadata in src/read/stream.rs. A crafted archive can therefore appear benign to a component that inspects the central directory but cause a streaming extractor to write a different attacker-selected path and content, potentially overwriting files used by a downstream service. This issue is fixed in version 9.0.5.

**技术原理：**

ZIP 是“目录 + 条目”结构：每个条目在本地头里有一个文件名，全部条目又在中央目录里登记一次。健壮的实现必须**以其中一份为准并拒绝不一致**，否则就产生 parser differential。此处两条路径各自选择了一份：`ZipArchive`（随机访问，基于中央目录）信中央目录；`ZipStreamReader`（顺序读取，只能看到本地头）信本地头。攻击者只需让两份名字不同（中央目录写 `innocent.txt`、本地头写 `../../etc/cron.d/x`），即可让安全检查与解压行为分叉。这类缺陷不需要内存破坏，也与语言无关——**它利用的是“对同一份数据的多种合法解读”**。

#### 3.4.2 漏洞摘要

Supermicro BMC（基板管理控制器）的 IPMI 实现**未正确强制执行完整性与加密要求**（`CWE-306` 关键功能缺失认证），CVSS 9.8：攻击者可**构造数据包在活动会话中执行任意命令**。BMC 是服务器的**带外管理平面**——独立于操作系统运行，具备电源控制、虚拟媒体（挂载 ISO）、KVM over IP、固件更新与传感器读取能力。**因此 BMC 被拿下的意义远超“一台主机失陷”**：攻击者可远程重装系统、以虚拟媒体植入引导级恶意代码、读取内存/屏幕内容、或在补丁齐全的操作系统上直接关机。IPMI 2.0 规范本身存在历史包袱（RAKP 协议缺陷、密码哈希使用 MD5 且可离线爆破），使“未强制完整性/加密”的后果被进一步放大。这类设备通常与管理网同段、口令多年未改、固件极少更新。

## 五、当日处置建议

1. **把“解析器差异”列为架构级风险**：本期 Rust `zip` 的教训可推广到 tar/7z/ISO/容器镜像/文档转换。检查项：**检查与执行是否使用同一解析器**、是否校验重复元数据的一致性。凡“先扫后解”的流程都要复核。
2. **AI/Agent 平台默认配置三查**：监听地址是否 `0.0.0.0`、认证密钥是否为空、端口是否对外发布。OpenHands、Langchain-Chatchat、DB-GPT、Letta 在本轮补齐期内反复出现同类问题，建议一次性统一基线。
3. **MCP 工具服务器按“高权限服务”对待**：它同时具备文件访问与出网能力。要求：认证、路径规范化、出站白名单、非 root 运行。不要把“本地 IDE 插件”的假设直接搬到网络部署。
4. **BMC/IPMI 独立建账**：带外管理面一旦失陷，操作系统层面的所有加固都会失效。建议单列台账、管理网隔离、关闭 IPMI over LAN（若不用）、禁用弱 cipher suite。
5. **EPSS/KEV 的滞后要写进流程**：本期 EPSS 覆盖率仅 2.7%（数据集截至 10-26），说明“按 EPSS 排优先级”在当日场景不可靠。建议规则改为“KEV/在野 > 有 PoC > 组件关键性 > EPSS”，并为未评分条目保留人工复核位。
6. **PHP 两条 KEV 在 10-29 前闭环**：`CVE-2026-109618`／`109619` 的期限为 2026-10-29，且已有 Exploit-DB 利用代码（PHP2Shell）。若尚未完成 PHP 版本盘点，应作为本周唯一 P0 推进。
