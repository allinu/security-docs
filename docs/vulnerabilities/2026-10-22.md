### 1.3 今日重点关注

1. **`CVE-2026-109618`：PHP 核心 OOM 路径内存未初始化致 RCE：EPSS 99.98%，Exploit-DB 已有 PHP2Shell（9.2）**  
   PHP 使用 `longjmp()` 处理 **OOM（内存耗尽）** 错误以退出当前上下文并中止请求处理。部分上下文**未正确处理这一情形**，在内存分配前把请求内存留在未初始化状态，随后的请求清理流程会**读取或基于该内存做分支**。多种 OOM 触发策略可稳定复现，**最终导致远程代码执行**。Exploit-DB `EDB-52704`「PHP2Shell」覆盖 **PHP 5.4 之后的核心版本**，Nuclei 亦有模板，EPSS 99.98%。**PHP 是互联网上部署最广的服务端运行时，这一条的影响面按“所有未打补丁的 PHP 应用”计算。** 编制时 GitHub 上与该编号相关的仓库已达 **478 个**（含按版本判定的检测脚本与“php2shell-version-frontier”一类工具），**数量级远超普通漏洞，属典型的“大规模复现运动”**——这意味着扫描与尝试几乎必然已经发生。

2. **`CVE-2026-109619`：PHP 全局状态指向已释放请求内存（stale internal request-state）致 RCE（9.2，EPSS 99.997%）**  
   与上一条同批披露：PHP 有多处**临时指向请求内存的全局状态**，在某些场景下未被正确重置、或在重置后又被重新填充，导致全局状态在请求内存被释放后**仍然引用该内存**；后续请求在完全初始化之前读取或基于这份**陈旧状态**做分支，多种策略可触发 **RCE**。EPSS 99.997% 是本轮回溯期的最高值。两条漏洞的利用方式互补（一条走 OOM 路径、一条走全局状态生命周期），**说明 PHP 请求生命周期的内存管理存在系统性问题**，而非孤立缺陷。

3. **`CVE-2026-87337`：Oracle 10 月 CPU：1076 条中 64 条严重，Fusion Middleware 多个 10.0**  
   Oracle 本批一次性提交 1076 条（占本期 53.9%），其中严重 64 条。多条为 10.0 满分：`CVE-2026-87337`（Access Manager，认证组件）、`CVE-2026-91216`／`91221`（SOA Suite Fabric Layer）、`CVE-2026-91231`（SOA Suite Adapters）、`CVE-2026-91299`（JD Edwards EnterpriseOne Orchestrator）、`CVE-2026-101809`（E-Business Suite Workflow）。Oracle 条目的特点是**描述极简（仅给出组件与“远程可利用”）、CVSS 高但利用链不公开**，实际处置只能按“暴露面 + 组件重要性”排序，无法按 PoC 判断。

4. **`CVE-2026-105944`：Apache Pulsar Manager：创建初始管理员的接口始终匿名可用（10.0）**  
   Pulsar Manager 的**“创建初始超级管理员”操作无需认证，且在实例完成初始化之后仍然可用**。任何能访问 Pulsar Manager 的人都可以**随时新建一个管理员账号并登录**。同批还有：代理 Pulsar admin API 的请求使用了 Manager 自身配置的凭据（导致权限提升）。CVSS 10.0。Pulsar 是主流消息中间件，Manager 是其管理控制台——**拿到管理员等价于能创建/删除租户、读取所有主题数据**。同期的 `CVE-2026-111813`（Apache Traffic Server magick 插件，未认证客户端可控制 ImageMagick `convert` 参数，10.0）与 `CVE-2026-81212`（IBM DataStage on Cloud Pak for Data，未认证可向共享 Redis 任意写入、污染任意租户缓存，10.0）也属“配置/设计层面直接给出高权限”的类型。

#### 3.1.2 漏洞摘要

PHP 核心存在内存破坏缺陷：PHP 使用 `longjmp()` 处理**内存耗尽（OOM）** 错误，以此退出当前上下文并中止对请求的处理。**部分上下文未正确处理这一情形**，在执行内存分配之前把请求内存留在**未初始化状态**；随后请求清理流程会**读取或基于这块内存做分支**。公告明确“多种 OOM 触发策略可稳定复现该条件，并导致远程代码执行（RCE）”，CVSS 9.2，归入 `CWE-416`（UAF）、`CWE-755`（异常处理不当）、`CWE-824`（未初始化指针访问）、`CWE-1325`（资源生命周期管理不当）。**可利用性证据是本轮回溯期最强的**：Exploit-DB `EDB-52704`「PHP2Shell」明确覆盖 **PHP 5.4 之后的核心版本**，Nuclei 有检测模板，EPSS 99.98%，CISA 于 2026-10-26 纳入 KEV。这意味着“能不能被利用”已不需讨论，问题只剩“你的 PHP 打了补丁没有”。注意其触发依赖 OOM 条件——**攻击者可以主动构造请求把内存推到极限**（例如提交超大 POST、深递归、巨大数组），因此“内存充足所以触发不了”不是有效缓解。

> 原文摘要（NVD）：PHP uses longjmp() for out-of-memory (OOM) errors to exit the current context and abort handling of the request. Some contexts may not properly account for this scenario and leave request memory in an uninitialized state before performing an allocation. The subsequent request cleanup procedure may read or branch on this memory. Multiple OOM strategies can consistently trigger this condition and lead to remote code execution (RCE).

| 条件 | 状态 | 说明 |

**技术原理：**

OOM 属于“无法继续执行、必须立即退出”的异常路径。PHP 用 `longjmp()` 直接跳出深层调用栈，跳过正常的清理与初始化收尾。若某个上下文没有在 `longjmp` 后重新建立一致状态（例如未清零指针、未重新分配缓冲区），请求清理阶段就会读到未初始化（或已释放）的内存。攻击者控制的是“OOM 发生的位置与时机”，从而控制哪些结构停在半初始化状态——**这使得原本“随机”的内存破坏变成了可稳定触发的利用原语**。与 `CVE-2026-109619`（全局状态陈旧引用）配合看，两条缺陷分别从“异常路径”与“正常路径的全局状态生命周期”两个方向暴露了请求内存管理的系统性弱点。

**核心利用链：**

```text
攻击者
```

#### 3.2.2 漏洞摘要

PHP 核心的全局状态中有若干**临时指向请求内存**的指针。在某些场景下，这些全局状态**未被正确重置**，或者**在被重置之后又被重新填充**；结果是请求内存已经释放，全局状态却仍然引用它。后续请求在**尚未完全初始化**时读取或基于这份**陈旧状态**做分支判断，从而产生不可预期的行为；公告指出“多种策略可触发该条件并产生远程代码执行（RCE）”，CVSS 9.2（`CWE-416`／`755`／`824`／`1325`）。**EPSS 99.997% 是本轮回溯期的最高值**，与 `CVE-2026-109618` 同批被 CISA 纳入 KEV（2026-10-26）。与前者相比，本条不依赖 OOM——它利用的是**请求之间状态未隔离**，这在长驻进程模型（`php-fpm`、RoadRunner、Swoole 等常驻内存运行时）中风险更高，因为进程在请求之间不会被销毁。

> 原文摘要（NVD）：PHP has various global state that temporarily points into request memory. In some scenarios, global state may not be correctly reset, or may be repopulated after being reset. The global state may then refer to request memory even after it has been freed. Subsequent requests may read or branch on this stale state before it is fully initialized. Multiple strategies can trigger this condition and produce remote code execution (RCE).

#### 3.2.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 任何暴露到网络的 PHP 应用（长驻运行时风险更高） |

**技术原理：**

传统 `mod_php`/CGI 模型“一个请求一个进程”，请求结束进程即销毁，因此状态残留影响有限。但 `php-fpm` 复用 worker 进程，常驻型运行时（Swoole/RoadRunner）更是显式地在同一进程内处理多个请求。当全局状态（如编译缓存、过滤器句柄、语言环境、错误处理上下文）在请求结束时未彻底清理，下一个请求就可能读到上一请求的残留指针。若该指针指向已释放的请求内存，且其内容可被攻击者影响（例如通过上一请求分配可控数据），即可形成“跨请求的 UAF 利用”。

**核心利用链：**

## 五、当日处置建议

1. **PHP 是今日唯一的 P0**：EPSS 近 100% + Exploit-DB 有 PHP2Shell + Nuclei 可验证 + KEV 收录，四项齐全。建议按“可能已被利用”处置：先盘点版本（含容器镜像与设备内置 PHP），再升级，再排查 webshell 与异常进程。**注意“内存充足所以打不了”是错误假设——攻击者可主动构造 OOM。**
2. **限制 OOM 可及性作为临时缓解**：收紧 `memory_limit`、`post_max_size`、`max_input_vars` 与并发，并在网关层限制单请求体大小与参数深度，可显著降低被批量尝试的成功率。
3. **清点 Oracle 暴露面而非逐条研判**：本期 1076 条 Oracle 条目无法按 PoC 判断，有效动作是“找出可从公网/办公网访问的 Oracle 管理端口（7001/7002/APEX/ORDS）”。这一步的收益远大于逐条读公告。
4. **关闭“初始化向导”类接口**：Pulsar Manager 的教训是安装完成后接口未下线。建议对所有产品做一次检查：初始化/首次配置端点是否仍可匿名访问。
5. **代理型服务要传用户身份而非复用自身凭据**：Pulsar Manager 用自身 token 调后端 admin API 导致权限提升。建议对自研代理层强制“用户凭据透传 + 权限裁剪”。
6. **多媒体与图像解析栈持续高危**：GStreamer（rtpL16depay）、Traffic Server 的 ImageMagick 调用说明“解析不可信媒体”仍是稳定的 RCE 入口，建议对这类处理链路做独立隔离（容器 + 低权限 + 无外网）。
