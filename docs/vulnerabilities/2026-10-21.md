### 1.3 今日重点关注

1. **`CVE-2026-75128`：Langchain-Chatchat `/tools/call` 未认证调用任意工具：内置 shell 工具可直接执行命令（9.3）**  
   Langchain-Chatchat ≤0.3.1.3 暴露 `POST /tools/call` 端点，**按名称调用任意已注册工具且不校验认证**，而 **shell 工具始终处于注册状态**。攻击者只需一次请求、工具名填 shell，即以服务用户身份执行任意 OS 命令——**官方 Docker 镜像中该用户是 root**。同期的 DB-GPT（`CVE-2026-77932`，9.3）问题更彻底：`/api/v1/chat/react-agent` 依赖一个 **mock 的 `get_user_from_headers` 函数，把所有调用者都当作 admin**，进而让未沙箱的 `code_interpreter`／`shell_interpreter` 以 root 执行 Python 或 bash。

2. **`CVE-2026-113672`：Argo CD repo-server jsonnet importer 逃逸仓库根：可读 SA token 与凭据（9.9）**  
   Argo CD 0.9.0 至 3.3.15/3.4.10/3.5.4/3.6.0-rc2，repo-server 在求值 `.jsonnet` 时，importer **未把 `import`／`importstr`／`importbin` 限制在仓库根目录**。绝对路径、父目录穿越、仓库内符号链接都能打开 repo-server 可读的任意文件——包括 **`/proc/self/environ`、投射的 ServiceAccount token、挂载的私钥与仓库凭据**。虽然生成的 Secret 会被脱敏，但把导入内容放进 ConfigMap 就能绕过脱敏把数据带出。GitOps 工具持有“能部署一切”的权限，**它的 repo-server 等价于集群的配置中心**。

3. **`CVE-2026-113620`：Eclipse ioFog Controller exec/log WebSocket 不校验 JWT（9.8）**  
   ioFog Controller 3.8.0–3.9.1 中，**operator 的 WebSocket 升级请求（exec 与 log 路由）不校验 bearer JWT**，而是直接解码载荷并用其中的 `groups`／`roles` 作为 RBAC subject。攻击者**自签一个 `groups` 含 `admin` 的令牌**即可匹配内置 admin 角色——不需要账号、不需要 RoleBinding——只要知道目标微服务或 fog 的 UUID，就能开 exec 或 log 会话。HTTP 路由与 agent WebSocket 不受影响（它们先验令牌）。这是“只解码不验签”的典型，与 JWT 算法混淆属同一族问题。

4. **`CVE-2026-105312`：Strimzi Console CR 权限设计缺陷：租户可跨租户接管 Kafka 控制面（9.9）**  
   拥有 Console 自定义资源创建权限的 Kubernetes 租户，可以把 `spec.containers.api.spec.image` 设为**任意镜像**。operator 会把该镜像部署到一个 pod 中，而该 pod 的 ServiceAccount 通过 ClusterRoleBinding 绑定了集群级权限（对全部 Strimzi CRD 的 get/list/watch、对 Kafkas/KafkaRebalances 的 patch、cluster-monitoring-view）。攻击者代码读取投射的 SA token 即获得**跨租户的 Strimzi 控制面读写能力**。根因是“CRD 字段可被租户控制 + operator 以高权限部署该字段指定的镜像”，属于 Operator 设计的经典权限陷阱。

### 1.4 综合研判

本期 445 条，严重 34 条（7.6%）、高危 128 条（28.8%），整体中高位。**第一主线是 AI 应用框架的“执行面失控”**：Langchain-Chatchat 的 `/tools/call`（未认证 → shell 工具 → root 命令）、DB-GPT 的 react-agent（mock 认证 → 未沙箱解释器 → root）、Letta 的 compose 默认未开 `LETTA_SERVER_SECURE`（所有 API 无认证 + 暴露带默认凭据的 PG 端口，可经 `COPY PROGRAM` 执行命令）、piflow 的 DeepAgents 聊天代理（`CVE-2026-109442`）、OpenSRE 与 EvoScientist 的审批门绕过（`CVE-2026-109444`／`77930`）。这些产品的共同设计是“让模型调用工具执行代码”，**而工具执行通道普遍缺少认证、沙箱与审批三件套**；它们又多以 Docker Compose 形态部署在内网，**被当作“实验环境”而跳过安全评审**。第二主线是**云原生交付链的信任边界**：Argo CD 的 jsonnet importer 逃逸（可读 SA token 与仓库凭据）、Strimzi operator 的跨租户提权（CR 字段被租户控制 → 高权限 pod）、ioFog 的 WebSocket JWT 不验签。第三类是**开发库的内存安全**：Pillow 一次披露 4 条 9.2（Ghostscript 参数注入、多路径堆溢出与越界写），影响所有做图像处理的 Python 服务。KEV 无新增，节奏上属“缓冲期”，但**上述 AI 框架条目一旦被暴露到公网，其实际危害等同于未认证 RCE**，不应因 EPSS 低而降级。

!!! danger "研判结论：较高风险"
    本期无在野利用、无公开 PoC，但**存在多条“一条请求即 root”的未认证利用路径**（Langchain-Chatchat、DB-GPT、Letta），且都出现在常被当作“内部实验平台”的 AI 框架上。建议：① 对内部所有 Chatchat／DB-GPT／Letta／piflow 类部署做一次清单与暴露面核查，禁止公网可达；② Argo CD 升级至 3.3.15／3.4.10／3.5.4 并核查 repo-server 的 SA 权限；③ Strimzi 核查 Console CR 的 RBAC 授予范围；④ Pillow 升级至 13.0.0，并禁止对不可信来源的 EPS 做转换。

#### 3.1.2 漏洞摘要

Langchain-Chatchat 至 0.3.1.3 暴露了 `POST /tools/call` 端点（实现见 `libs/chatchat-server/chatchat/server/api_server/tool_routes.py#L33`），该端点**按名称调用任意已注册工具，且不做任何认证校验**。由于 **shell 工具始终处于注册状态**，远程攻击者只需发送一次请求、把工具名指定为 shell，即可**以服务进程用户身份执行任意操作系统命令**——而官方随附的 Docker 镜像中该用户是 **root**。CVSS 9.3（`CWE-306` 关键功能缺失认证）。这条漏洞不涉及复杂的利用链：**它就是产品设计里留给自己的“执行任意命令”的能力，只是忘了加认证**。对部署在内网、被当作“知识库问答实验平台”的 Chatchat，实际风险取决于其网络可达范围；一旦为方便访问而映射到公网或大网段，等价于给攻击者一个 root 命令通道。

> 原文摘要（NVD）：Langchain-Chatchat through 0.3.1.3 exposes a POST /tools/call API endpoint that invokes any registered tool by name without authentication, leaving the always-registered shell tool callable. Remote attackers can send a single request naming the shell tool to execute arbitrary OS commands as the server user (root in the shipped Docker image).

#### 3.1.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | HTTP API（`/tools/call`）可达 |
| 身份认证 | 无需 | 无需任何凭据即可触发 |
| 用户交互 | 不需要 | 无需受害者交互 |
| 特定配置 | 否 | 默认部署即暴露；shell 工具默认注册 |
| 利用复杂度 | 低 | 低（单请求，无需凭据） |

**技术原理：**

Agent 框架需要“工具（tool）”抽象：模型输出工具名与参数，框架据此调用对应实现。厂商为了调试与扩展，注册了一批内置工具（搜索、计算、shell、python 执行）。`/tools/call` 是给前端或外部系统直接调用工具的入口，其设计假设是“调用者已在可信环境内”。缺失认证使该假设不成立：任何能访问 HTTP 端口的人都可以直接点名调用工具，绕过模型的“决策”环节。**这类端点是 AI 应用中最高价值的攻击面，因为它是“意图 → 执行”的直通车。**

**核心利用链：**

```text
攻击者
  └─ 定位暴露的 目标组件（目标产品）
      └─ 直接访问受保护接口或伪造身份
          └─ 触发 CWE-306 对应处理逻辑
              └─ 绕过认证获得未授权能力
                  └─ 横向利用或持久化（视环境）
```

#### 3.1.8 检测与排查

| 检测项 | 可疑特征 |

#### 3.4.2 漏洞摘要

在 Strimzi（Kubernetes 上的 Kafka Operator）环境中，**拥有 Console 自定义资源（CR）创建权限的租户**可以把 `spec.containers.api.spec.image` 设置为**任意容器镜像**。Strimzi operator 会把该镜像部署到一个 pod 中，而该 pod 的 ServiceAccount 通过 **ClusterRoleBinding 绑定了集群级 ClusterRole**：对全部 Strimzi CRD（含 `KafkaUsers`）的 get/list/watch、对 `Kafkas`／`KafkaRebalances` 的 patch、以及 `cluster-monitoring-view`。攻击者在自己的镜像里读取**投射的 SA token**，即可获得**跨租户的 Strimzi 控制面读写权限**——包括读取其他租户的 `KafkaUsers`（其中常含 SASL 凭据）、修改 Kafka 与重平衡配置。CVSS 9.9（`CWE-269`）。这是 Kubernetes Operator 的典型陷阱：**CRD 字段由租户控制，operator 却以高权限把它“落地”为工作负载**。

> 原文摘要（NVD）：A Kubernetes tenant with create permission on Console custom resources can set spec.containers.api.spec.image to an arbitrary container image. The operator deploys this image into a pod whose ServiceAccount is bound via ClusterRoleBinding to a ClusterRole granting cluster-wide get/list/watch on all Strimzi CRDs (including KafkaUsers), patch on Kafkas/KafkaRebalances, and cluster-monitoring-view. The attacker's code reads the projected SA token and gains cross-tenant Strimzi control-plane read+write access.

#### 3.4.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | Kubernetes API（创建/修改 Console CR） |

**技术原理：**

Operator 的职责是把 CR 声明的期望状态转化为实际资源。当 CR 中的字段能指定“运行什么镜像”时，创建 CR 的能力就等价于“以 operator 的权限运行任意代码”。本例中 operator 使用的 SA 具备集群级权限（因为它需要跨命名空间管理 Kafka 资源），权限被“借用”给租户指定的镜像。正确设计应限制可指定的镜像（固定镜像仓库 + 摘要校验），或使用受限 SA 且按命名空间隔离权限。

              └─ 造成信息泄露、拒绝服务或状态破坏
                  └─ 横向利用或持久化（视环境）

## 五、当日处置建议

1. **给 AI 框架的“工具执行端点”做统一清单**：`/tools/call`、`/v1/tools/run`、`code_interpreter`、`shell_interpreter`、`react-agent` —— 这些端点的共同特征是“输入即执行”。要求：必须认证、必须沙箱、必须审批，三者缺一不可。
2. **不要因为“实验环境”跳过评审**：本期多条漏洞出现在以 Docker Compose 部署的 AI 平台，这类环境常有默认口令、无认证、root 运行。建议把“AI 实验平台”纳入正式资产，至少要求“非 root + 非公网 + 无默认口令”。
3. **GitOps 工具按“配置中心”级别防护**：Argo CD 的 repo-server 能读 SA token 与仓库凭据，它一旦被穿透，影响的是整个集群。建议限制 SA 权限、禁用不需用的配置工具（jsonnet/helm/kustomize 按需开启）、并监控 ConfigMap 异常变更。
4. **Operator 类系统审查“租户可控字段 → 高权限部署”路径**：Strimzi 的例子说明，CR 中凡是能指定镜像/命令/卷的字段，都应视为“以 operator 权限执行代码”的入口，必须用准入策略限制。
5. **WebSocket 路径不要成为认证盲区**：ioFog 的教训是“HTTP 路由验签、WS 路由漏了”。建议在网关层对**所有**升级请求统一做认证，而不是依赖各组件自行实现。
6. **Pillow 全量升级并禁止不可信 EPS**：Python 图像处理栈普遍依赖 Pillow，本期 4 条 9.2 集中在解码器与 Ghostscript 调用。除升级至 13.0.0，建议直接禁止处理不可信来源的 EPS/PS 文件。
