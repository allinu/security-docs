### 1.3 今日重点关注

1. **`CVE-2026-108263`：Astron Agent 默认执行器未沙箱：低权限租户可在容器内以 root 执行代码（9.9）**  
   iFlytek 的 Astron Agent 在 1.1.2 之前，`/console-api/workflow/code/run` 与 `/workflow/v1/run` 的代码节点默认走 `LocalExecutor`（`core/workflow/engine/nodes/code/code_node.py`），**未启用文档所述沙箱，直接向动态执行环境暴露完整 Python builtins**。认证后的低权限租户即可在 core-workflow 容器内以 root 身份执行代码，并借助容器内共享的服务凭据与数据库凭据**绕过应用层租户隔离**，读取或篡改其他租户数据。这是本期最具“横向后果”的条目：多租户 AI 平台的隔离假设被从执行层击穿。

2. **`CVE-2026-103889`：WooCommerce 3D Product Configurator 未认证 RCE（9.8，PoC 已公开）**  
   插件 ≤2.16.2 的 `wp_loaded` 处理器里，**唯一的 nonce 与认证检查被整体包在块注释中且没有替代实现**，攻击者向任意 URL 发一个未认证 POST、在 `xpv_image` 参数中注入内容，该内容会被原样拼进 Dompdf 渲染的 HTML 模板且模板允许 PHP 执行，最终形成 RCE。GitHub 已有 PoC 仓库，NVD 引用中亦给出插件源码行号（`class-pdf.php#L34`、`class-expivi-cart-manager.php#L212/238/598`），**属于“可读源码即可复现”的类型**。

3. **`CVE-2026-103501`：Apache DataSketches C++ HLL 反序列化堆溢出（9.8）**  
   `1.0.0-incubating` 至 `5.3.0` 之前，LIST 模式反序列化时**从输入读取 coupon 计数后直接作为拷贝条目数写入固定 8 项缓冲区，未校验容量**，最多可越界写入 988 字节。触发条件是“从不可信来源反序列化 HLL sketch”。该库被大量数据分析、监控与 OLAP 组件内嵌，**漏洞不在业务代码而在数据处理底座**，建议按依赖清单排查而非按产品名排查。

4. **`CVE-2026-108474`：JetBrains Exposed ORM SQL 注入（9.8）**  
   Exposed 1.5.1 之前，多个 SQL 函数对字符串参数未做转义，导致注入。ORM 层注入的隐蔽性高于业务代码注入：**调用点通常“看起来是参数化的”**，实际把用户输入拼进了函数参数。Kotlin 服务端项目应升级至 1.5.1 并检索 `exposed` 相关依赖版本。

### 1.4 综合研判

本期有效 359 条，严重 86 条（24.0%）、高危 144 条（40.1%），严重占比为本轮补齐期内最高值。但结构极不均衡：**WordPress 生态（主题／插件）占 55.2%，且几乎全部为“未认证 + 9.8”的模板化披露**——ThemeREX／Axiomthemes 等商业主题厂商一次性提交数十条 PHP 对象注入（`CVE-2026-62045` 至 `CVE-2026-93945` 区间），Patchstack 侧则贡献了大量“未认证 PHP 对象注入／任意文件上传／权限提升”。这类条目的 CVSS 向量高度一致（`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`），**说明评分模型对 WordPress 插件生态已近乎失去区分度**，研判价值必须回到“是否可达”“是否启用”“是否有 PoC”三个维度。真正具备跨环境影响的是四条非建站类条目：Astron Agent（多租户隔离击穿，容器内 root）、JetBrains Exposed（ORM 层 SQL 注入）、Apache DataSketches（数据处理库内存破坏）、Floci 的 Velocity 模板注入（`$util` 反射可达 `Runtime`/`ProcessBuilder`）。PoC 生态侧，本期检得 2 条具备公开利用代码或检测模板的编号（`CVE-2026-103889` 有 GitHub 仓库与源码定位、`CVE-2026-91136` 有 Nuclei 模板），其余 357 条在四源中均无命中；EPSS 最高值仅 2.9%，进一步印证“披露密集但武器化滞后”。KEV 无新增，在野利用压力处于近期低位。

!!! danger "研判结论：较高风险"
    本期风险呈“**面广而点弱**”特征：条目数量与严重占比都高，但绝大部分集中在 WordPress 建站侧且尚无武器化证据。建议不要按“86 条严重”平均分配处置资源，而应把 **Astron Agent（租户越界）** 与 **Apache DataSketches（库级内存破坏）** 作为架构性风险优先评估，把 WordPress 侧收束为一次“插件与主题清单比对 + 上传目录禁止解析 PHP”的批量作业，用一条流程覆盖 198 条编号。

#### 3.1.2 漏洞摘要

Astron Agent 是构建与运行 AI Agent 的智能体工作流平台。1.1.2 之前，`/console-api/workflow/code/run` 与 `/workflow/v1/run` 两个入口在处理“代码节点”时，若未显式配置 `CODE_EXEC_TYPE`，会默认选择 `LocalExecutor`（实现位于 `core/workflow/engine/nodes/code/code_node.py`）。该执行器**并未施加文档所声称的沙箱限制**，而是把完整的 Python builtins 暴露给动态代码执行，等价于把容器内的 Python 解释器交给租户。后果分三层：第一层是同容器内的任意代码执行（以 root 身份）；第二层是**借助容器共享的服务凭据与数据库凭据绕过应用层租户校验**，直接读写其他租户数据；第三层是对共享服务（工作流引擎、消息队列、模型网关）的干扰。NVD 给出 5 个弱点分类（`CWE-95` 代码注入、`CWE-306` 缺失认证、`CWE-653` 隔离不充分、`CWE-863` 授权不当、`CWE-1392` 默认配置不安全），恰好对应这条“从执行层穿透到数据层”的路径。该条目要求攻击者具备低权限租户账号，因此不属未认证 RCE，但对**任何对外开放注册的多租户 Agent 平台**而言，注册即等于拿到立足点。

#### 3.1.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 平台 API（`/console-api/workflow/code/run`、`/workflow/v1/run`）可达 |
| 身份认证 | 普通用户 | 需相应账号权限 |
| 用户交互 | 不需要 | 无需受害者交互 |
| 特定配置 | 是 | 未显式设置 `CODE_EXEC_TYPE` 时默认命中 `LocalExecutor`；已切换为沙箱执行器的部署不受影响 |
| 利用复杂度 | 低 | 低（租户账号 + 一次 API 调用） |

**技术原理：**

根因是“安全能力默认为关”。平台设计上提供沙箱执行器（受限于白名单模块、无网络、可资源配额），但默认值指向 `LocalExecutor`——一个直接 `exec()`/`eval()` 并注入 `__builtins__` 的实现。文档所述的沙箱限制只存在于另一条执行路径上，默认路径没有等价约束。攻击者提交代码节点后，可在其中调用 `os`、`subprocess`、`socket` 等模块，进一步读取容器内的环境变量（数据库口令、对象存储密钥、服务间 Token），再以外围服务的身份直接访问数据库，跳过平台自身的租户过滤逻辑。

**核心利用链：**

```text
攻击者
  └─ 定位暴露的 目标组件（目标产品）
      └─ 构造携带命令/表达式载荷的请求
          └─ 触发 CWE-95, CWE-306 对应处理逻辑
              └─ 以服务进程权限执行任意命令
                  └─ 横向利用或持久化（视环境）
```

#### 3.4.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 依赖 Exposed 的 HTTP 接口，且相关函数参数受外部输入影响 |

**技术原理：**

ORM 的价值主张之一是“自动参数化”，但多数 ORM 同时提供“原生 SQL 片段拼接”的逃生舱（如 `customFunction`、`wrapAsExpression`、排序表达式）。当这些逃生舱把 `String` 参数直接拼接而不走绑定变量，注入面就重新打开。与业务层注入相比，此类缺陷更难通过代码评审发现：调用点看起来像是调用了“安全的框架方法”。

**核心利用链：**

```text
攻击者
  └─ 定位暴露的 目标组件（目标产品）
      └─ 构造携带命令/表达式载荷的请求
          └─ 触发 CWE-89 对应处理逻辑
              └─ 以服务进程权限执行任意命令
                  └─ 横向利用或持久化（视环境）
```

## 五、当日处置建议

1. **给 WordPress 侧一条统一作业流程**：导出台账中全部站点 → 比对插件/主题清单与本期编号 → 命中即升级或停用 → 无论是否命中，统一禁止上传目录解析 PHP。这样可用一次作业覆盖 198 条编号，而不是逐条处置。
2. **多租户 AI/Agent 平台按架构风险处理**：Astron Agent 一类平台的“租户隔离”往往只做在应用层，一旦拿到代码执行，隔离即失效。建议核查所有代码执行类节点的执行器配置与容器凭据隔离。
3. **按依赖清单排查库级漏洞**：DataSketches（C++/Java/Python 绑定）与 Exposed（JVM）都属于“业务代码里看不见的依赖”，应通过 SBOM／依赖树比对版本，而不是靠产品名搜索。
4. **把“注释掉的校验”作为代码审计模式**：本期 CVE-2026-103889 的根因是认证检查被整块注释。建议对自研与二开代码做一次 `/* ... auth ... */` 类模式扫描，这类遗留往往是最容易被利用的。
5. **建立 PoC 命中优先级规则**：本期 359 条中仅 2 条有公开利用代码/模板，建议明确规定“有 PoC 的编号 24 小时内处置、无 PoC 的按暴露面排序”，避免资源被数量牵着走。
6. **留意 EPSS 的“新条目延迟”**：本期 EPSS 最高仅 2.9%，但新披露条目通常需要数天才会被扫描器采样，不宜据此判断“低危可拖”。
