### 1.3 今日重点关注

1. **`CVE-2026-111911`：phpMyFAQ WebAuthn 注册端点无认证无挑战校验，可绑定任意账号（9.3）**  
   4.0.0 至 4.1.9 之前，WebAuthn 注册端点**在未认证、未校验 challenge 的情况下把凭据挂到任意账号上**。攻击者先“占位”一个受害者用户名，提交伪造的 `fmt=none` 断言注册自己的 passkey，随后即可用该 passkey 登录，**同时绕过口令与 TOTP**。这是 WebAuthn 实现中最危险的一类错误——把“注册”当作可匿名操作，等于把最强的认证因子变成最强的后门。

2. **`CVE-2026-111853`：Tektronix 3 系 MDO 示波器 SCPI 命令注入与路径遍历（8.8 / 8.1）**  
   1.21.1 之前，`FILESystem:MOUNT:DRIve` SCPI 命令处理器**未充分中和用户输入**，远程攻击者可以**提升权限执行任意操作系统命令**（`CVE-2026-111853`，8.8）；同一 SCPI 文件接口还存在路径遍历（`CVE-2026-111854`／`111855`，8.1／7.5），可读写设备任意文件。示波器属实验室与产线测试设备，通常直接连在工程网段，**几乎不会被打补丁、也几乎不被纳入漏洞管理**——这类“有 IP 的仪器”是 OT/实验室环境里最容易被忽略的攻击面。

### 1.4 综合研判

本期仅 126 条，严重 8 条（6.3%）、高危 53 条（42.1%），无 KEV 新增、无 PoC 命中，整体处于低位。但从结构看有两点值得记录：其一，**phpMyFAQ 的 7 条缺陷构成一条完整的“认证链失效”**——WebAuthn 注册可匿名绑定（`CVE-2026-111911`）、改密不需要当前口令（`CVE-2026-111884`）、对象级越权（`CVE-2026-111908`）、组控制提权（`CVE-2026-111893`）、另有两条认证绕过（`CVE-2026-111882`）与 DoS（`CVE-2026-111901`）。单独看每条都是“中高危”，合起来意味着**该产品的认证与授权模型需要整体复核**，逐条打补丁不如一次性升级到 4.1.9 并审计账号状态。其二，**`Text::CSV_XS` 的 7 条缺陷集中在解析器的内存管理**（`CWE-416` UAF、`CWE-770` 无限制分配、`CWE-407` 算法复杂度、`CWE-127` 缓冲区下界读）。该模块是 Perl 生态最常用的 CSV 解析器，被无数批处理脚本与数据管道依赖，**9.8 的 UAF 意味着“解析一个恶意 CSV 就可能释放应用变量”**，对以 Perl 做数据交换的系统而言风险实在。此外，FreeRDP 服务器端 NTLM MIC 偏移校验缺失（`CVE-2026-111880`，8.3，未认证可写 16 字节越界）与 Fleet MDM 的 plist 递归（`CVE-2026-111923`，8.7，150 字节即可打崩）也属“边界组件被小输入打穿”的类型。

### 3.1 CVE-2026-111911 — phpMyFAQ WebAuthn 注册端点缺陷致任意账号接管（9.3）

#### 3.1.2 漏洞摘要

phpMyFAQ 4.0.0 至 4.1.9 之前，WebAuthn 注册端点存在认证绕过（`CWE-287`）：该端点**在未要求认证、也未校验 challenge 的情况下，就把提交的凭据附着到任意账号上**。攻击者的利用步骤非常明确——先“占位”一个受害者用户名，然后提交一个伪造的 `fmt=none` 证明（attestation）注册自己的 passkey，随后用该 passkey 登录，**同时绕过口令与 TOTP 双因素**，完成账号接管。CVSS 9.3。WebAuthn 的设计前提是“注册必须发生在已认证会话内，且 challenge 必须由服务端生成并一次性校验”；一旦把注册当作匿名操作、且接受 `fmt=none`（即不要求证明 attestation 来源），攻击者就可以自助式地为自己签发“合法”凭据。这也是 WebAuthn 落地时最常见的两类错误：**注册流程的授权缺失**与**attestation 校验的放松**。该产品的同期条目（改密不需原密码、对象级越权、组控制提权）表明其认证授权模型存在系统性问题。

> 原文摘要（NVD）：phpMyFAQ 4.0.0 before 4.1.9 contains an authentication bypass vulnerability where WebAuthn registration endpoints attach credentials to any account without authentication or challenge validation. Attackers can stage a victim username, submit a forged fmt=none attestation to register a passkey, then log in bypassing passwords and TOTP for account takeover.

#### 3.1.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | phpMyFAQ Web 入口（注册/登录端点） |
| 身份认证 | 无需 | 无需任何凭据即可触发 |
| 用户交互 | 不需要 | 无需受害者交互 |
| 特定配置 | 是 | 需启用 WebAuthn 功能；具体版本 4.0.0–4.1.9 之前 |
| 利用复杂度 | 低 | 低（步骤固定，无需任何凭据） |

**技术原理：**

WebAuthn 注册（`navigator.credentials.create`）分两段：服务端下发 challenge 与用户信息，客户端生成密钥对并回传 attestation。服务端在第二段必须做三件事：确认调用者已认证且就是目标用户、确认 challenge 与本次会话匹配且未被使用、按策略校验 attestation（或明确接受 `none`）。本漏洞缺失了前两项，因此任何人都能为任意用户名登记凭据。登录阶段验签本身是正确的——**问题不在验签，而在“谁有权登记凭据”**。

**核心利用链：**

```text
攻击者
  └─ 定位暴露的 目标组件（目标产品）
      └─ 直接访问受保护接口或伪造身份
          └─ 触发 CWE-287 对应处理逻辑
              └─ 绕过认证获得未授权能力
                  └─ 横向利用或持久化（视环境）
```

#### 3.1.10 修复与缓解措施

**官方修复：**

1. 升级 phpMyFAQ 至 4.1.9 或更高
2. **审计全部已注册 WebAuthn 凭据**，删除无法对应到真实用户的 passkey
3. 强制受影响账号重置口令并重新绑定双因素
4. 检查是否存在异常账号（新注册的管理员、异常邮箱）

**临时缓解：**

- 临时关闭 WebAuthn 登录/注册功能，回退到口令 + TOTP
- 在反向代理层限制注册端点仅允许已登录会话访问
- 对账号变更操作启用邮件/短信告警

#### 3.2.2 漏洞摘要

Tektronix 3 Series MDO 混合域示波器 1.21.1 之前，`FILESystem:MOUNT:DRIve` 这个 SCPI 命令处理器存在 OS 命令注入（`CWE-78`）：**用户提供的输入未被充分中和**，远程攻击者可借此**以提升权限执行任意操作系统命令**，CVSS 8.8。同批披露的 `CVE-2026-111854`（8.1）与 `CVE-2026-111855`（7.5）是 SCPI 文件系统接口的路径遍历，可读取或修改设备上的任意文件。这类漏洞的价值不在 CVSS，而在**资产可见性**：示波器、频谱仪、信号源等测试仪器通常通过以太网接入实验室或产线网段，**有 IP、有 Web 界面、有 SCPI 监听端口，但几乎不进漏洞台账、不做补丁管理**。设备被拿下的后果包括：篡改测试结果（对产线质检是直接的业务风险）、作为实验室网段的跳板、以及在设备上持久化。

> 原文摘要（NVD）：An issue was discovered on Tektronix 3 Series MDO devices before 1.21.1. An OS command injection vulnerability exists in the FILESystem:MOUNT:DRIve SCPI command handler. Insufficient neutralization of user-supplied input allows remote attackers to execute arbitrary operating system commands with elevated privileges.

#### 3.2.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | SCPI 端口（5025/TCP）、Web 或 VXI-11 接口 |
| 身份认证 | 普通用户 | 需相应账号权限 |
| 用户交互 | 不需要 | 无需受害者交互 |
| 特定配置 | 是 | 需设备网络可达；SCPI 接口默认启用 |
| 利用复杂度 | 低 | 低（协议无认证） |

**技术原理：**

SCPI（Standard Commands for Programmable Instruments）是测试仪器的标准命令集，通过 TCP（常见 5025 端口）或 VXI-11 传输，历史上设计为“无认证、纯文本命令”。当厂商在 SCPI 处理器中调用 shell 完成挂载/文件操作时，命令参数若未做转义，`;`、`|`、`$()` 即可注入。路径遍历同源：文件系统命令的路径参数未限制根目录。由于 SCPI 协议本身不带认证，**任何能连到 5025 端口的人都可以尝试**。

**核心利用链：**

```text
攻击者
  └─ 定位暴露的 目标组件（目标产品）
      └─ 构造携带命令/表达式载荷的请求
          └─ 触发 CWE-78 对应处理逻辑
              └─ 以服务进程权限执行任意命令
                  └─ 横向利用或持久化（视环境）
```

## 五、当日处置建议

1. **按组件处置而非按 CVE**：phpMyFAQ 一次升级即可覆盖 7 条缺陷；`Text::CSV_XS` 升级到 1.65 覆盖全部 CSV 解析问题。逐条跟踪会浪费大量工时且容易漏。
2. **WebAuthn 实现审计要点**：注册端点是否要求已认证会话、challenge 是否一次性、是否接受 `fmt=none`。这三条可作为所有自研 WebAuthn 功能的检查清单。
3. **给测试仪器建台账**：把示波器、频谱仪等“有 IP 的仪器”纳入资产系统，记录固件版本与网络位置。本期 Tektronix 的三条漏洞说明这类设备的风险真实存在，且它们通常处在“没人管”的状态。
4. **FreeRDP 与 Fleet 按常规升级**：两者都是“小输入打崩/越界”的类型，影响集中在服务端稳定性与内存安全，按正常补丁周期处理即可。
