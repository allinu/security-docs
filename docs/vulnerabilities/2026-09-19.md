### 1.3 今日重点关注

1. **Linux 内核 3 个被在野利用漏洞（`CVE-2025-39682` / `CVE-2026-53266` / `CVE-2025-39964`，CISA KEV 2026-09-18 新增，期限 2026-09-21）**  
   CISA 依据「存在实际在野利用的证据」将三者纳入 KEV。`CVE-2025-39682`（kTLS 接收路径对零长度记录处理不当，`CWE-754`，kernel.org CNA 评定 **9.8**）可经网络路径触发且影响服务端 TLS 数据流；`CVE-2026-53266`（ebtables SNAT 目标以太网源地址重写未先做可写性保障，`CWE-787` 越界写，**8.8**）可被用于容器/虚拟化网络场景；`CVE-2025-39964`（AF_ALG 套接字并发写竞态，`CWE-362`，**7.8**）属本地权限提升。凡使用内核 kTLS、netfilter/ebtables 或 AF_ALG 的主机与容器宿主机应**在 2026-09-21 前**完成发行版内核更新。

2. **`CVE-2026-91843`：Check Point Security Management / Log Server 未认证登录栈溢出致 root 代码执行**  
   漏洞位于**认证前**的登录处理流程，攻击者仅需在登录请求中构造**超长用户名**即可触发栈溢出，从而在目标管理/日志服务器上以 **root** 权限远程执行任意代码，CVSS 3.1 = **9.8**。利用需目标启用 **Trusted Clients** 设置，且攻击路径为网络可达的管理接口。Check Point 已通过 **LivePatch** 通道发布修复（公告 `sk1000155`），并建议把 Trusted Clients 收敛至已知内部 IP；Censys 观测全球有 **3,836 台**具备 Security Management / Log Server 角色的主机（按厂商默认 SIC 标识统计，属「角色存在数」而非「确认易受攻击数」）。

3. **Docker Sandboxes 沙箱逃逸（`CVE-2026-77179` CVSS 9.4 / `CVE-2026-79994` CVSS 8.7）**  
   二者均需**沙箱内的恶意代码**作为前置条件，而「隔离智能体所运行的东西」正是沙箱的设计目标，因此对使用 AI 编码智能体的团队属直接风险：`CVE-2026-77179` 中宿主机侧 virtio-fs 服务在重开被删除文件时**跟随符号链接**，客机可把父目录替换为符号链接逃出共享工作区，以 **VMM 用户**身份读写宿主机任意文件（可能进一步导致宿主机代码执行）；`CVE-2026-79994` 的客机→宿主机 Unix socket 中继在**校验与连接之间存在竞态**，可让宿主机连接到工作区之外的任意 AF_UNIX 套接字。修复版本 **0.42.0**，无法升级时 Docker 建议改用 **clone 模式**并避免读写宿主机挂载。

### 1.4 综合研判

本期是「**补丁已就绪、风险集中在未落地**」的典型窗口。其一，最紧迫的并非 CVSS 满分的新面孔，而是 **CISA KEV 在 2026-09-18 一次性新增的 3 个 Linux 内核漏洞**：它们不在 RSS 候选条目中，仅能通过 KEV 目录主动核对发现，且**整改期限仅 3 天（2026-09-21）**——这正说明「只看资讯流」会漏掉最具时效性的合规级风险。内核类漏洞的影响面覆盖全部物理机、虚拟机与容器宿主机，且部分发行版（如 Debian 12 基于 9.18 系内核等 EOL 分支）可能迟迟不带修复，需要按发行版单独确认。其二，`CVE-2026-91843` 把风险指向**安全设备自身**：Check Point 管理/日志服务器是防火墙策略、管理员账户与日志留存的「中枢」，一旦被未认证 root RCE 攻陷，攻击者可改写策略、读取日志并清除痕迹，其战略价值远高于单台业务主机；Censys 给出的 3,836 台管理角色主机说明互联网暴露面客观存在，而「需启用 Trusted Clients」这一前置条件在现实配置中相当常见。其三，Docker Sandboxes 的两个逃逸漏洞把「**AI 智能体的隔离边界是否可信**」这个长期争论变成了具体 CVE：客机里运行的正是智能体自己安装的代码，一旦智能体被提示注入或供应链投毒劫持，逃逸即自动发生，因此这类漏洞的**实际触发门槛低于表面上的 `AV:L`**。其四，本期全部重点 CVE 均**无公开可用 PoC、无新增在野利用确认**（KEV 三项除外），给了 24～72 小时的处置窗口，属于「节奏可控但必须动手」的一天。其五，从威胁面看，无 CVE 动态同样值得注意：**RatHat** 用 GenAI 实时解析无障碍树来决定点击位置，绕过了传统脚本化 RAT「界面一变就失效」的弱点，并通过无线调试自配对获得 `ADB shell`、在 `/dev/input` 层做硬件级键盘记录以绕过 `FLAG_SECURE`，卸载后还能自恢复；**智谱 ZCode 静默上传工作区与 Git 历史**则属于典型的数据外流型供应链风险；**Gyazo 2362 万条用户记录与约 4.9 亿条图片元数据泄露**再次印证「用户生成内容处理服务」是高价值泄露面。本地资产侧，本站为公开文档站点，无内核宿主机、Check Point 管理服务器、Docker Sandboxes、DNS 服务器等资产的内部台账可关联，相关字段按规范填「不适用/待核查」。

!!! danger "研判结论：较高风险"
    今日最主要风险点为 **CISA KEV 2026-09-18 新增的 3 个 Linux 内核在野利用漏洞（整改截止 2026-09-21）** 与 **`CVE-2026-91843`（Check Point 管理/日志服务器，CVSS 9.8，未认证即可 root 代码执行）**。要求：**在 2026-09-21 前**完成内核 kTLS / netfilter / AF_ALG 相关主机的发行版内核升级与重启验证；**立即**核查所有对外暴露的 Check Point Security Management / Log Server 是否已应用 LivePatch（`sk1000155`），未启用自动更新的尽快手工应用，并把 Trusted Clients 收敛到已知内部 IP；同时按表末提醒，对 **当日到期**的 `CVE-2026-58704`、`CVE-2026-76460`、`CVE-2026-87886` 完成 KEV 整改闭环留档。

### 3.1 `CVE-2026-91843` — Check Point Security Management / Log Server 未认证栈溢出致 root 代码执行

#### 3.1.2 漏洞摘要

该漏洞存在于 Check Point Security Management Server 与 Security Log Server 的**登录处理流程**中，属于典型的**栈上缓冲区溢出**（`CWE-121`）。Censys 研究人员发现，攻击者只需在登录请求中提交**极长的用户名**，即可在认证完成之前触发溢出；Check Point 公告明确其影响为「未认证攻击者可通过登录流程远程以 root 权限执行任意代码」。

> 需要强调两点评判：其一，漏洞点在**认证之前**，因此常规的账号策略、口令强度与 MFA 完全无法形成阻碍；其二，执行权限为 **root**，意味着攻击者可直接读取/改写安全策略、管理员凭据与历史日志，并具备清理取证痕迹的能力——对以「策略中枢」定位的 Check Point 管理面而言，被攻陷后的横向影响远超单台业务主机。

#### 3.1.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需可达管理服务器的登录接口（SmartConsole 管理通道，默认 18190/TCP 等） |
| 身份认证 | 无需 | 漏洞点在认证完成之前 |
| 用户交互 | 不需要 | 直接构造登录请求即可 |
| 特定配置 | 是 | 需目标启用 **Trusted Clients** 设置（限制经 SmartConsole 访问管理服务器的来源） |
| 利用复杂度 | 低 | 只需超长用户名字段触发栈溢出；构造稳定利用链的难度未知 |

**技术原理：**

登录流程在处理用户名时未对长度做有效边界校验，攻击者提交超长用户名后，数据被写入固定长度的栈缓冲区并覆盖相邻栈帧（如返回地址），从而实现控制流劫持。在管理/日志服务器上，运行该登录服务的进程具备高权限，故成功利用后的命令执行权限为 **root**。

**核心利用链：**

```text
攻击者
  └─ 定位互联网/内网可达的 Check Point 管理服务器登录接口（Trusted Clients 已启用）
      └─ 构造含超长用户名的登录请求
          └─ 触发登录流程中的栈缓冲区溢出（CWE-121）
              └─ 覆盖返回地址并劫持控制流
                  └─ 以 root 权限远程执行任意代码
                      └─ 读取/改写安全策略、获取管理员凭据、清除日志痕迹
```

#### 3.2.2 漏洞摘要

三者均为 Linux 内核已修复（upstream 已合入）但在野已被利用的漏洞：

- **`CVE-2025-39682`（kTLS 接收路径，`CWE-754`）**：内核 TLS 接收路径对 `rx_list` 中**零长度记录**的校验不充分。当从 `rx_list` 取出的记录类型与当前处理状态不一致时，代码本应中断主处理循环，但零长度记录可绕过既定的 `recvmsg()` 记录类型处理逻辑，导致后续 TLS 记录在**错误的零拷贝与排队假设**下被处理，进而造成内存与解析状态异常。该漏洞被评定为可**经网络触发**，属本期评分最高项。
- **`CVE-2026-53266`（ebtables SNAT 目标，`CWE-787` 越界写）**：ebtables 的 SNAT 目标把以太网源地址重写放在 `skb_ensure_writable(skb, 0)` 之后，而 ARP 发送方硬件地址（SHA）重写路径在执行时**未保证目标内存可写**，可能直接写入由 splice 导入的文件页所支撑的非线性 skb 片段，形成**越界写**。该漏洞在容器/虚拟化网络与桥接转发场景中更具现实意义。
- **`CVE-2025-39964`（AF_ALG，`CWE-362` 竞态）**：对同一个 `af_alg` 套接字发起两次并发写会导致数据不可预测地交错，并可能使套接字内部状态不一致。上游通过新增 `ctx->write` 字段实现写独占来禁止并发写。该漏洞属本地攻击者可用于提升权限/破坏内核状态的类型。

> CISA 要求按 **BOD 26-04** 与 **Forensics Triage Requirements** 执行；因其影响的是「开源组件/第三方库」类基础件，几乎所有物理机、虚拟机与容器宿主机都在潜在受影响范围内。

#### 3.2.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 视漏洞而定（`CVE-2025-39682` 为**是**） | kTLS 场景需可达使用内核 TLS 的服务端口；`CVE-2026-53266` 需处于桥接/ebtables SNAT 转发路径 |
| 身份认证 | `CVE-2025-39682` 无需 / `CVE-2026-53266` 与 `CVE-2025-39964` 需本地低权限 | 见 CVSS 向量中的 `PR` 取值 |
| 用户交互 | 不需要 | 无交互依赖 |
| 特定配置 | 是 | 需启用 kTLS、ebtables SNAT、AF_ALG 中的对应功能 |
| 利用复杂度 | 中～高 | 需结合内存布局或竞态窗口，但已有在野利用证据表明可实现 |

**技术原理：**

`CVE-2025-39682`：`recvmsg()` 约定每次调用只处理「连续的 DATA 记录（任意条）」或「一条非 DATA 记录」。当记录类型发生切换时循环应当中断；但**零长度记录**在 TLS 1.3 下类型需解密后才可知，被排队进 `rx_list` 后，下一次 `recvmsg()` 取回时绕过了上述类型处理约定，使后续记录沿用错误的零拷贝与排队假设，破坏 skb 生命周期与解析状态。

`CVE-2026-53266`：`ebt_snat` 在改写以太网源地址时未先确保线性化与可写性，ARP SHA 重写路径可直接落到非线性 skb 片段（可能由 `splice` 导入的文件页支撑），从而越过缓冲区边界写入。

`CVE-2025-39964`：`af_alg_sendmsg` 允许对同一套接字并发写，数据交错并使内部套接字状态不一致；上游以 `ctx->write` 独占标志拒绝并发写。

**核心利用链：**

```text
（CVE-2025-39682，网络侧）
攻击者
  └─ 与使用内核 TLS（kTLS）的服务建立/控制连接
      └─ 构造包含零长度记录的 TLS 记录序列，使记录进入 rx_list
          └─ 触发后续 recvmsg() 的类型处理绕过
              └─ 在错误的零拷贝/排队假设下处理后续记录
                  └─ 内核状态破坏→可致进程/内核内存异常，配合其他原语可实现提权或信息泄露

（CVE-2026-53266，本地/网络侧）
低权限本地上下文
  └─ 触发 ebtables SNAT 对 ARP 源硬件地址的重写路径
      └─ 写入非线性 skb 片段（splice 导入的文件页）
          └─ 越界写（CWE-787）
              └─ 内存破坏→可致提权或崩溃
```

#### 日志与行为排查

重点检查：

- 内核日志（`dmesg`、`journalctl -k`）中的 `BUG`、`Oops`、`general protection fault`、`KASAN` 报告与异常 panic；
- kTLS/TLS 相关服务的异常断连、记录解析错误与内存异常增长；

- 主机安全/EDR 对内核漏洞利用行为（异常 `setsockopt`、`AF_ALG` 套接字批量创建、竞态线程爆发）的告警。

### 3.3 `CVE-2026-77179` — Docker Sandboxes virtio-fs 符号链接逃逸

!!! danger "严重漏洞"
    在 macOS 上运行的 Docker Sandboxes 中，**沙箱内恶意代码**（例如被对抗性提示词劫持的 AI 编码智能体，或其安装的恶意包）可将父目录替换为符号链接逃出共享工作区，以 **VMM 用户**身份读写宿主机任意文件，**可能导致宿主机代码执行**；修复版本 0.42.0。

#### 3.3.2 漏洞摘要

Docker Sandboxes 的设计目标是**让每个 AI 编码智能体运行在自己的一台小虚拟机中**，并把项目目录共享进该虚拟机；会发生逃逸的代码正是「虚拟机内运行的任何东西」——被对抗性提示注入劫持的编码智能体，或该智能体自行安装并运行的恶意包。

逃逸路径位于 **virtio-fs 宿主机侧服务**（Mac 与虚拟机之间文件共享的宿主端）：该服务在**重新打开一个已被删除的文件、且路径来源于此前保存的字符串**时，未能正确避免跟随符号链接。客机（虚拟机内运行的代码）因此可以把某个**父目录替换为符号链接**，从而逃出共享工作区，以 **VMM 用户**（运行虚拟机监视器的宿主机账号）的权限读取或修改宿主机上的任意文件，Docker 原文称「可能导致宿主机代码执行」。

> 值得注意：Docker 文档自 2026 年 3 月起即声明「指向工作区之外的符号链接不会被跟随」，而本漏洞正是这一承诺在**特定重开路径**上的失效。Docker 的隔离文档亦明确「虚拟机管理程序边界才是隔离控制，而不是虚拟机内的权限分离」——换言之，智能体在虚拟机内使用 `sudo`、安装任意包都是预期行为，**宿主机侧的边界失守就等于隔离失效**。

#### 3.3.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 否（本地） | 需在沙箱内执行恶意代码 |
| 身份认证 | 无需（沙箱内代码） | 攻击者是沙箱内运行的任意代码，无需额外凭据 |
| 用户交互 | 不需要 | 一旦智能体被劫持/安装恶意包即自动发生 |
| 特定配置 | 是 | 需使用默认的**读写**工作区共享（`sbx run` 默认把当前目录以读写方式共享进沙箱） |
| 利用复杂度 | 低 | 替换父目录为符号链接即可，无需内存布局技巧 |

**技术原理：**

virtio-fs 宿主机侧服务在「按存储的路径字符串重新打开一个已被 unlink 的文件」时，未做 `O_NOFOLLOW` 等安全打开语义或逐段路径校验，导致路径中间组件中的符号链接被跟随。客机先让某个父目录被删除/替换，再插入指向工作区之外的符号链接，宿主机服务随即将访问解析到工作区之外，并以 **VMM 用户**权限完成读写。

**核心利用链：**

```text
沙箱内恶意代码（被劫持的 AI 编码智能体 / 其安装的恶意包）
  └─ 在共享工作区内制造“被删除文件 + 父目录替换”的时序
      └─ 将父目录替换为指向工作区之外的符号链接
          └─ 触发 virtio-fs 宿主机服务按存储路径重开文件并跟随符号链接（CWE-59）
              └─ 逃出共享工作区，以 VMM 用户身份读写宿主机任意文件
                  └─ 可能进一步实现宿主机代码执行（例如篡改启动项、脚本或配置）
```

#### 3.3.11 风险影响

漏洞成功利用后，可能导致：

- 沙箱隔离失效，客机代码获得宿主机文件读写能力；
- 读取宿主机敏感数据（SSH 私钥、云凭据、`.env`、浏览器数据、源码仓库）；
- 修改宿主机脚本、启动项与配置文件，实现宿主机代码执行与持久化；
- 以开发机为跳板横向渗透内网与代码托管平台；
- 供应链投毒（在源码仓库或构建脚本中植入后门）；
- 数据泄露与合规风险（开发机常持有生产环境凭据）。

#### 临时缓解

无法立即升级时，可采取：

- 改用 **clone 模式**（`--clone`）创建沙箱，并在创建后**删除并重建**已存在的沙箱；

- 不在承载生产凭据的开发机上运行不可信智能体/插件；

### 3.4 `CVE-2026-79994` — Docker Sandboxes 客机→宿主机 Unix socket 中继 TOCTOU

!!! warning "高危漏洞"
    与 `CVE-2026-77179` 同批修复（0.42.0）。Docker Sandboxes 中允许沙箱连接其授权工作区内 Unix 域套接字的**中继组件**存在**检查与使用之间的竞态（TOCTOU）**：客机若在校验与连接之间把路径中的某个中间目录替换为符号链接，即可让**宿主机**连接到工作区之外的任意 `AF_UNIX` 套接字，从而泄露数据或暴露该套接字提供的宿主机侧能力。

#### 3.4.2 漏洞摘要

Docker Sandboxes 提供一个**中继**组件，用于让沙箱连接到其**授权工作区内**的 Unix 域套接字。该中继的实现逻辑是「**先校验套接字路径位于工作区之内，随后再按该路径名发起重连**」，两步之间存在时间窗（TOCTOU）。客机若在这段窗口内把路径中的某个中间目录替换为**符号链接**，即可让宿主机侧握手/连接落到工作区**之外**的任意 `AF_UNIX` 套接字上，从而泄露该套接字所承载的数据，或获得其提供的**宿主机侧能力**。

> Docker 在发布该 CVE 记录时曾把首个修复版本误列为 0.41.0 并链接到不存在的 0.41.0 发布页，**约一小时后更正为 0.42.0**；据此评估受影响范围时应以更正后的 0.42.0 为准。

|---|---|---|---|---|
| Docker | Docker Sandboxes（guest→host Unix socket relay） | `0.37.0` 至 `< 0.42.0`（Docker 未标注平台） | `0.42.0` 或更高（当前最新 0.43.0） | 本地开发终端（AI 编码智能体沙箱） |

#### 3.4.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 否（本地） | 需在沙箱内执行恶意代码 |
| 身份认证 | 无需（沙箱内代码） | 攻击者是沙箱内运行的任意代码 |
| 用户交互 | 不需要 | 沙箱内代码自动完成 |
| 特定配置 | 是 | 需使用沙箱的 Unix 域套接字中继能力（工作区内共享套接字） |
| 利用复杂度 | 中（CVSS 4.0 `AT:P`，需赢得竞态窗口） | 需稳定命中检查与连接之间的时间窗 |

**技术原理：**

中继在第一步对「套接字路径是否位于授权工作区内」做校验，第二步却再次**以路径名**发起连接（而非使用已校验的文件描述符或 `openat`+`O_NOFOLLOW` 等原子化安全接口），形成经典的检查/使用分离。客机控制工作区内的目录结构，可在两步之间用符号链接替换中间目录，把最终连接重定向至工作区之外。

**核心利用链：**

```text
沙箱内恶意代码
  └─ 请求经中继连接工作区内某个 Unix 域套接字
      └─ 中继执行“路径位于工作区内”的校验（通过）
          └─ 在校验与连接之间的窗口内，将路径中的中间目录替换为符号链接
              └─ 中继按路径名重连，落点变为工作区之外的任意 AF_UNIX 套接字（CWE-367）
                  └─ 泄露该套接字数据或滥用其宿主机侧能力
```

#### 3.4.11 风险影响

漏洞成功利用后，可能导致：

- 越权访问宿主机侧的 `AF_UNIX` 套接字（如容器运行时、数据库、代理管理接口）；
- 泄露套接字承载的敏感数据与凭据；
- 滥用套接字提供的宿主机侧能力（配置修改、命令下发等）；
- 沙箱隔离失效，为后续宿主机代码执行或横向移动创造条件；
- 供应链投毒与数据外泄风险（开发机通常持有仓库与生产凭据）。

#### 3.4.13 修复与缓解措施

#### 官方修复

1. 将 Docker Sandboxes 升级至 **0.42.0 或更高**（当前最新 0.43.0），与 `CVE-2026-77179` 同批完成；
2. 升级前记录沙箱与共享配置，注意 clone 模式须在创建沙箱时设定；
3. 在测试环境验证套接字中继相关功能（如智能体访问数据库/容器运行时）；
4. 升级后核验版本号与沙箱配置；
5. 评审工作区内仍需共享的 Unix 域套接字，按最小必要原则收敛；
6. 重新执行版本核查并留存修复证据。

#### 临时缓解

无法立即升级时，可采取：

- 使用 clone 模式并避免读写宿主挂载（Docker 对两个漏洞的统一建议）；
- 收敛沙箱工作区内共享的 `AF_UNIX` 套接字范围，避免共享高权限 socket（尤其是容器运行时 socket）；
- 限制沙箱内智能体的权限与可安装包范围，启用提示注入防护；
- 不在持有生产凭据的开发机上运行不可信智能体或插件；
- 加强开发机对工作区外 socket 访问的审计与告警。

#### 3.5.2 漏洞摘要

Internet Systems Consortium（ISC）在 BIND 9 中披露并修复 **14 个**安全漏洞，涉及**递归解析器**与**权威服务器**的不同攻击面，多数可导致 `named` 崩溃（DoS），部分可造成 CPU/内存耗尽与状态不一致：

- **`CVE-2026-77692`（DoH 未认证崩溃）**：任何提供 DNS-over-HTTPS（DoH）的 BIND 服务器均受影响。**无凭据的发送方仅需一个携带无效 SIG(0) 签名的请求**，并在 `named` 完成签名校验前**关闭连接**，即可致服务进程崩溃。
- **`CVE-2026-76163`**：查询类型为 **TKEY** 时，若 `named.conf` **没有全局 options 块**，可致 `named` 崩溃。
- **`CVE-2026-19667`**：默认配置下的**递归解析器**收到单个精心构造的响应即可崩溃（需攻击者控制上游服务器）。
- **`CVE-2026-19666`**：使用 `dns64` 且启用 `break-dnssec yes` 的解析器可被单个构造响应崩溃。
- **`CVE-2026-80274`**：**验证型解析器**收到同时携带 NSEC 与 NSEC3 证明的**通配符回答**时可被崩溃。
- **`CVE-2026-19662`**：需要特定答案顺序与时间配合才崩溃；**不影响 9.21 分支**（这是 9.21.26 仅修复 13 个的原因）。
- **`CVE-2026-81563`、`CVE-2026-81736`**：通过**缓存的 SVCB/HTTPS 别名记录树**消耗解析器 CPU（`CVE-2026-81736` 被描述为「驱动解析器为组装单个响应而做不成比例的 CPU 工作」）。
- **`CVE-2026-19668`**：可导致 CPU 耗尽。
- **`CVE-2026-75029`**：可导致**内存使用超过配置上限**。
- **`CVE-2026-19033`**：**未认证的 IXFR 传输增量被应用到实时区域**——即使 TSIG 签名从未到达，`named` 也不会回滚到传输前状态（需为多报文 TCP IXFR，见 RFC 8945）；HKCERT 将本批影响概括为「阻断服务、资料篡改及绕过保安限制」。
- 其余条目（`CVE-2026-19941`、`CVE-2026-77119`、`CVE-2026-78301`）同属本批，细节以 ISC KB 各 CVE 页面为准。

> **关键两点**：① ISC 对本批**未提供任何 workaround**，唯一路径是升级；② **9.18 分支（至 9.18.50 为其最终版本）受影响但无修复版本**，ISC 已于 2026 年 6 月终止支持并在 5 月建议 9.18 用户尽快迁移到 9.20——其漏洞矩阵明确「EOL 版本应假定对新 CVE 均易受攻击」。

#### 3.5.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | DoH/TKEY 类漏洞**无需自备 DNS 服务器**，仅需可达相关服务接口 |
| 身份认证 | 无需 | `CVE-2026-77692`、`CVE-2026-76163` 均可由未认证请求触发 |
| 用户交互 | 不需要 | 无需交互 |
| 特定配置 | 是 | 部分条目依赖特定配置：DoH 启用、`dns64` + `break-dnssec yes`、无全局 options 块等 |
| 利用复杂度 | 低～中 | 单请求即可崩溃的条目复杂度低；需攻击者控制上游服务器或命中时序的条目复杂度较高 |

**技术原理：**

本批多数条目属于**异常条件处理不完整**导致的状态机/内存管理错误：解析器在处理来自上游的构造响应时（DNSSEC 证明组合、别名记录树、记录类型切换）未覆盖全部异常分支，触发断言失败或越界访问；`CVE-2026-77692` 则是 DoH 签名校验流程中的**连接关闭时序**问题（发送方在校验完成前断开，导致 `named` 进入不一致状态而崩溃）；`CVE-2026-19033` 属**传输状态回滚缺失**（无 TSIG 签名到达时不回滚至传输前状态，可致增量数据被应用），是「数据篡改」类影响。

**核心利用链：**

```text
攻击者
  └─ 识别可用的 BIND 9 服务面（DoH 端点 / 递归解析器 / 权威服务 IXFR）
      └─ 构造触发请求或上游响应
          ├─ 单请求路径（如无效 SIG(0) + 提前关闭连接）→ named 崩溃（CVE-2026-77692 / CVE-2026-76163）
          ├─ 需控制上游服务器 → 构造响应致默认配置解析器崩溃（CVE-2026-19667 等）
          ├─ 缓存 SVCB/HTTPS 别名记录树 → 解析器 CPU 不成比例消耗（CVE-2026-81563 / CVE-2026-81736）
          └─ 多报文 TCP IXFR 未带 TSIG → 增量被应用到实时区域（CVE-2026-19033）
              └─ 结果：DNS 解析/权威服务中断，或区域数据被篡改
```

#### 3.5.9 检测与排查

#### 资产排查

- [ ] 是否部署 ISC BIND 9（含容器镜像内的 `named`）
- [ ] 当前版本是否处于 9.11.0–9.18.50 / 9.20.0–9.20.27 / 9.21.0–9.21.25 等受影响范围
- [ ] 是否使用 9.18 等 EOL 分支（**无修复版本，需规划迁移至 9.20**）
- [ ] 是否对外提供 DoH（对应 `CVE-2026-77692`）
- [ ] 是否使用 `dns64` + `break-dnssec yes`（对应 `CVE-2026-19666`）
- [ ] `named.conf` 是否存在全局 `options` 块（对应 `CVE-2026-76163`）
- [ ] 是否开放 IXFR 传输（对应 `CVE-2026-19033`）

#### 日志与行为排查

重点检查：

- `named` 异常退出、崩溃重启与 `systemd` 重启计数；
- `named` 日志中的断言失败（`assertion failed`）、`SIGABRT`、内存分配失败与外发失败；
- DoH 端点出现的短连接/半开连接异常模式；
- `named` 进程 CPU 长时间接近饱和（别名记录树 CPU 耗尽）；
- 内存占用超过配置上限（`max-cache-size` 等）的告警；
- 区域数据的非授权变更与 IXFR 传输记录缺失 TSIG 的情况；
- 上游解析响应中携带 NSEC+NSEC3 组合的通配符回答。

| 检测项 | 可疑特征 |
| --- | --- |
| 请求路径 | DoH 端点（`/dns-query` 等）、`TKEY` 类型查询、IXFR 传输请求 |
| 请求方法 | `POST`/`GET`（DoH）、TCP（IXFR） |
| 参数特征 | 无效 SIG(0) 签名并立即断开；类型为 TKEY 的查询；多报文 TCP IXFR 无 TSIG |
| User-Agent | 不适用 |
| 响应状态 | DoH 端点连接被提前关闭；`named` 无响应/服务不可达 |
| 进程行为 | `named` 崩溃重启、CPU / 内存异常占用 |
| 文件行为 | 区域文件/日志出现非授权变更 |
| 网络行为 | 短时间内大量异常查询/响应；上游响应含异常 DNSSEC 证明组合 |

#### 3.5.11 风险影响

漏洞成功利用后，可能导致：

- DNS 解析服务中断，波及依赖域名解析的全部业务；
- 权威 DNS 服务不可用，造成面向互联网的域名无法解析；
- 解析器 CPU / 内存资源被耗尽，影响同主机其他服务；
- 区域数据被非授权增量篡改（`CVE-2026-19033`）；
- 缓解 DNS 安全控制，被用于后续攻击链（如域名劫持、流量重定向）；
- 递归解析器被用作放大器或跳板。

#### 3.5.13 修复与缓解措施

#### 官方修复

1. 将 BIND 9 升级至 **9.20.29**（修复全部 14 个）、**9.21.26**（修复 13 个）或 **9.20.29-S1**（Supported Preview Edition，修复全部 14 个）；
2. **9.11.0–9.18.50 分支无修复版本**，须规划迁移至 9.20 受支持分支；
3. 升级前备份 `named.conf`、区域文件与 DNSSEC 密钥材料；
4. 在测试环境验证解析、区域传输、DNSSEC 验证与 DoH 功能；
5. 升级后核验 `named -v`、服务状态与解析结果；
6. 重新执行漏洞检测并留存修复证据。

#### 临时缓解

ISC 对本批 **14 个漏洞均未提供 workaround**。在无法立即升级时可采取：

- 关闭 DoH 服务面（若业务允许），减少 `CVE-2026-77692` 暴露；
- 限制 DNS 服务（53/TCP、53/UDP、DoH 端口）仅对必要来源开放；
- 为 `named.conf` 补充全局 `options` 块（降低 `CVE-2026-76163` 触发面）；
- 关闭非必需的 `dns64` / `break-dnssec yes` 组合；
- 收敛 IXFR 传输权限并对传输实施 TSIG 强制要求（降低 `CVE-2026-19033` 风险）；
- 限制缓存大小与资源配额，并对 `named` 进程设置 CPU/内存监控与自动重启；
- 加强 `named` 日志集中采集、崩溃告警与可用性拨测。

#### 3.6.2 漏洞摘要

#### 3.6.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是（需用户访问恶意页面） | 典型为**路过式下载/恶意页面**触发渲染栈漏洞 |
| 身份认证 | 无需 | 浏览器进程内触发 |
| 用户交互 | 需要 | 需用户访问构造页面（或打开恶意 PDF / 扩展场景） |
| 特定配置 | 视漏洞而定 | 部分依赖 WebGL / WebGPU(Dawn) / 扩展 / PDF 查看等功能启用 |
| 利用复杂度 | 中～高 | 需配合渲染器沙箱逃逸链才能达成本机代码执行 |

**技术原理：**

多数为**内存安全类缺陷**：`CVE-2026-93374` 与 `CVE-2026-93382`、`CVE-2026-93373` 属释放后使用（对象在仍被引用时被释放，可被重占位），`CVE-2026-93372`、`CVE-2026-93381` 属缓冲区溢出（长度校验缺失导致越界写），`CVE-2026-93377` 属 V8 类型混淆（优化编译器对对象类型判断错误，导致以错误类型解释内存）。逻辑类缺陷包括 `CVE-2026-93379`（ORB 授权判断不当，破坏跨源读取隔离）、`CVE-2026-93384`（Omnibox SSRF）、`CVE-2026-93378`（Storage 授权缺失）、`CVE-2026-93387`（Skia 状态校验不当）与 `CVE-2026-93380`（FileSystem 竞态）。

**核心利用链：**

```text
攻击者
  └─ 托管恶意页面（或投放恶意 PDF / 诱导安装恶意扩展）
      └─ 诱导用户使用未修复 Chrome 访问
          └─ 触发渲染栈内存缺陷（Dawn UAF / WebGL 溢出 / V8 类型混淆 / Skia 状态错误）
              └─ 在渲染器进程中实现任意读写/代码执行
                  └─ 结合独立的渲染器沙箱逃逸漏洞
                      └─ 在宿主系统上实现代码执行与持久化
```

#### 3.6.6 MITRE ATT&CK 映射

| 战术 | 技术编号 | 技术名称 | 关联说明 |
| --- | --- | --- | --- |

#### 3.6.11 风险影响

漏洞成功利用后，可能导致：

- 渲染器进程内代码执行，进而窃取浏览器中的会话、Cookie 与凭据；
- 配合沙箱逃逸漏洞后在终端上执行任意代码；
- 绕过跨源读取保护（ORB）读取他人数据；
- 敏感信息泄露（内存内容、密码、文件内容）；
- 页面仿冒导致用户误操作；
- 浏览器崩溃造成业务中断；
- 被用作水坑攻击与针对性攻击的入口。

#### 3.6.13 修复与缓解措施

#### 官方修复

1. 将 Chrome 升级至 `153.0.8010.52`（Linux）/ `153.0.8010.52.53`（macOS、Windows）或更高版本（通常重启浏览器即完成）；
2. 对使用基于 Chromium 的第三方浏览器的终端，等待并部署其厂商对应安全版本；
3. 通过企业策略（如 `Chrome Browser Cloud Management`、组策略）强制开启自动更新；
4. 核查终端是否因关闭更新服务而长期滞后；
5. 升级后核验版本号（`chrome://version`）并抽查关键终端；
6. 留存版本盘点与升级证据。

#### 临时缓解

无法立即升级时，可采取：

- 通过企业策略**禁用或限制** WebGL / WebGPU 等高风险渲染特性（视业务影响评估）；
- 收紧扩展安装权限，仅允许白名单扩展；
- 保持站点隔离（Site Isolation）与渲染器沙箱开启；
- 强化网络侧对未知域名的拦截与恶意页面检测；
- 对高风险终端（运维、财务、研发）优先升级；
- 加强浏览器异常外联与子进程行为的 EDR 监控。

Zimperium 研究员披露新型 Android 高级木马 **RatHat**，其核心特征在于**用生成式 AI 替代传统脚本化 UI 自动化**：木马把设备**实时的 Accessibility（无障碍）树序列化为 XML** 发送给主流生成式 AI 助手，由 AI 返回目标控件的**屏幕坐标与文本**，木马据此执行合成点击与自动导航（`SCROLL_DOWN` 等）。相较传统 RAT「界面一变即失效」，这种「实时看屏再点」的方式具备更强适应性。攻击链上，木马先获取**无障碍服务**权限，随后静默开启**开发者选项与无线调试**，并在同一无障碍服务的帮助下**直接从屏幕读取 ADB 配对码**完成自配对（无需第二台设备、数据线或用户手动批准），再把两个伪装为 `liblocal-service.so`（Go 编写的 shell 工具，负责持久化、电池设置、隐藏权限变更）与 `libmedia_codec.so`（改造版 FRP 反向代理客户端）的原生二进制写入 `/data/local/tmp`，**打通从互联网远程连接设备 ADB shell 的隧道**。窃密分三路：无障碍键盘记录、浏览器地址栏 URL 抓取，以及**在同一 ADB shell 中运行、直接从 `/dev/input` 读取原始触摸坐标的硬件级键盘记录**（配合覆盖各大品牌的数字键盘布局 JSON，把一次点按还原为一个数字），可绕过 `FLAG_SECURE`、自定义键盘与锁屏保护。木马还会在真实银行/支付应用（含微信、支付宝）之上叠加**仿冒界面**骗取 PIN 与登录凭据，并拦截短信获取 2FA 验证码，最终形成**完整的账户接管**。持久化方面：卸载时会弹出伪造的 Google Play 错误以取消卸载；若强制卸载，运行在应用生命周期之外的 Go 代理会察觉并**静默重装 APK 并重新授予全部权限（含无障碍）**。通信上使用 HTTP 注册 + WebSocket 实时通道，并注册为 C2 客户端接收凭据、短信、文件、应用列表、锁屏数据与日志。

**修复建议：**  
① **严格收紧无障碍权限**——不向无明确使用必要的应用授予 Accessibility 权限（这是整条攻击链的唯一硬性前置条件）；② 审查「已安装应用」与「开发者选项/无线调试」状态，发现无线调试在无用户操作下被开启应立即处置；③ 关闭「安装未知来源应用」，不通过仿冒商店页面、短信或广告链接安装 APK；④ 对金融类应用启用生物识别与设备绑定，避免仅依赖短信 2FA；⑤ 企业 MDM 侧对 Android 设备强制启用 Play Protect、限制未知来源安装、监控无障碍服务开启行为；⑥ 若疑似感染，因存在卸载后自恢复机制，建议**安全模式下清除或恢复出厂设置**，并轮换所有在该设备上登录过的账号凭据与集成令牌。
