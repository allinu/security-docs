### 1.3 今日重点关注

1. **`CVE-2026-85706`：GitLab CE/EE 未认证路径遍历任意文件读取（KEV 截止次日）**  
   影响 GitLab CE/EE 18.7 至 19.1.7、19.2.0–19.2.5、19.3.0–19.3.1，未认证远程攻击者可借 Workhorse 请求体落盘机制与路由归一化差异读取服务器本地任意文件（含 `gitlab.rb`、`database.yml`、密钥与令牌）。当前状态为 **CISA KEV 已收录（修复截止 2026-09-14）、GitHub 已有 ≥4 个公开 PoC、中文社区出现利用链辨析**，建议**立即升级至 19.1.8 / 19.2.6 / 19.3.2 并轮换实例内凭据**。

2. **`CVE-2026-84869`：ConnectWise ScreenConnect 客户端未授权文件传输与提权执行（KEV 截止次日）**  
   影响 ScreenConnect 26.6.5 之前的 Host/Access 客户端组件（**服务端不受影响**）。在特定条件下，攻击者可在无 Host 确认、无授权的情况下通过活动远程会话传输并执行文件，甚至使用提权执行动作。建议升级至 **26.6.5**，无法升级时在 Role 中取消 `TransferFiles` 权限。

3. **`CVE-2026-42016` + `CVE-2026-42018`：JFrog Artifactory 认证/授权缺陷被串联在野利用**  
   Wiz Research 确认 2026-08-15 至 09-08 期间多个攻击者串联两漏洞，把一次未认证请求变成管理员级令牌，随后创建持久管理员账号、部署 Groovy 插件执行任意代码，并投放具备 C2 能力的 Rust 后门；两条 CVE 于 2026-09-11 新入 CISA KEV（截止 2026-09-25）。建议优先处置**互联网可达的自建 Artifactory 实例**，升级至 7.111.21 / 7.117.28 / 7.125.20 / 7.133.29 / 7.146.38 / 7.161.20 或更高版本。

### 1.4 综合研判

本期的结构性特征与前一期不同：**风险重心从"边界设备与制品库"收敛到"研发基础设施的单点失守"**，但驱动因素不是新的 0day，而是**已修复漏洞的存量清点速度跟不上对手的利用速度**。

第一条线是 **GitLab 的"满分漏洞 + 次日截止"**。`CVE-2026-85706` 的破坏力不在于技术复杂度（其利用链完全依赖 GitLab 自身的 Workhorse 请求体落盘设计与 Puma/Grape 路由归一化差异），而在于"未认证 + 可读任意本地文件"这一组合：GitLab 实例的 `gitlab.rb`、`database.yml`、`gitlab-secrets.json`、CI/CD 变量与 Runner 令牌往往落在同一台主机上，一次未认证的文件读取即可能等价于整条 CI/CD 供应链与全部代码仓库的失守。该漏洞 2026-09-10 修复、09-11 入 KEV、**09-14 截止**，留给组织的窗口仅 4 天，且中文技术社区已出现"能否真正回显"的辨析——需要特别说明的是，**回显存在边界**（见 3.1.7），因此以"回显成功与否"作为唯一的失陷判定会低估风险，正确做法是升级 + 凭据轮换 + 日志回溯三件套并行。

第二条线是 **JFrog Artifactory 的"组合拳式在野利用"**。`CVE-2026-42018` 与 `CVE-2026-42016` 单独看分别只是"7.5 分令牌泄露"和"8.1 分越权"，但串联后即可把未认证请求升级为管理员令牌，这正是 Wiz 观测到的最短 5 分钟拿下管理员账号的原因。Wiz 的数据同时指出：`CVE-2026-42016` 披露六周后仍有 **59%** 的组织未修复、`CVE-2026-42018` 四周后仍有 **62%** 未修复——说明"中高危漏洞无人排期"是本次在野利用规模化的直接土壤。

第三条线是 **远程运维与终端管理平面的持续暴露**。ConnectWise ScreenConnect（`CVE-2026-84869`）与 JFrog 同批进入 KEV，且截止日均为 2026-09-14/09-25；ScreenConnect 属于典型的"管理面即攻击面"产品——客户端一旦被滥用，攻击者获得的是**合法的远程控制通道**，其隐蔽性远高于普通 WebShell。

第四条线是 **AI 相关资产成为新的风险面**（本期 RSS 窗口的主体报道方向）：Anthropic 发布 154 页 AI 滥用威胁情报报告、黑鸟整理"AI 被武器化的真实网络行动案例合集"、安全圈报道"数百个 AI Agent 被操纵、26 秒攻破 11 家企业"；同期 NVD 也披露了 vLLM（`CVE-2026-90553`，`trust_remote_code` 被忽略导致模型加载即执行代码）等 AI 基础设施漏洞。AI 组件"默认信任模型仓库"的设计与"模型即代码"的供应链模式，正在把传统 CI/CD 的风险平移到大模型运行平面。

综合判断本期整体风险为 **较高风险**，处置重心为：**GitLab 09-14 前强制升级 + 凭据轮换（P0）→ ConnectWise ScreenConnect 升级/禁 TransferFiles（P0）→ 互联网可达的 JFrog Artifactory 升级与账号审计（P1）→ GitLab EE Duo Chat 凭据面收敛（P1）→ AI/模型运行平面组件（vLLM 等）版本核查（P2）**。

!!! danger "研判结论：较高风险"
    两条已确认在野利用的漏洞（`CVE-2026-85706` GitLab、`CVE-2026-84869` ConnectWise ScreenConnect）**修复截止日均为 2026-09-14（次日）**，且自建 GitLab 与远程运维工具同时失守即可直接暴露源码、凭据与企业内网控制通道；请于 24 小时内完成这两项升级或等效隔离，并对 GitLab 实例内的密钥/令牌、Artifactory 的管理员账号与插件目录执行轮换与回溯审计。

#### 3.1.2 漏洞摘要

该漏洞位于 GitLab CE/EE 的**仓库提交与文件接口**（Repository Commits API / Repository Files API）。GitLab 为处理大体积提交请求，由 Workhorse 先将 HTTP 请求体落盘为临时文件，再把 `file.path`、`file.size`、`Content-Type` 等元数据注入转发给 Rails 的请求中；而 Rails 侧的 `file_params_from_body_upload` 直接采信请求参数中的 `file.path`，未区分该参数究竟来自 Workhorse 注入还是来自攻击者伪造，随后在**任何认证动作之前**执行本地文件读取。

漏洞真正的"门槛"在于 Workhorse 本应改写这类请求——其路由正则匹配的是**转义后**的路径（`EscapedPath()` 加一个不会解码 `%XX` 的 `path.Clean` 副本），而 Puma 会在 Grape 路由前先完成 `%XX` 解码。两者对同一 URL 的理解不一致，于是只需对静态路径段做百分号编码（如 `%63ommits`）、在末尾追加 `/`，或附加 `.json` 后缀，即可让 Workhorse 的正则失配、落入兜底的签名反向代理，从而携带有效 JWT 原样转发到 Rails，`require_gitlab_workhorse!` 检查随之失效。

> 这一"**鉴权在读取之后**"的顺序问题是本漏洞的根因：`post ':id/repository/commits'` 入口只校验"请求是否经 Workhorse 转发"，真正的 `authenticate!` 藏在后续的 `authorize_push_to_branch!` 中，而 `File.open/File.read` 发生在其之前。

#### 3.1.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需可访问 GitLab HTTP/HTTPS 服务端口（默认 80/443） |
| 身份认证 | 无需 | 全程无需账号；利用链在 `authenticate!` 之前完成文件读取 |
| 用户交互 | 不需要 | 纯服务端请求触发 |
| 特定配置 | 是 | 需存在至少一个**可被未认证请求寻址的项目 ID**（公开项目即可；仓库内容非必需） |
| 利用复杂度 | 低 | 攻击者为复杂度的唯一约束是 URL 编码变体的选择，脚本可枚举尝试 |

**技术原理：**

四个环节叠加构成完整利用链：

1. **鉴权在文件读取之后**——入口仅 `require_gitlab_workhorse!`，真正鉴权在其后。
2. **落盘元数据取自请求参数**——`file_params_from_body_upload` 采信攻击者可控的 `file.path` / `file.size`，直接进入 `File.read(file_path)`。
3. **Rack 解析错误回显**——当 `Content-Type: application/x-www-form-urlencoded` 时，文件内容被交给 `Rack::Utils.parse_nested_query` 解析，内容中出现的非法 `%` 序列会触发 `ArgumentError: invalid %-encoding (<组件内容>)`，并经 `bad_request!` **原样回显**进 HTTP 400 响应体。回显"先到先得"：`&` / `=` 为组件边界，解析在第一个非法 `%` 所在组件处中断并回显该组件。
4. **尾部斜杠/编码绕过 Workhorse 改写**——Workhorse 的 body-upload 拦截严格匹配 `.../repository/commits\z`；请求 URL 末尾追加 `/`（或对静态段做百分号编码、附加 `.json`）即不匹配该规则，请求体连同伪造参数原样转发 Rails，且携带 Workhorse 生成的有效 JWT。

**核心利用链：**

```text
攻击者（未认证）
  └─ 探测 GitLab 版本 / 确认存在可寻址项目 ID
      └─ 构造 URL：对 repository/commits 的静态段百分号编码，或追加 /
          └─ 绕过 Workhorse 正则与 body-upload 拦截（落入签名反向代理，带有效 JWT）
              └─ Rails 端点通过 require_gitlab_workhorse! 校验
                  └─ file.path 伪造成绝对路径（如 /etc/gitlab/gitlab.rb）
                      └─ File.read 在 authenticate! 之前执行（以 git 用户身份）
                          └─ 内容经 Rack 解析错误回显进 400 响应体
                              └─ 获得配置、密钥、数据库口令、CI/CD 令牌
```

#### 3.1.11 风险影响

- 未经授权读取 GitLab 主机上的任意可读文件（以 `git` 用户权限）；

1. 将 GitLab CE/EE 升级至 `19.1.8` / `19.2.6` / `19.3.2` 或对应分支更高版本（2026-09-10 发布）；
2. Omnibus 部署：`apt-get update && apt-get install gitlab-ce=<版本>`；Helm 部署同步升级 Chart 内镜像标签；
3. 升级前完成配置、程序和业务数据备份（`gitlab-backup create` 与 `gitlab.rb`、`gitlab-secrets.json` 单独备份）；
4. 在测试环境验证兼容性及回退方案；
5. 升级后核验版本与组件状态（`gitlab-ctl status`、`/help` 页面版本号）；
6. **升级后必须轮换凭据**：数据库口令、`gitlab-secrets.json` 相关密钥、CI/CD 变量、Personal/Project Access Token、Runner 注册令牌、Deploy Key 与 Webhook 密钥；
7. 重新执行漏洞检测并留存修复证据。

#### 临时缓解

无法立即升级时，可采取：

- 通过防火墙、ACL、安全组**限制 GitLab 的互联网可达性**（仅允许办公出口/堡垒机/VPN 访问），这是本漏洞最有效的缓解手段；
- 在 WAF 或前置 nginx 中拦截 URI 尾部斜杠与编码变形的 `repository/commits` / `repository/files` 请求（例如拒绝匹配 `repository/(%63ommits|commits|%66iles|files)` 且以 `/` 或 `.json` 结尾的 `/api/v4/projects/*` 请求）；
- 关闭或限制公开项目的匿名可见性，减少未认证攻击者可寻址的项目面；
- 启用身份认证、多因素认证与最小权限控制；
- 加强日志审计、主机监控与异常外联检测；
- 对高风险实例实施网络隔离或访问收敛。

!!! warning "缓解措施不是修复"
    WAF/nginx 层拦截依赖攻击者未使用新的绕过变体，属于降低概率而非消除风险；KEV 截止为 2026-09-14，请以升级为唯一销项标准。

### 3.2 `CVE-2026-87719` — GitLab EE GraphQL 订阅序列化器不安全反序列化致实例配置与凭据泄露

!!! danger "严重漏洞（CVSS 3.1 = 9.9，同一关键补丁批次）"

#### 3.2.2 漏洞摘要

该漏洞位于 GitLab EE 的 **GraphQL 订阅序列化器**。在特定条件下，拥有 Duo Chat 访问权限的已认证用户可构造特制的 GraphQL 订阅参数，**绕过序列化限制并触发服务端对象查找（server object lookup）**，从而获取 Advanced Search（Elasticsearch/OpenSearch 集成）的实例配置以及配置中包含的敏感凭据。

与其他 GitLab 同级漏洞相比，该缺陷的特殊之处在于**利用门槛极低但不要求高权限**：攻击者只需一个能使用 Duo Chat 的普通账号；而其产出物是"检索后端配置 + 凭据"，可直接用于进一步读取实例内被索引的全部代码与议题内容，属于典型的"从低权限到数据面全量读取"的越权路径。

> 该 CVE 与 `CVE-2026-85706` 由同一关键补丁批次（19.1.8 / 19.2.6 / 19.3.2）修复，**但两者根因与利用前置条件不同**：前者是未认证路径遍历，后者是需要账号的不安全反序列化。组织在销项时不应因为"已经为 85706 升级过"而忽略对 EE 版 Duo Chat 权限面的复核。

#### 3.2.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 可访问 GitLab EE 的 GraphQL（`/api/graphql`）接口 |
| 身份认证 | 普通用户 | 需要一个具备 Duo Chat 访问权限的已认证账号 |
| 用户交互 | 不需要 | 服务端 GraphQL 请求直接触发 |
| 特定配置 | 是 | 需启用 Duo Chat 及 Advanced Search（EE 特性） |
| 利用复杂度 | 中 | 需构造特定 GraphQL 订阅参数，PoC 未公开，但攻击面（任何 Duo Chat 用户）较宽 |

**技术原理：**

GraphQL 订阅通道需要将客户端提供的参数序列化后在服务端还原。GitLab EE 在该序列化器中对**攻击者可控数据的类型与目标类**限制不足，使得特制参数可绕过序列化约束，在服务端触发任意对象查找，从而把本不应暴露的实例级配置对象（Advanced Search 配置及其中的凭据）纳入了查询结果。

**核心利用链：**

```text
攻击者（已认证普通用户，具备 Duo Chat 权限）
  └─ 向 /api/graphql 提交特制 Subscription 参数
      └─ 绕过 GraphQL 订阅序列化器的类型/目标限制
          └─ 触发服务端对象查找（server object lookup）
              └─ 读取 Advanced Search 实例配置对象
                  └─ 获得配置中的敏感凭据（Elasticsearch/OpenSearch 等）
                      └─ 进一步读取被索引的代码、议题与敏感内容
```

#### 3.2.11 风险影响

漏洞成功利用后，可能导致：

- 泄露 GitLab Advanced Search 实例配置及其中保存的检索后端凭据；
- 借检索后端权限读取被索引的代码、议题、合并请求与 Wiki 内容（覆盖多个项目）；
- 结合实例内的其他配置信息进一步扩展访问范围；
- 低权限账号（如外部协作者）成为数据面全量读取的入口。

### 3.3 `CVE-2026-84869` — ConnectWise ScreenConnect 客户端未授权文件传输与执行

!!! danger "严重漏洞（CVSS 3.1 = 9.9，CISA KEV 修复截止 2026-09-14）"

#### 3.3.2 漏洞摘要

该漏洞存在于 **ScreenConnect 客户端**（Host 客户端与 Access Agent）的**客户端侧文件传输处理逻辑**中。较早版本的 ScreenConnect Client 在 Support / Access 会话中，对文件传输动作缺少充分的授权校验与 Host 确认环节；在特定条件下，文件传输动作可经由一个活动远程会话被处理，从而把文件传输到 Host 客户端系统并执行，甚至可利用"提权执行"（elevated execution）动作在更高权限上下文中落地。

**关键边界：ScreenConnect 服务端不受影响**——这意味着漏洞利用依赖于"已有会话的客户端侧信任关系"，因此攻击者需要先获得一个可用的会话通道（例如通过被盗的会话凭据、被污染的 Host 客户端，或被诱导加入的伪造安装）。这正是该漏洞与常规"服务端认证绕过"的区别：它不是"未认证直接打穿服务端"，而是"客户端对会话内指令的授权判断可被绕过"，其后果是**攻击者获得一条合法的远程控制通道**，隐蔽性高。

> ConnectWise 公告同时指向社区调查（Huntress 关于"异常/伪造 ScreenConnect 安装"的分析），提示本漏洞的现实滥用场景与远程管理软件的"合法工具滥用（LOTL）"趋势高度一致。

#### 3.3.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 否（针对服务端） | 服务端不受影响；利用发生在**已建立的活动远程会话**内 |
| 身份认证 | 需会话（低权限即可） | CVSS 向量为 `PR:L`，需可获得/维持一个活动会话（如被盗凭据、被诱导的会话） |
| 用户交互 | 不需要 Host 确认 | 核心问题即"缺少 Host 确认"，因此 Host 端用户不会被提示 |
| 特定配置 | 是 | 角色（Role）被授予 `TransferFiles` 权限时暴露面最大 |
| 利用复杂度 | 中 | 需先具备会话通道，但一旦具备则利用链短、无需 Host 交互 |

**技术原理：**

ScreenConnect 的会话权限模型由服务端下发的角色权限（Role）与客户端侧的本地判断共同约束。该缺陷出在**客户端侧**：在 Support / Access 会话中，客户端对"文件传输"这类高影响动作的**授权校验与 Host 确认环节可被绕过**，直接按会话指令处理文件传输，并支持"提权执行"动作。由于服务端未受影响，漏洞的成因不是服务端鉴权缺失，而是**客户端把"会话已建立"错误地等价于"该会话内的动作已被授权"**。

**核心利用链：**

```text
攻击者（获得/维持一个活动 ScreenConnect 会话）
  └─ 在会话中发起文件传输动作
      └─ 客户端侧未要求额外授权、未向 Host 请求确认（缺陷点）
          └─ 文件被传输到 Host 客户端系统
              └─ 使用"提权执行"动作运行文件
                  └─ 在 Host 系统上以更高权限获取代码执行
                      └─ 借合法远程管理通道维持访问（隐蔽性高）
```

#### 3.3.11 风险影响

    - **P1：24小时内处置**，PoC公开且利用门槛较低；
    - **P2：3个工作日内处置**，利用条件受限或暂无成熟PoC；
    - **P3：常规整改**，风险较低或仅影响非关键场景。

#### 3.3.13 修复与缓解措施

#### 官方修复

1. 将 ScreenConnect（**Host 客户端与 Access Agent**）升级至 `26.6.5` 或更高版本；
2. On-Premise 部署升级服务器组件至 26.6.5；Automate 集成部署通过 Automate Product Updates 应用更新（需 Automate Assurance 订阅有效）；
3. 若许可证已超出维护期，需先续期或升级许可证后再安装受支持版本；
4. 云托管服务端无需操作，但**仍须自行升级客户端与 Access Agent**；
5. 升级前完成配置与业务数据备份，并在测试环境验证兼容性及回退方案；
6. 升级后核验客户端版本并重新执行权限配置核查。

#### 临时缓解

无法立即升级时，可采取：

- 逐角色取消 `TransferFiles` 权限（Administration > Security > Roles → 编辑角色 → 对每个会话组取消勾选 `TransferFiles` → 保存；对所有角色重复）；
- 限制 ScreenConnect 服务端的互联网可达性，仅允许受控出口/堡垒机访问；
- 启用多因素认证、收紧会话批准策略（要求 Host 显式确认）；
- 排查并清理异常/伪造的 ScreenConnect 安装（参考 Huntress 分析）；
- 加强终端 EDR 监控，重点覆盖"远程管理进程派生命令解释器 + 提权执行"的组合行为；
- 对高风险终端实施网络隔离或访问收敛。

!!! warning "临时缓解的局限"
    厂商明确说明 `TransferFiles` 权限收敛**不能替代安装安全更新**，仅用于无法立即升级时降低暴露面。

### 3.4 `CVE-2026-42016` / `CVE-2026-42018` — JFrog Artifactory 认证与授权缺陷被串联在野利用

!!! danger "高危组合漏洞（CVSS 8.1 / 7.5，Wiz 确认在野利用，CISA KEV 修复截止 2026-09-25）"
    两个单独看仅属"中高危"的缺陷被攻击者串联后，可把一次**未认证**请求在 5 分钟内升级为**管理员作用域令牌**：`CVE-2026-42018` 负责向未认证调用方返回内部匿名用户 JWT，`CVE-2026-42016` 负责把该低权限令牌的 scope 提升为管理员；随后攻击者创建持久管理员账号、部署 Groovy 插件执行任意代码并投放 Rust 后门。

#### 3.4.2 漏洞摘要

**`CVE-2026-42018`（CWE-287）**：Artifactory 在**匿名访问已被禁用**的情况下，仍可能向未认证调用方返回**内部匿名用户令牌**。该内部身份本身权限有限，但其令牌可用于访问内部匿名身份可触及的资源，从而暴露本不应被未认证方接触的制品与仓库数据。

**`CVE-2026-42016`（CWE-863）**：Artifactory 在令牌校验中**只验证签名与签发者，不校验令牌的 scope**。因此持有任一有效令牌的低权限者，可凭该令牌执行超出其授权范围的操作，实现权限提升。

**组合效果（本期核心）**：两者单独都不足以获得管理员权限，但先由 `CVE-2026-42018` 拿到匿名 JWT，再用 `CVE-2026-42016` 把该 JWT 换成**管理员作用域令牌**，即完成"未认证 → 管理员"的两步跨越。Wiz 观测到的典型请求序列为：

```text
POST /access/api/v1/aws/token/    → 200，返回内部匿名用户 JWT（CVE-2026-42018）
POST /access/api/v1/tokens        → 200，返回匿名身份但具管理员作用域的令牌（CVE-2026-42016）
PUT  /api/security/users/<用户名>  → 201，创建持久管理员账号（post-exploitation）
```

值得注意的是，提升后的令牌**用户名仍显示为 `anonymous`**，因此后续请求在审计日志中表现为 `token:anonymous` 执行管理员操作——这是本组合漏洞最具辨识度的特征。Wiz 数据还显示：`CVE-2026-42016` 披露六周后仍有 **59%** 的组织未修复、`CVE-2026-42018` 四周后仍有 **62%** 未修复，修复滞缓是本次在野利用规模化的直接原因。

> 关联项 `CVE-2026-82329`（未认证获取管理员权限，CVSS 9.8，CISA KEV 2026-09-02 收录）已于第 43 期详录；Wiz 同期观测到其在 2026-09-01 至 09-08 被多个攻击者利用（入口为 `POST /access/api/v1/registry/join`），本期仅作状态引用，不重复展开。

#### 3.4.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需可访问 Artifactory 的 `/access/*` 与 `/artifactory/api/*` 接口 |
| 身份认证 | 第一跳无需；第二跳需持有该匿名令牌 | `CVE-2026-42018` 未认证可达（`PR:N`），`CVE-2026-42016` 需持有有效令牌（`PR:L`） |
| 用户交互 | 不需要 | 纯 API 请求链 |
| 特定配置 | 是 | 默认配置下即可利用（`CVE-2026-82329` 描述明确"under default configuration"；42018 在"禁用匿名访问"场景下仍泄露令牌） |
| 利用复杂度 | 低 | 两条 API 请求即可完成提权，攻击者最快 5 分钟创建管理员账号 |

**技术原理：**

- **`CVE-2026-42018`**：Artifactory 的匿名令牌生成/返回逻辑存在路径分支，在特定变体路径（如带尾部斜杠的 `POST /access/api/v1/aws/token/`）下会向**未认证**请求方返回内部匿名用户 JWT，即便管理员已关闭匿名访问。该令牌本身只具匿名身份，但已足以满足 `CVE-2026-42016` 的"持有有效令牌"前置条件。
- **`CVE-2026-42016`**：令牌校验流程**验证签名与签发者，却未验证 scope**。因此匿名身份的令牌在换取新令牌（`POST /access/api/v1/tokens`）时，可被签发为带 `admin` scope 的令牌；由于用户名仍取自原令牌，日志呈现为 `token:anonymous` 却具管理员权限。

**核心利用链：**

```text
攻击者（未认证，网络可达 Artifactory）
  └─ POST /access/api/v1/aws/token/  （尾部斜杠变体）
      └─ 200：获得内部匿名用户 JWT                     ← CVE-2026-42018
          └─ POST /access/api/v1/tokens（携带该 JWT）
              └─ 200：获得 anonymous 用户名 + admin scope 令牌  ← CVE-2026-42016
                  └─ PUT /api/security/users/<用户>（创建持久管理员账号，customData.artifactory_admin=true）
                      ├─ 部署恶意 Groovy 插件 → GET/POST /api/plugins/execute/<plugin> 执行任意命令
                      ├─ 丢弃器下载二进制 → /dev/shm、/tmp、/var/tmp → 建立 C2（Rust 后门）
                      ├─ GET /api/system/configuration 导出实例配置
                      ├─ 枚举仓库/用户/令牌，窃取集群 join key
                      └─ 上传 WebShell 至仓库路径维持访问
```

重点检查：

- Artifactory `access` 与 `request` 日志中 `/access/api/v1/aws/token/`、`/access/api/v1/tokens`、`/access/api/v1/registry/join` 的请求序列；
- `actor` 为 `token:anonymous` 却执行管理员级操作（创建用户、读写插件、导出配置、枚举令牌）的记录；
- `/api/plugins/execute/<plugin>` 的执行调用与新安装的插件文件；
- `/dev/shm`、`/tmp`、`/var/tmp` 下的新落地二进制与外部下载行为；
- 主机侧：Artifactory 进程派生的 `sh`/`bash`/`curl`/`wget` 进程；
- 异常 DNS 解析、外联 IP、C2 反向连接与数据外传；
- 仓库路径中的可疑脚本文件（WebShell 型落点）。

| 检测项 | 可疑特征 |
| --- | --- |
| 请求路径 | `/access/api/v1/aws/token/`（含尾部斜杠）、`/access/api/v1/tokens`、`/access/api/v1/registry/join`、`/api/plugins/execute/*` |
| 请求方法 | `POST`（提权链）、`PUT`（创建管理员账号）、`GET`（配置/用户/令牌枚举） |
| 参数特征 | 匿名或低权限身份提交 token 签发请求，且返回体携带管理员 scope |
| User-Agent | 未发现固定特征（利用脚本可自定义） |
| 响应状态 | 同一客户端对同一路径的 `401 → 200` 变体探测序列；`PUT /api/security/users/<用户名>` 返回 201 |
| 进程行为 | Artifactory 派生命令解释器或下载工具 |
| 文件行为 | 新 Groovy 插件文件、`/dev/shm` 或 `/tmp` 下新二进制、仓库内新脚本 |
| 网络行为 | 异常 DNS、恶意 C2 外联、长时间反向连接 |

#### 3.4.11 风险影响

漏洞成功利用后，可能导致：

- 未认证攻击者获得 Artifactory **管理员权限**，完全控制制品库及其管理的凭据与集成；
- 篡改或替换依赖制品，形成**软件供应链投毒**（影响所有从该制品库拉取依赖的构建与生产环境）；
- 通过 Groovy 插件框架执行任意代码，并在服务器上落地 Rust 后门建立持久化；
- 窃取集群 join key、实例配置、用户与令牌清单；
- 横向移动至与 Artifactory 集成的 CI/CD、K8s 与云环境；
- 中断业务服务或破坏制品可用性。

#### 3.4.12 处置优先级

| 研判维度 | 状态 |
| --- | --- |
| 互联网暴露 | 是（Wiz 建议优先处置互联网可达实例；本次未做测绘统计） |
| 无需认证利用 | 是（组合链的第一跳为未认证） |
| 利用复杂度低 | 是（两条 API 请求即可提权，最快 5 分钟） |
| 已公开PoC | 否（但利用手法已由 Wiz 公开，门槛大幅降低） |
| 已确认在野利用 | 是（Wiz 确认，多攻击者、多环境） |
| 已纳入CISA KEV | 是（截止 2026-09-25） |
| 影响核心业务 | 是（制品库为研发与交付中枢） |
| 涉及敏感数据 | 是（凭据、令牌、制品与企业集成密钥） |

!!! danger "综合处置优先级：P1（互联网暴露实例建议按 P0 处理）"
    - **P0：紧急处置**，已在野利用或可直接影响核心互联网资产；
    - **P1：24小时内处置**，PoC公开且利用门槛较低；
    - **P2：3个工作日内处置**，利用条件受限或暂无成熟PoC；
    - **P3：常规整改**，风险较低或仅影响非关键场景。

#### 3.4.13 修复与缓解措施

#### 官方修复

1. 将自建 Artifactory 升级至对应分支的修复版本：`7.111.21` / `7.117.28` / `7.125.20` / `7.133.29` / `7.146.38` / `7.161.20` 或更高；
2. 升级前完成配置、制品库元数据与业务数据备份（含数据库与应用目录）；
3. 在测试环境验证兼容性及回退方案（尤其是插件、集成与权限模型）；
4. **升级后必须轮换凭据**：所有用户令牌、管理员账号口令、集群 join key、与 CI/CD 及云平台的集成密钥；
5. 审计并删除非预期账号（对照 3.4.10 的账号命名模式）与未知 Groovy 插件；
6. 重新执行漏洞检测并留存修复证据。

#### 临时缓解

无法立即升级时，可采取：

- **优先切断互联网可达性**：通过防火墙、ACL、安全组将 Artifactory 收敛至可信网络/VPN 内；
- 启用匿名访问并配合最小权限，或确保匿名关闭的同时在反代层拒绝 `/access/api/v1/aws/token/` 等变体路径；
- 在 WAF/网关增加对 `POST /access/api/v1/aws/token/`（尾部斜杠）、`POST /access/api/v1/registry/join`、`/api/plugins/execute/*` 的针对性拦截；
- 收紧插件目录权限并对插件安装实施审批；
- 启用多因素认证与最小权限控制，清理默认账号与默认令牌；
- 加强日志审计、主机监控与异常外联检测（重点覆盖 `token:anonymous` 的管理员行为）；
- 对高风险实例实施网络隔离或访问收敛。

### `CVE-2026-78006` / `CVE-2026-78159` — WordPress 插件 The Events Calendar 未认证 PHP 对象注入致远程代码执行

| PoC状态 | 未发现公开 POC（GitHub 搜索 0 命中；厂商已发布 GHSA-3c86-2m5g-59q7） |
| 在野利用 | 未发现 |
| 修复版本 | vLLM 0.28.0 及更高版本 |

**漏洞描述：**  
vLLM 在 `LlavaOnevision2` 处理器加载路径中**忽略了 `trust_remote_code` 参数**，即使管理员显式将其设为 `False`，加载远程处理器类时仍会执行模型仓库中 `processing_llava_onevision2.py` 内的任意代码，且以 vLLM 进程权限运行。该漏洞把"加载模型"等同于"执行代码"，典型地体现了 AI 供应链的信任边界问题：攻击者只需诱导目标拉取一个恶意模型仓库即可达成代码执行。

**修复建议：**  
升级至 0.28.0 或更高版本；过渡期仅在隔离环境加载来源可信的模型，对模型仓库启用哈希固定与来源白名单，限制推理进程的出网与文件写权限。

### `CVE-2026-90616` — Flatpak 缺失符号链接保护致沙箱逃逸与宿主机代码执行

| 字段 | 内容 |
| --- | --- |
| 风险等级 | 高危 |
| CVSS评分 | 7.4 |
| CWE编号 | `CWE-61` |
| 影响产品 | Flatpak（Linux 桌面沙箱运行时） |
| 影响版本 | < 1.18.1 |
| PoC状态 | 未发现公开 POC（GitHub 搜索 0 命中；厂商已发布 GHSA-8688-9x26-hhxj） |
| 在野利用 | 未发现 |
| 修复版本 | Flatpak 1.18.1 及更高版本 |

**漏洞描述：**  
Flatpak 在每次启动应用时会在沙箱内创建 `/var/cache`、`/var/data`、`/var/config`、`/var/tmp` 等应用数据目录，其中部分路径组件由攻击者控制。由于**缺少符号链接保护**，恶意沙箱应用可通过符号链接把上述目录重定向到宿主机任意位置；Flatpak 随后以 `bwrap --bind SRC DST` 的方式挂载这些路径，内核会跟随符号链接，最终使宿主机任意目录被挂载进沙箱，形成任意读写乃至宿主机代码执行。该漏洞与 `CVE-2026-76925` 是不同的问题，厂商公告给出了明确区分。

**修复建议：**  
升级至 Flatpak 1.18.1 或更高版本；过渡期避免在含敏感数据的桌面终端上安装来源不可信的应用，并限制沙箱应用的自动启动。
