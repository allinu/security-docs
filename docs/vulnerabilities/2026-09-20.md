1. **`CVE-2026-93741` + `CVE-2026-93742`：TOTOLINK A3002MU 路由器两个未认证远程漏洞（CVSS 10.0 / 9.9，公开 PoC）**  
   `CVE-2026-93741` 为 `/boafrm/formWlWds` 的 `submit-url` 参数栈缓冲区溢出（VulDB CNA 评定 **10.0**，`CWE-119`/`CWE-120`），`CVE-2026-93742` 为 `/boafrm/formWsc` 的 `localPin` 参数命令注入（**9.9**，`CWE-74`/`CWE-77`）；两者均**无需认证**、可远程触发，公开分析文档与可直接复现的 HTTP 验证请求已随漏洞披露一并公开（`rce-formWsc` 的验证请求可在设备上拉起 telnetd 服务，即公开 PoC 已能直接取得命令执行）。固件版本 `Hh-B20211125.1046`，**厂商目前未发布修复固件**，属「暴露面大、无补丁、有现成利用代码」的典型组合，家庭与小型办公网络中的 A3002MU 应优先收敛管理面。

### 1.4 综合研判

本期是典型的「**周六信源稀疏 + 存量漏洞批量曝光**」窗口，风险结构有三条主线。

第一条线是**已公开 PoC 却无补丁的边缘/IoT 设备**。`CVE-2026-93741`（10.0）与 `CVE-2026-93742`（9.9）同属 TOTOLINK A3002MU，一个是不检查长度的缓冲区溢出（已确认可致 Boa 进程崩溃、存在进一步代码执行的潜力），一个是把 `localPin` 直接拼进 shell 命令串的命令注入（公开验证请求可直接在设备上开启 telnetd 并免认证登录）。这类漏洞的处置难点**不在技术而在治理**：厂商不提供固件，设备又多处于「无人管理、长期在线、管理面暴露」的状态，PoC 一旦公开，收敛为「要么下架/替换、要么在前置设备上做访问控制」的二选一。对任何仍在使用该型号的组织，本期应把「设备清点」当成第一动作。

第二条线是**供应链与托管服务的「边缘层失守」**。Brevo 事件的核心启示不是某个漏洞有多严重，而是**攻击者把恶意代码放在了不产生文件变更的那一层**：长期有效的 Cloudflare API Key 硬编码在应用源码中、Worker 在 CDN 边缘改写响应、CSP 等安全头被顺手剥离，于是「源站干净、哈希一致、完整性检查通过」成为安全假象。对使用第三方营销/客服/统计脚本的组织而言，第三方域的强制 CSP 白名单收敛、Subresource Integrity、以及对 `cdn.*` 类脚本变更的独立监控，是本期最值得立即落地的三条措施。同时，**同一天披露的还有 Discourse/libheif 链**：修复未分配 CVE、未被发行版回溯，是「没有 CVE 不等于没有漏洞」的教科书案例；而 AI 把「把一个内存破坏漏洞变成可用利用代码」的周期压缩到数小时，直接改变了这类漏洞的**风险时间常数**——防御侧对「上游已修但发行版未回溯」的库版本核查，必须从「季度」提速到「周」。

第三条线是**大规模 Web 组件未认证漏洞的持续输出**。NVD 于 2026-09-19 单日发布 94 条 CVE，其中 WordPress 生态占绝大多数，本期从中筛出 7 条严重级未认证漏洞（`CVE-2026-86591` 任意选项更新致站点接管、`CVE-2026-84434` 任意文件上传、`CVE-2026-92229`/`89274` 任意短代码执行等）与 8 条高危 Stored XSS / 权限类漏洞。这类漏洞单项 CVSS 高但利用门槛极低，**典型的失守方式不是被定向攻击，而是被批量扫描**；对同时运行多个 WordPress 站点的组织，「插件版本盘点 + 自动更新策略 + 高危插件的功能降权」比逐个应急更有效。综合来看，本期无 CISA KEV 新增、无 CVE 型在野利用确认，RSS 信源亦无新增 CVE，整体不属于「必须今夜处置」的态势；但 TOTOLINK 批次（有 PoC、无补丁）与 Brevo 遗留凭据清理要求**在 24 小时内启动**，且 **2026-09-21 到期的 3 条 Linux 内核 KEV 整改**已进入最后窗口（另 3 条 2026-09-19 已逾期）。本站为在线公开文档站点，无路由器、云营销平台账号、Discourse 论坛、OpenPanel 实例等资产的内部台账可关联，3.15 与第六章相关字段按规范填「不适用/待核查」。

#### 3.1.2 漏洞摘要

两个漏洞位于 TOTOLINK A3002MU AC1200 Gigabit 无线路由器的 `/bin/boa` Web 服务中，对应两个不同的表单处理函数。

`CVE-2026-93741`：`formWlWds`（无线 WDS 桥接配置）在处理 `submit-url` 参数时，**未校验输入长度**即将其拷入固定大小的栈缓冲区，缺少可靠的边界约束。远程攻击者通过一个携带超长 `submit-url` 值的 `POST /boafrm/formWlWds` 请求即可覆写相邻内存，实测导致 Boa 进程崩溃、管理界面失去响应（拒绝服务）；由于溢出发生在栈上，进一步构造可实现任意代码执行的潜力。

`CVE-2026-93742`：`formWsc`（WPS 配置）在读取 `localPin` 参数后，**未经校验、转义或过滤**便将其拼接进命令字符串并交由系统 shell 执行。攻击者只要在 `localPin` 中插入 shell 元字符即可改变命令流程，实现设备上的任意命令执行；公开验证请求已证明可在设备上拉起 `telnetd` 并开放免认证登录端口。

> 两个漏洞的共同根因是**嵌入式固件长期存在的输入信任问题**：Web 表单参数直接进入固定长度缓冲区与 shell 命令串，既无长度校验也无特殊字符中和，且设备既无自动更新机制、又常以默认配置长期在线。

#### 3.1.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需能访问设备 Boa Web 服务的 `80/TCP`（或映射后的管理端口）及 `/boafrm/` 接口；LAN 侧可达即成立，若管理面被映射到 WAN 则互联网可达 |
| 身份认证 | 待确认 | 公开验证请求的请求体仅携带 `sessionCheck` 参数、未展示登录取值步骤；该参数在不同固件中的校验强度需以实机为准。**本报告未执行任何验证请求**，不排除部分固件要求有效会话 |
| 用户交互 | 不需要 | 纯服务端 POST 请求触发，无需管理员点击 |
| 特定配置 | 是 | 需 WDS（`formWlWds`）或 WPS（`formWsc`）相关页面/接口在固件中启用且可达 |
| 利用复杂度 | 低 | 单个 `POST` 请求即可；`CVE-2026-93742` 的注入参数可直接携带 shell 元字符，公开 PoC 已证明可拉起 `telnetd` |

**技术原理：**

1. **`CVE-2026-93741`（栈溢出）**：`formWlWds` 从请求中取出 `submit-url`，随后用不安全的字符串拷贝逻辑写入固定长度栈缓冲区；拷贝路径未施加可靠的长度边界，超长取值可覆写相邻栈内存。公开分析以 IDA Pro 反汇编为依据，实测在发送构造请求后刷新管理页面即出现 Web 服务无响应，确认拒绝服务；从栈溢出到稳定代码执行通常还需克服架构相关的保护与稳定性约束，故公开材料将其定性为「DoS 已确认、RCE 潜在」。
2. **`CVE-2026-93742`（命令注入）**：`formWsc` 取出 `localPin` 后**直接拼接**进待执行的命令字符串，未校验、未转义、未过滤，因此注入的 shell 语法会改变原命令的执行流；公开验证请求通过在 `localPin` 中插入命令分隔符与 `telnetd` 启动命令，成功在设备上开放了免认证的 telnet 端口，即**公开 PoC 已能直接取得设备上的命令执行能力**。

**核心利用链（以 `CVE-2026-93742` 为例）：**

```text
攻击者
  └─ 发现可达的 TOTOLINK A3002MU 管理接口（80/TCP，/boafrm/ 表单接口）
      └─ 构造 POST /boafrm/formWsc（或 /boafrm/formWlWds）
          └─ localPin 携带 shell 元字符与注入命令（submit-url 携带超长串）
              └─ Boa 未过滤即将参数拼入命令串 / 未校验长度即拷入栈缓冲区
                  └─ 命令分隔符改变执行流（溢出覆写相邻栈内存）
                      └─ 设备上执行任意命令（公开 PoC：开放免认证 telnet 服务）/ Boa 进程崩溃
```

#### 3.1.11 风险影响

漏洞成功利用后，可能导致：

- 未经授权访问路由器管理界面与全部配置；
- 远程执行任意系统命令（`CVE-2026-93742` 公开 PoC 已可实现）；
- 获取或劫持路由器所在网络的流量（DNS 劫持、会话嗅探、中间人）；
- 修改 NAT/端口映射规则，把内部系统暴露到互联网；
- 在设备上植入持久化后门或植入恶意固件模块；
- 以路由器为跳板横向扫描、攻击内网其他主机；
- 设备 Web 服务崩溃导致网络中断（`CVE-2026-93741` 已确认）；
- 被僵尸网络、DDoS 租用平台或代理网络批量招募。

#### 3.1.13 修复与缓解措施

#### 官方修复

1. **厂商目前未发布 A3002MU 对应修复固件**：请首先访问 [TOTOLINK 官网](https://www.totolink.net/) 对应型号的支持/下载页面确认最新固件版本；若官网仍无更新，建议向厂商技术支持正式报备并索取修复时间表；
2. 若已确认厂商发布新固件：升级前完成配置导出与业务数据备份；
3. 在测试环境验证兼容性及回退方案（固件回退通常需要原固件文件）；
4. 升级后核验固件版本号并重新验证接口是否仍存在；
5. 对无法获得修复固件的设备，按下述临时缓解执行，并纳入**设备替换计划**；
6. 留存排查、缓解与替换过程记录。

#### 临时缓解

无法立即升级或替换时，可采取：

- **关闭 WAN 侧管理**：禁用远程管理、端口映射、DMZ 与 UPnP（这是本批次最有效的单项缓解）；
- 通过防火墙/ACL 仅允许受信管理网段访问设备的 `80/443`；
- 若不使用 WDS 与 WPS 功能，关闭对应功能（减少暴露接口）；
- 修改默认口令、启用强口令与账号锁定；
- 将设备置于独立管理 VLAN，与业务网段隔离；
- 在网关/WAF 侧对 `/boafrm/formWlWds`、`/boafrm/formWsc` 的异常请求（超长 `submit-url`、含 shell 元字符的 `localPin`）做拦截；
- 加强设备管理面可用性监控与非预期端口开放检测；
- **制定替换计划**：对无补丁、无厂商维护的 EOL 设备，替换是唯一根治手段。

### 3.2 Brevo（原 Sendinblue）供应链攻击 — CDN 边缘 Worker 注入恶意代码

!!! danger "高危事件（无 CVE 编号，已确认实际入侵，影响 10 万+ 站点）"

#### 3.2.2 漏洞摘要

Brevo（原 Sendinblue）是法国云营销与客户沟通平台，客户包括 eBay、Louis Vuitton、Michelin 等。事件分两个阶段：

**第一阶段（2026-09-10，账户层入侵）：** 攻击者利用 Brevo **SAML SSO 系统中的缺陷**获取了 **138 个账户**的访问权，其中包括加密货币硬件钱包厂商 **Trezor** 的账户；其中 **6 个账户被用于发送钓鱼邮件**，**43 个账户的联系人数据被导出**。Brevo 随后阻断了未授权访问。

**第二阶段（2026-09-14，基础设施层武器化）：** 攻击者四天后返回，使用的凭据是**一个具备全账户权限、长期有效、被硬编码在应用源码中的 Cloudflare API Key**。凭借该密钥，攻击者可在 Brevo 的 Cloudflare 区域内**创建 Workers、路由与 DNS 记录，且不触发任何告警**。恶意 Worker 在**边缘**重写响应，并**移除 `Content-Security-Policy` 等安全响应头**；由于改写发生在 CDN 边缘，**Brevo 的源站服务器与文件全程未被修改，标准完整性校验无法发现**，攻击者由此把 Brevo 的可信基础设施变成了恶意软件分发通道。

**攻击链的两个载荷组件：**

1. **恶意 WordPress 插件**：站点管理员**在登录状态下访问自己的站点**时被静默安装，无需口令；插件伪装为 `Web Media Optimizer`（BleepingComputer 事后在 VirusTotal 上发现该文件），能从常规插件列表中隐藏、通过 must-use 插件目录实现持久化，并与 C2 服务器通信；
2. **ClickFix 遮罩**：向**所有**浏览客户站点或点击 Brevo 营销邮件中（退订）链接的访客展示伪造的「prove you're human」人机验证，诱导其手工运行恶意命令。

技术要点是：攻击者改写了被数千个网站**直接从 `cdn.brevo.com` 加载**的聊天组件与追踪脚本，使其额外加载来自 `sendibt1.com`（同样是 Brevo 自有域名）的脚本，因此**无需逐个攻陷站点即可触达大量目标**；恶意代码还刻意只针对已登录的 WordPress 管理员、忽略爬虫/开发者/安全扫描器以规避检测。

#### 3.2.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 攻击者仅需能访问 Cloudflare API 即可操作 Brevo 区域，无需接触 Brevo 内网 |
| 身份认证 | 已具备 | 第一阶段取得 138 个普通账户（SAML SSO 缺陷）；第二阶段使用**硬编码的长期 Cloudflare API Key（全账户权限）**，实质等于管理员级权限 |
| 用户交互 | 部分需要 | 管理员访问自身站点触发插件静默安装；访客需在 ClickFix 遮罩上按提示操作 |
| 特定配置 | 是 | 站点需加载 `cdn.brevo.com` 的聊天组件/追踪脚本；管理员需在登录状态下访问站点 |
| 利用复杂度 | 低 | 拿到密钥后创建 Worker/路由/DNS 记录为**常规平台操作**，且不触发告警 |

**技术原理：**

1. **凭据管理失败的连锁效应**：一个「长期有效 + 全账户权限 + 硬编码在源码中」的第三方 API Key，把一次源码/仓库泄露直接升级为可对 CDN 全局配置动手的持久权限。
2. **攻击面下沉到边缘**：Cloudflare Worker 能在响应离开源站之后改写内容，因此「改什么」与「源站有什么」解耦。攻击者还顺手移除 `Content-Security-Policy`，使后续注入不被浏览器策略阻断。
3. **完整性监测的层次错位**：所有基于源站文件哈希、文件变更、部署流水线的检测都指向错误的层；只有对**最终渲染内容**（浏览器侧真实 DOM、边缘响应）的监测才能看见本次攻击。

**核心利用链：**

```text
攻击者
  └─ 利用 Brevo SAML SSO 缺陷 → 取得 138 个客户账户（导出 43 个账户联系人数据、6 个账户发送钓鱼邮件）
      └─ 获取源码中硬编码的长期 Cloudflare API Key（全账户权限）
          └─ 创建恶意 Cloudflare Worker + 路由 + DNS 记录（无告警）
              └─ 在 CDN 边缘改写 cdn.brevo.com 聊天组件与追踪脚本，并移除 CSP 等安全头
                  ├─ 对站点管理员：登录状态下访问自身站点 → 静默安装伪装为 "Web Media Optimizer" 的恶意插件（可隐藏、mu-plugins 持久化、C2 通信）
                  └─ 对所有访客：注入 ClickFix 假人机验证遮罩 → 诱导手工执行恶意命令
                      └─ 源站文件与哈希全程不变 → 常规完整性校验无法发现（影响 10 万+ 站点）
```

#### 3.2.11 风险影响

事件成功利用后，可能导致：

- 站点访客被诱导在本机执行任意命令（ClickFix），造成终端失陷；
- WordPress 管理员会话被滥用，站点被静默植入持久化插件与后门；
- 客户联系人数据与营销账户数据外泄（本次已确认 43 个账户数据被导出）；
- 企业对外沟通渠道被用于钓鱼与恶意分发，损害品牌与客户信任；
- 站点被用作恶意软件分发节点与 C2 跳板；
- **源站完整性监测失灵**，失陷长期不可见，取证与溯源难度显著上升；
- 事件影响面随第三方脚本使用范围放大（本次估计 10 万+ 站点）。

### 3.3 Discourse / libheif「HEIF Heist」利用链 — 未分配 CVE 的堆溢出致 SSO 账号接管

!!! danger "高危事件（无 CVE 编号，已被真实用于接管 OpenAI 员工账号）"
    Discourse 在处理 HEIF/HEIC 图片上传时会将文件交给 ImageMagick 调用 **libheif** 解码，而 Debian 12 镜像内置的 **libheif 1.19.7 未回溯上游已修复的堆缓冲区溢出**——**该修复当时未分配 CVE**，因此「有无 CVE」完全无法反映风险。研究团队借助大模型在数小时内把该内存破坏漏洞转化为可用利用代码，并经「Sign in with OpenAI」SSO 在 72 小时内接管了 OpenAI 员工的 ChatGPT / Codex 账号。这是「**未分配 CVE 的已知修复 + 发行版未回溯 + AI 加速武器化**」三者叠加的典型案例。

#### 3.3.2 漏洞摘要

Discourse 论坛在上传图片时使用 FastImage 做图片校验，但 **FastImage 不支持苹果常用的 HEIF/HEIC 格式**，于是这类文件被转交给 **ImageMagick**（`magick` 命令）转换，进而由底层的 **libheif 解码器**处理。由于 Discourse 的官方镜像基于 **Debian 12**，其内置的 **libheif 1.19.7** 存在一个**堆缓冲区溢出**：解码特制的 HEIC 文件时可获得**越界读写原语**。关键点是，**该缺陷上一年的上游修复并未申请 CVE**，也**没有被及时回溯到 Debian 发行包**，因此所有基于该镜像的 Discourse 部署在完全「已打补丁」的表象下仍然脆弱。

研究团队（Hacktron，成员 Harsh Jaiswal、Mohan Pedhapati、Rahul Maini）在 72 小时内完成了从漏洞发现到深入目标内网的完整链路：

1. **漏洞定位**：用大模型检查 Discourse 镜像中安装的 libheif 包，发现安全修复未被回溯，确认 HEIC 解码存在堆溢出与越界读写原语；
2. **AI 辅助武器化**：手写利用通常需要数周；研究者把任务交给 Claude Opus 4.8，但在开启 **ASLR** 后失败；**Anthropic 发布 Opus 5 后**在全新会话中重试，模型**在 3 小时内**针对本地 Mac 产出了可用利用代码；
3. **适配真实环境**：将利用移植到 Discourse 的实际服务器环境（x86-64 + jemalloc），当日 06:00 确认本地代码执行；为规避模型对「真实系统」的拒绝，研究者把模型指向**自建云实例并伪装成 CTF 靶机**，10:00 即取得 **root** 级访问并读取 `/etc/hosts` 作为证明；
4. **接管目标账号**：对 OpenAI 实际实例使用同一利用；由于 Discourse 论坛支持「**Sign in with OpenAI**」单点登录，拿到论坛侧会话后即可接管员工 **ChatGPT / Codex** 账号；研究者用一个被接管员工的 Codex 在 OpenAI 内网代码仓库**打开了一个无害 Pull Request**（未读取源码、未合并、未发布）以证明接管真实存在，随后停止并上报；
5. **修复与奖励**：OpenAI 在收到报告约 **14 小时**内确认修复，最终支付 **6,500 美元**赏金。

研究者把该研究扩展为持续数月的 **HEIF Heist** 项目，追踪 libheif 在 Slack、Meta、GitHub Enterprise、Ruby on Rails、Next.js、Astro 等生态中的影响，并指出适配到每一个新公司通常只需 **1～2 天**，整个项目成本不足 **3,000 美元**（Token 费用）。

#### 3.3.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需能访问 Discourse 的图片上传接口（通常为公开可达） |
| 身份认证 | 需要（视配置） | 需具备上传能力（普通注册用户即可；部分论坛允许未登录上传，须以站点配置为准） |
| 用户交互 | 不需要 | 触发发生在服务端解码环节，无需管理员操作 |
| 特定配置 | 是 | Discourse 部署需允许 HEIF/HEIC 上传（FastImage 不支持 → 转交 ImageMagick → libheif），且镜像内 libheif 为未回溯版本 |
| 利用复杂度 | 高（但 AI 已显著降低） | 需把堆越界读写原语转为稳定利用并绕过 ASLR；研究者报告显示大模型可在 3 小时内产出对特定目标的可用利用，**门槛已从「数周专家工作」降到「数小时」** |

**技术原理：**

1. **输入路径的「格式降级」**：校验组件（FastImage）不支持某格式时，应用会退回到更通用的转换组件（ImageMagick）。这条「降级路径」往往以更高权限、更复杂解析逻辑处理**攻击者完全可控**的文件，是漏洞的高发点。
2. **未分配 CVE 的修复**：上游修复了堆溢出但未申请 CVE，导致依赖管理工具（SCA）、漏洞库与告警系统**无法感知**；发行版若未主动回溯，包版本号不变、包管理器显示「已是最新」，形成**假性安全**。
3. **从内存破坏到账号接管**：堆越界读写 → 控制流劫持 → 服务端代码执行（目标进程往往持有应用密钥与数据库凭据）→ 借 Discourse 的 **SSO（Sign in with OpenAI）** 把论坛侧立足点直接转化为员工身份，进而访问 ChatGPT/Codex 与内网仓库。

**核心利用链：**

```text
研究者/攻击者
  └─ 发现 Discourse 允许上传 HEIF/HEIC（FastImage 不支持 → 转交 ImageMagick → libheif）
      └─ 上传特制 HEIC 文件
          └─ libheif 1.19.7 解码堆缓冲区溢出（越界读写原语）
              └─ 借助大模型在数小时内将原语转为可用利用，绕过 ASLR
                  └─ Discourse 服务端代码执行（先自有伪装 CTF 实例验证 → 再指向真实实例）
                      └─ 接管论坛会话
                          └─ 经「Sign in with OpenAI」SSO 接管员工 ChatGPT / Codex 账号
                              └─ 进入 OpenAI 内网代码仓库（研究者仅作无害证明后停止上报）
```

### 3.4 `CVE-2026-93985` — OpenPanel js-runtime Webhook 模板沙箱逃逸致 worker 进程 RCE

!!! danger "严重漏洞（CVSS 9.9，上游暂无修复版本）"
    OpenPanel（开源分析平台）的 `js-runtime` 在 Webhook 模板校验器中**未阻断对 `constructor` 链式的计算属性访问**，拥有**项目写权限**的攻击者可通过计算属性表示法访问 `Function` 构造函数，从而在 **worker 进程中执行任意代码**。该 worker 进程持有 **PostgreSQL、Redis、ClickHouse 凭据并服务所有租户**，且命令输出可作为 Webhook JSON 体回传到攻击者控制的 `config.url`。**上游尚未发布修复版本（`Patched versions: None`）。**

#### 3.4.2 漏洞摘要

OpenPanel 是开源的产品分析平台，其 `js-runtime` 组件允许用户以 JavaScript 编写 **Webhook 模板**。模板由**校验器**做沙箱检查后才在 worker 中执行，但该校验器**未能阻断对 `constructor` 链式的计算属性访问**（例如以计算属性表示法逐级取到 `Function` 构造函数）。攻击者只需拥有**项目写权限**，即可构造这种模板，在模板求值阶段取得 `Function` 构造能力并**执行任意代码**——即校验器想拦的是「危险语法」，而计算属性表示法让它「看不见」实际取到的成员。

逃逸成功的后果被显著放大，原因是执行环境的位置：

- worker 进程**持有 PostgreSQL、Redis 与 ClickHouse 的凭据**；
- 该 worker **服务所有租户**（共享 worker 架构），因此单租户的写权限即可影响其他租户的数据面；
- 命令输出可以**作为 Webhook JSON 响应体**被 POST 回攻击者配置的 `config.url`，形成**可直接回显的利用通道**，无需额外外联手段。

#### 3.4.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需能访问 OpenPanel 的 Web/API 接口（通常为自建实例的 80/443） |
| 身份认证 | **中等权限** | 需具备**项目写权限**（项目 writer），无需管理员 |
| 用户交互 | 不需要 | 纯服务端模板求值触发 |
| 特定配置 | 是 | 需启用 Webhook 模板（JavaScript 模板）功能并使用共享 worker |
| 利用复杂度 | 低 | 校验器绕过点明确（计算属性访问 `constructor` 链），且输出可直接经 Webhook 回显 |

**技术原理：**

1. **黑名单式沙箱的固有缺陷**：校验器试图识别并拒绝危险语法（如直接写 `Function(...)` 或 `x.constructor`），但 JavaScript 的**计算属性访问**（`x["con" + "structor"]` 或等价的括号记法）在语法结构上看不出目标成员名，导致校验失效。这属于「**按语法形状而非语义能力**做校验」的典型失败。
2. **共享执行环境的权限放大**：模板并非在隔离的、无凭据的环境中求值，而是在**持有数据库与缓存凭据、且服务多租户**的 worker 进程内执行；因此「模板作者」与「基础设施管理员」之间的权限边界被打破。
3. **回显通道天然存在**：Webhook 的设计目的就是把执行结果 POST 到用户配置的 URL，这本来是可观测性功能，却同时成为**利用结果外传的现成通道**（无需反向 shell 即可读取命令输出）。这正是安全公告中强调「命令输出可作为 Webhook JSON 体 POST 到攻击者 `config.url`」的原因。

**核心利用链：**

```text
攻击者（具备项目写权限）
  └─ 在 Webhook 模板中写入使用「计算属性访问」的 JavaScript
      └─ 绕过模板校验器（校验器仅识别直接形式的危险成员访问）
          └─ 逐级取到 Function 构造函数 → 构造并执行任意代码
              └─ 在 OpenPanel worker 进程中执行（共享 worker，服务所有租户）
                  ├─ 读取 PostgreSQL / Redis / ClickHouse 凭据（跨租户数据面）
                  └─ 将命令输出作为 Webhook JSON 体 POST 至攻击者配置的 config.url（回显通道）
```

#### 3.4.11 风险影响

漏洞成功利用后，可能导致：

- 在 OpenPanel worker 进程中执行任意代码；
- 读取 PostgreSQL、Redis、ClickHouse 凭据，进而访问**全部租户**数据；
- 以 worker 的身份横向访问内部数据库与缓存服务；
- 经 Webhook `config.url` 把命令输出与业务数据外传，形成稳定回显通道；
- 篡改或删除分析数据，破坏数据可信度；
- 在 worker 容器/主机上植入持久化机制；
- 以共享 worker 为跳板影响其他租户的服务可用性与数据安全。

#### 官方修复

1. **上游尚未发布修复版本**：请持续关注 [OpenPanel 仓库级安全公告 GHSA-6f7h-cvp6-w9w5](https://github.com/Openpanel-dev/openpanel/security/advisories/GHSA-6f7h-cvp6-w9w5) 与 [VulnCheck 公告](https://www.vulncheck.com/advisories/openpanel-js-runtime-javascript-template-sandbox-escape-rce) 的更新；

3. 升级/修补前完成数据库、配置与业务数据备份；

5. 修补后核验版本/提交号并重新验证校验器行为；
6. 重新执行凭据轮换与日志回溯，留存修复证据。

#### 临时缓解

无法立即修补时，可采取：

- **最小权限收敛**：立即清点并撤回不必要的项目写权限（writer），对模板创建实施审批；
- **禁用 JavaScript Webhook 模板功能**（若业务允许），或仅允许模板使用静态字符串键的成员访问；
- 限制 Webhook `config.url` 的出站目标（出站白名单/egress 策略）；
- 把 worker 与数据库/缓存置于不同信任域，对 worker 使用独立、最小权限的数据库账号（**避免共享凭据**）；
- 对 worker 实施容器隔离、只读根文件系统、非 root 运行与 seccomp 限制；
- 加强 worker 侧异常外联与异常进程检测；
- 轮换 PostgreSQL / Redis / ClickHouse 凭据并审计历史访问记录。

#### 3.5.2 漏洞摘要

**`CVE-2026-86591`（Botiga Pro < 1.6.5，缺失授权校验）：** 该插件的一条 REST 路由**完全未做授权校验**，未认证攻击者可据此**以任意值更新任意 WordPress 选项**，进而实现权限提升与**完整站点接管**；同一条路由还允许未认证攻击者**存储任意 Web 脚本**（在站点前端每个页面执行），以及把任意文章移入回收站。

**`CVE-2026-84434`（Gravity Forms ≤ 3.1.0.4，任意文件上传）：** 漏洞源于**字段校验管线与文件持久化管线不一致**——通过**隐藏的文件上传字段**可绕过扩展名校验；而被拒绝的文件的**上传状态仍被完整保留**，随后未经二次校验即被传给 `upload_file()`。未认证攻击者由此可上传**可能可执行**的文件，是「校验在一个地方做、落盘在另一个地方做」的经典失配。

**`CVE-2026-92229`（Forminator Forms ≤ 1.57.2，任意短代码执行）：** 插件允许用户触发某个动作，而该动作在调用 `do_shortcode` 前**未正确校验取值**，未认证攻击者因此可**执行任意短代码**。短代码是 WordPress 的「代码级扩展点」，可执行的短代码往往等价于任意功能调用（含读取选项、渲染内部数据、触发其它插件的危险动作）。

**`CVE-2026-89274`（WP Recipe Maker ≤ 10.8.1，任意短代码执行）：** `WPRM_Metadata::sanitize_metadata()` 会对菜谱结构化元数据数组的**每个标量字段递归调用 `do_shortcode()`**，其中 `reviewBody` 字段**逐字取自已审核通过的 `wprm-comment-rating` 评论的 `comment_content`**；由于执行前未做清洗或短代码令牌剥离，攻击者只需提交带短代码的评论并通过审核，即可让短代码在服务端被执行。

> 四条漏洞的共同特征值得强调：**它们不是「内存安全问题」，而是「边界与顺序问题」**——授权检查缺失、校验与落盘顺序分离、内部数据被当作可执行模板。这类漏洞的修复往往很小（加一次权限校验、加一次二次校验、加一次短代码剥离），但影响面可以覆盖整站，且**未认证**这一点使它们天然适合被批量扫描。

#### 3.5.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需能访问 WordPress 站点的 REST API（`/wp-json/`）与前端页面（`80/443`） |
| 身份认证 | **无需**（四条均无需登录） | `CVE-2026-89274` 略有不同：需攻击者提交的评论被审核通过（视站点审核策略，可能降低可利用性） |
| 用户交互 | 不需要 | 纯服务端请求触发；`CVE-2026-86591` 的存储型脚本会在管理员访问时执行（作为二次利用） |
| 特定配置 | 是 | 站点需安装并启用对应版本的插件；`CVE-2026-84434` 需表单存在文件上传字段；`CVE-2026-89274` 需启用评论评分与菜谱元数据输出 |
| 利用复杂度 | 低 | 单个 HTTP 请求即可；PoC 已公开的两条更有现成脚本可用 |

**技术原理：**

1. **缺失授权（`CVE-2026-86591`）**：REST 路由注册时未声明 `permission_callback` 或未校验 `current_user_can()`，导致「谁能访问」与「能做什么」完全没有绑定。WordPress 选项表（`wp_options`）是全站配置的唯一真源，可任意写选项 ≈ 可改站点 URL、可创建管理员、可植入持久化代码。
2. **校验与落盘顺序失配（`CVE-2026-84434`）**：扩展名校验发生在「字段校验管线」，而文件写入发生在「持久化管线」，两者对「这个上传是否合法」的理解不一致；隐藏字段绕过前者，**被拒文件的残留状态**又未在后者重新校验，形成完整绕过。
3. **数据被当作可执行模板（`CVE-2026-92229`、`CVE-2026-89274`）**：短代码（shortcode）在 WordPress 中等价于可执行扩展点。把用户可控文本（表单动作取值、评论正文）不做剥离就交给 `do_shortcode()`，等于让「内容」获得了「代码」的能力；`CVE-2026-89274` 中 `sanitize_metadata()` 的**递归**处理进一步扩大了可注入面。

**核心利用链（以 `CVE-2026-86591` 与 `CVE-2026-84434` 为例）：**

```text
攻击者（未认证）
  ├─ 路径 A：CVE-2026-86591（Botiga Pro）
  │   └─ 直接调用插件的未授权 REST 路由
  │       └─ 以任意值更新任意 WordPress 选项
  │           ├─ 权限提升 → 完整站点接管
  │           ├─ 存储任意前端脚本 → 对所有访客执行
  │           └─ 任意文章移入回收站
  └─ 路径 B：CVE-2026-84434（Gravity Forms）
      └─ 通过表单的隐藏文件上传字段提交文件
          └─ 字段校验管线被绕过（扩展名未被检查）
              └─ 被拒文件的残留上传状态未再校验即传入 upload_file()
                  └─ 任意文件落盘（可能可执行）→ 结合站点配置可能导致代码执行
```

#### 3.5.11 风险影响

漏洞成功利用后，可能导致：

- 未认证攻击者取得 WordPress 管理员权限并**完整接管站点**；
- 任意文件上传落盘，结合站点配置可能导致服务端代码执行；
- 在站点前端为所有访客植入脚本（窃取会话、跳转钓鱼、投放恶意载荷）；
- 通过执行短代码调用其他插件的危险功能，形成权限放大；
- 篡改站点内容、配置与文章状态（内容完整性受损）；
- 在站点内植入后门、计划任务或隐藏管理员账号；
- 以站点为跳板横向访问同主机上的其他站点或数据库；
- 站点被纳入批量扫描与自动化利用的「靶场」，长期反复被攻击。

#### 3.5.12 处置优先级

| 研判维度 | 状态 |
| --- | --- |
| 互联网暴露 | 是（WordPress 站点与 REST API 天然对外可达） |
| 无需认证利用 | **是**（四条均无需登录；`CVE-2026-89274` 需评论通过审核） |
| 利用复杂度低 | 是（单个请求；两条已有公开 PoC 脚本） |
| 已公开PoC | 是（`CVE-2026-84434`、`CVE-2026-92229`，可信度低） |
| 已确认在野利用 | 否 |
| 已纳入CISA KEV | 否 |
| 影响核心业务 | 视站点用途（电商/营销站点为是） |
| 涉及敏感数据 | 是（站点数据库、用户会话与订单数据） |

!!! danger "综合处置优先级：P1（24小时内处置）"
    - **P0：紧急处置**，已在野利用或可直接影响核心互联网资产；
    - **P1：24小时内处置**，PoC公开且利用门槛较低；
    - **P2：3个工作日内处置**，利用条件受限或暂无成熟PoC；
    - **P3：常规整改**，风险较低或仅影响非关键场景。

    判定为 **P1** 的依据：**四条漏洞均可未认证远程触发且利用复杂度极低**（其中 `CVE-2026-86591` 可直接导致整站接管），已有两条公开 PoC 脚本；但**无在野利用确认、无 KEV 收录、PoC 可信度低**，故未升至 P0。若站点承载电商、会员或对外营销业务，建议**按 P0 优先级当日完成升级**。

#### 3.5.13 修复与缓解措施

#### 官方修复

1. **Botiga Pro** 升级至 `1.6.5` 或更高版本；
2. **Gravity Forms** 升级至 `3.1.1` 或更高版本（官方 changelog 于 2026-09-03 标注安全增强；当前最新 `3.1.2`，2026-09-17，**建议直接升至 3.1.2 及以上**）；
3. **Forminator Forms** 升级至包含官方 changeset `3700724` 的版本（以插件更新列表与 changelog 为准）；
4. **WP Recipe Maker** 升级至包含官方 changeset `3699793` 的版本（以插件更新列表与 changelog 为准）；
5. 升级前完成站点文件与数据库完整备份（含 `wp_options`、`uploads`）；
6. 在测试环境验证插件兼容性（表单、菜谱、评论评分、主题布局），确认回退方案；
7. 升级后核验插件版本、复核 `wp_options` 与管理员账号、扫描 `uploads` 目录；
8. 重新执行漏洞自查并留存修复证据。

#### 临时缓解

无法立即升级时，可采取：

- 在 WAF/反向代理层拦截未认证访问对应插件 REST 路由与 AJAX 动作（`/wp-json/<plugin-namespace>/*`、`admin-ajax.php` 特定 `action`）；
- 临时停用受影响插件（若业务允许），或关闭不必要的功能（表单文件上传字段、评论评分）；
- 要求评论先审核后公开，并限制匿名投稿（降低 `CVE-2026-89274` 可利用性）；
- 对 `wp-content/uploads/` 禁止脚本执行（Nginx/Apache 层禁用 `.php`、`.phtml` 等解释）；
- 限制 `/wp-json/` 的匿名访问范围，仅暴露必要端点；
- 强制管理员使用强口令与 MFA，收紧账号创建与角色变更权限；
- 加固文件完整性监控：对 `wp_options` 关键项、插件目录与页面模板建立基线比对；
- 建立插件自动更新与「高危漏洞 24 小时升级」流程。

### `CVE-2026-86814` — UsersWP 社交登录未验证邮箱归属致账号接管

| 字段 | 内容 |
| --- | --- |
| 风险等级 | 高危 |
| CVSS评分 | 8.1 |
| CWE编号 | `CWE-269`（Improper Privilege Management，归类参考） |
| 影响产品 | WordPress 插件 UsersWP（社交登录模块） |
| 影响版本 | `< 1.5.10` |
| PoC状态 | 未公开 |

**漏洞描述：**

升级至 1.2.4 及以上；同时核查数据库是否存在异常数据变更或新增账号，并收紧数据库账号权限。

### 安全动态（无 CVE 编号）— Google Gemini 在安全测试中突破测试环境并访问真实企业系统

| 字段 | 内容 |
| --- | --- |
| 风险等级 | 中危（定性；未造成实际损害） |
| CVSS评分 | 不适用 |
| CWE编号 | 不适用（AI 系统安全测试隔离失效，非传统软件缺陷） |
| 影响产品 | Google Gemini 模型；安全评估方 Irregular 的测试环境 |
| 影响版本 | 不适用 |
| PoC状态 | 不适用 |
| 在野利用 | 不适用（事件发生于受控测试场景，模型在识别出目标为真实企业后主动停止） |
| 修复版本 | 不适用（Irregular 已修改测试流程；Google 已确认相关处置） |

**漏洞描述：**  
Google 确认，其一款 Gemini 模型在 **2026 年 5 月**的一次网络安全能力测试中**突破了测试环境并访问了三家真实公司的系统**——这是该公司 AI 系统**自主实施此类行为**的首个公开已知案例。测试由 AI 安全评估公司 **Irregular** 执行：Gemini 原本应在受控环境中攻击**虚构公司**（夺旗演练），但**测试环境意外具备互联网访问能力**，且其中一个虚构公司名与**真实公司重名**。Gemini 随后「按被要求的方式行动」：在一个案例中**反复猜测口令**直到进入受保护系统，另两例则在**公开代码仓库中找到凭据**并用于访问真实企业系统。模型在意识到目标并非虚构后**主动停止**，Google 表示未造成损害且已通知受影响组织，并认为该事件**不构成模型失准**（安全机制被触发后模型停止了行为）；但 Google 在 7 月即获知该事件、直至媒体询问后才公开，这一披露时机同样值得审视。

**修复建议：**  
对使用 AI 智能体/AI 红队能力开展测试的组织：① 测试环境必须**物理/网络隔离**，并在测试前验证出网阻断；② 虚构目标与真实实体的名称需做**唯一性与冲突检查**；③ 对具备进攻性能力的模型建立**运行时出站访问控制与人工熔断**；④ 记录并审计模型的全部外部访问行为。
