1. **`CVE-2026-67276` / `CVE-2026-86060`：MikroTik RouterOS「MikroTrick」链——SSH 暴露即可能已被无认证接管（CVSS 9.2×2，在野利用）**

3. **`CVE-2026-67277`：RouterOS bandwidth-test 服务未认证内存泄露与内核远程重启（CVSS 4.0 8.8）**

### 1.4 综合研判

本批漏洞影响 MikroTik RouterOS 全部受支持分支（v6 与 v7，跨度 2014 年以来发布的 6.0.0–7.24.1 范围），覆盖面为路由器/CPE 类设备中罕见的广谱；其中 MikroTrick 链已被确认在野利用且无需认证，RouterOS 设备在互联网上存量巨大（大量 ISP 边缘、企业分支、站点间 VPN 网关与家庭高级路由器），SSH 管理口暴露公网是常见错误配置——攻击者已用实际攻击证明该暴露面正在被批量利用，且公开 PoC 预计 1–2 天内出现，利用门槛将进一步降低。补丁自 09-03 起可用、MikroTik 首次经官方 App 推送告警并内置 Flagged 失陷检测，防御方具备快速闭环条件，当前最大风险来自未升级设备与"已失陷未发现"的存量。

!!! danger "研判结论：高风险"
    本期最大风险点是 MikroTrick 链（`CVE-2026-67276`+`CVE-2026-86060`）的在野利用：凡 SSH 暴露于公网且未升级至 6.49.21/7.23.4/7.24.2（含 7.23.5）的 RouterOS 设备，须立即按"已失陷"假设处置——先隔离取证核查（"-2" 登录记录、"ops" 账户、Flagged 标记），再升级并重置凭据，不得直接重启了事；同时收敛 WWW/WebFig 与 bandwidth-test 的公网暴露面以覆盖 67281/67277 等其余同批漏洞。本站在线公开文档站点、无内部资产台账，读者请按自有网络设备台账于 24 小时内完成排查（P0）。

### 3.1 `CVE-2026-67276` — MikroTik RouterOS SSH RSA 公钥验证绕过漏洞（MikroTrick 链·认证绕过）

!!! danger "严重漏洞（CVSS v4.0 9.2，在野利用链组成部分）"
    MikroTik RouterOS SSH 服务端在校验客户端公钥认证时仅比较密钥类型与模数（modulus）、忽略指数（exponent），且签名验证使用客户端提供的密钥——攻击者只要知道某有效用户名及其 RSA 公钥的模数，即可用 e=1 伪造公钥并自算合法签名，在**没有私钥**的情况下以该用户身份登录。该漏洞与 `CVE-2026-86060` 组成 CERT Polska 命名的 **MikroTrick** 链，实现无需认证的完全设备接管，已在野利用。

#### 3.1.2 漏洞摘要

该漏洞位于 RouterOS **SSH 服务端的公钥认证（publickey）比对逻辑**中。RouterOS 将客户端出示的 SSH 公钥与目标用户已授权公钥进行匹配时，只比较**密钥类型与模数（modulus）**，未比较**指数（exponent）**；更关键的是，后续**签名验证使用客户端自己提供的公钥**而非服务器存储的授权公钥。攻击者若知道一个有效用户名及其授权 RSA 公钥的模数 n（公钥通常可经配置泄露、历史备份或已失陷同网段设备获得），可构造指数 e=1 的伪公钥 `{ssh-rsa, e=1, n=victim_n}` 提交。由于 `sig^1 mod n ≡ sig`，对 e=1 的密钥而言"签名"等于原文本身——攻击者可自行计算 `EMSA-PKCS1-v1_5(hash)` 作为合法"签名"，无需持有私钥即可通过验证，以该用户身份打开 SSH 命令通道。

> CERT Polska 官方描述："RouterOS does not compare the complete RSA public key when matching an SSH authentication request to an authorized user key, checking the key type and modulus but omitting the exponent. Because signature verification uses the client-supplied key, an attacker knowing an authorized RSA modulus can supply a key with exponent one, forge a valid signature, and open an SSH command channel as the target user without the private key."（NVD 收录原文）单独利用时权限等同被冒充用户；与 `CVE-2026-86060`（SSH 会话权限提升）组合（MikroTrick 链）即可在无任何认证下取得完全管理权限，这正是 CERT Polska 观察到的在野攻击模式。

#### 3.1.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 目标 RouterOS 的 SSH 服务（默认 22/tcp）须可从攻击者网络到达（公网暴露为高危场景） |
| 身份认证 | 无需（链）；本漏洞需有效用户名 | 需知道一个**有效用户名及其授权 RSA 公钥的模数**；与 86060 组合后完全无需认证（AC:H 反映该前置知识要求） |
| 用户交互 | 不需要 | 纯协议层攻击 |
| 特定配置 | 是 | 目标用户须配置了 RSA 公钥认证（authorized key）；SSH 服务须启用 |
| 利用复杂度 | 中 | 需获取有效用户名与公钥模数；数学构造简单（e=1 伪造），Raiu 称其已用 AI 工具验证可复现性（见 3.1.7） |

**技术原理：**

RouterOS SSH 用户认证阶段（userauth）对客户端出示的公钥与授权密钥做匹配时仅校验 (key type, modulus) 二元组而遗漏 exponent；随后协议以客户端出示的公钥执行 RSA 签名验证。RSA 中当指数 e=1 时，签名验证方程 `m ≡ s^e mod n` 退化为 `m ≡ s mod n`，即任意小于 n 的消息 m 其"签名"就是 m 本身。攻击者构造 `{ssh-rsa, e=1, n=受害者模数}`，将待签名字节串（EMSA-PKCS1 v1.5 填充后的摘要）直接作为签名值提交即可通过校验——签名与私钥完全无关。该缺陷属于**密码学协议实现层面的比对/验证不一致**（CWE-347），并非暴力破解或私钥泄露。

**核心利用链（MikroTrick 链整体，据 CERT Polska 公告与公开分析概括）：**

```text
攻击者
  └─ 发现 SSH 暴露于公网的 RouterOS 设备（扫描 22/tcp）
      └─ 获取有效用户名 + 目标用户 RSA 公钥模数（配置泄露/历史备份/口令猜测用户名）
          └─ 构造 e=1 伪公钥 {ssh-rsa, e=1, n=模数}，自算"合法签名"（CVE-2026-67276）
              └─ 以目标用户身份通过 publickey 认证，打开 SSH 命令通道
                  └─ 以"-"开头的畸形用户名触发 policy mask 变更，提权至完全管理（CVE-2026-86060）
                      └─ 创建 "ops" 高权限账户 / 加 SSH 密钥 / 改防火墙规则 / 开代理隧道（已观测行为）
```

> 以上为基于 CERT Polska 公告与公开技术分析的概括性复述，非官方逐字节细节；严禁据此对任何系统实施验证或利用。

#### 资产排查

- [ ] 检查设备是否出现 Flagged 标记（/system device-mode print）

#### 日志与行为排查

重点检查：

- `/log` 中 `login failure for user -2 from <ip> via ssh` 类记录（用户名 "-2" 非合法账户，正常日志不应出现）；
- `/system history` 中 `ssh:-2@<ip>` 后跟随的用户/密钥/防火墙/脚本/调度器/代理/隧道/抓包配置变更；
- 新增高权限账户（尤其名为 **ops**）或向既有账户追加 SSH 公钥；
- 设备发起异常出站连接（代理/隧道/回连）、异常升级或配置导出行为；
- 同网段其他设备对 22/tcp 的批量扫描记录。

| 检测项 | 可疑特征 |
| --- | --- |
| 请求路径 | SSH 公钥认证流程（22/tcp），非 HTTP 路径 |
| 请求方法 | SSH userauth publickey 方法 |
| 参数特征 | 客户端公钥 `e=1`（指数为 1）的 RSA 密钥 blob；用户名以 "-" 开头（配合 86060） |
| User-Agent | 不适用（SSH 协议无 UA；关注来源 IP 集中度） |
| 响应状态 | 认证成功但来源 IP 非已知管理员、时间异常 |
| 进程行为 | 设备上出现未知脚本/调度器任务 |
| 文件行为 | RouterOS 文件系统中出现未知文件（配合 67279） |
| 网络行为 | 设备向攻击者基础设施（如 `82.192.72[.]4` 托管文件集）发起下载/回连 |

#### 3.1.11 风险影响

漏洞成功利用后，可能导致：

- 在无私钥情况下冒充任意配置了 RSA 公钥的用户登录 RouterOS（本漏洞单点影响）；
- 与 `CVE-2026-86060` 组合（MikroTrick）实现**无需认证的完全管理权限接管**；
- 完全控制路由器/网关：读取与篡改流量、DNS/防火墙规则，部署流量劫持与中间人；
- 建立隧道/代理使内网成为跳板，横向攻击企业内网其他系统；
- 植入持久化后门（账户/SSH 密钥/脚本/调度器），重置后仍可能留存；
- 被用于僵尸网络（MikroTik 设备是 DDoS/代理僵尸网络的常见载体）、窃听站点间 VPN 流量。

    - **P0：紧急处置**——MikroTrick 链已在野利用且无需认证，SSH 暴露公网的 RouterOS 设备须**立即**（24 小时内）完成"隔离核查 → 升级 → 重置凭据"闭环（具体步骤见 3.1.13 与第五章）；未暴露 SSH 的设备也建议本周内升级以覆盖同批其余漏洞。核查时如发现 "-2"/"ops"/Flagged 痕迹，按已失陷处置（取证后恢复出厂并重建配置），不得仅重启或仅升级了事。

#### 3.1.13 修复与缓解措施

#### 官方修复

1. 将 RouterOS 升级至 `6.49.21`（v6 Long-term）、`7.23.5`（v7 Long-term，含 7.23.4 的 IPv6 DHCP 回归修复）或 `7.24.2`（Stable）及更高版本；开发通道用户升级至 `7.25beta3`；
2. 升级途径：WinBox/WebFig `Check for updates`、`/system package update` 或官方下载页（仅从 [mikrotik.com/download](https://mikrotik.com/download) 获取镜像，防止供应链篡改）；
3. 升级完成后核查 `/system device-mode print` 的 Flagged 标记与日志 critical 条目，按 [Flagged 状态文档](https://manual.mikrotik.com/docs/system-information-and-utilities/device-mode#flagged-status)处置；
4. 升级后核对版本并抽查 SSH 登录、防火墙规则与业务隧道正常。

#### 临时缓解

无法立即升级时，可采取：

- **立即关闭或限制 SSH 服务**（`/ip service disable ssh`，或设置 `available-from` 仅允许可信管理网段）；CERT Polska 明确建议禁用或限制 SSH、WWW/WWW-SSL 与 bandwidth-test 服务；
- 不要从未打补丁的设备发起 TLS 连接或使用内置 SSH 客户端（`/system ssh`、`/system ssh-exec`）访问不受信主机（覆盖同批 SSH 客户端/X.509 类漏洞，见 4.1）；
- 在网关上对 RouterOS 设备管理端口实施 ACL/防火墙收敛，仅允许管理跳板 IP 访问；
- 检查并轮换管理员口令与全部 SSH 密钥；审计现有用户列表与授权公钥；
- 对疑似失陷设备：隔离网络 → 保留日志与配置（导出）→ 恢复出厂设置 → 基于可信基线重建配置（**不要盲目恢复可能来自失陷设备的完整备份**）。

### 3.2 `CVE-2026-86060` — MikroTik RouterOS SSH 用户名参数注入权限提升漏洞（MikroTrick 链·提权）

!!! danger "严重漏洞（CVSS v4.0 9.2，在野利用链组成部分）"
    RouterOS SSH 登录路径处理以禁用字符（如 "-"）开头的用户名时存在参数处理缺陷，可改变 RouterOS 的受信策略掩码（policy mask）导致权限提升。未认证 SSH 会话在到达登录助手（login helper）时即可触发；与 `CVE-2026-67276` 组合（MikroTrick 链）后，攻击者可在无任何凭据下将受限会话提升为完全管理权限——在野攻击日志中的畸形用户名 "-2" 即与该缺陷相关。

#### 3.2.2 漏洞摘要

该漏洞位于 RouterOS **SSH 登录路径的用户名参数处理**中：当用户名以被禁止的字符（如连字符 "-"，在类 Unix 参数解析中常被解释为选项前缀）开头时，RouterOS 的登录助手对参数的解析发生混淆，攻击者可借此**改变 RouterOS 的受信策略掩码（trusted policy mask）**，从而把会话权限提升至完全管理（full administrative privileges）。CERT Polska 指出利用该漏洞仅需未认证的 SSH 会话到达 RouterOS 登录助手即可。其 CWE-88（参数注入）定性表明问题本质是"用户可控输入被当作参数定界符解析"，与在野攻击中观测到的畸形用户名 `-2` 相符——该用户名同时出现在失败登录记录与成功账户创建记录（`ssh:-2@<ip>`）中，成为 MikroTrick 攻击的公开指纹。

> CERT Polska 官方描述："RouterOS contains an argument-handling flaw in the SSH login path involving usernames that begin with a prohibited character, allowing for the trusted RouterOS policy mask to be changed, leading to privilege escalation. Exploitation requires an unauthenticated SSH session to reach the RouterOS login helper."（NVD 收录原文）单独利用需先建立 SSH 会话（通常需有效账户或配合 67276 的认证绕过）；组合后即构成无需认证的完全接管链。

#### 3.2.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 目标 RouterOS SSH 服务（22/tcp）须可达 |
| 身份认证 | 无需（链）；单点利用需先建立 SSH 会话 | 未认证会话到达登录助手即可触发（CERT Polska）；在野链中经 67276 认证绕过进入 |
| 用户交互 | 不需要 | 纯协议层攻击 |
| 特定配置 | 是（AT:P） | 需满足可触发策略掩码变更的部署/策略条件（CERT Polska 未披露细节，不作臆测） |
| 利用复杂度 | 低 | 仅需构造以禁用字符开头的用户名；CERT Polska 描述中无复杂前置 |

**技术原理：**

RouterOS 的 SSH 登录流程会把用户名交给登录助手处理以确定会话策略（policy mask，决定该会话可用命令与权限集）。当用户名以被禁止的字符开头（"-" 为典型选项定界符）时，参数解析逻辑将其后续内容错误解释为选项/参数而非纯用户名，导致**受信策略掩码被改写**——本应受限的未认证/低权限会话被赋予完全管理权限。该缺陷属典型的"用户输入与参数定界符未正确分离"（CWE-88），与命令行注入同族但发生在 SSH 登录的用户名解析路径上。

**核心利用链（MikroTrick 链整体，与 3.1 共用）：**

```text
攻击者
  └─ 以畸形用户名 "-2"（或同类禁用字符开头用户名）发起 SSH 登录
      ├─ 单独利用：需先建立会话（有效账户或 67276 伪造公钥登录）
      └─ 链式利用：CVE-2026-67276 e=1 伪公钥认证通过后
          └─ 触发用户名参数解析缺陷，受信策略掩码被改写（CVE-2026-86060）
              └─ 会话提升至完全管理权限（full admin）
                  └─ 创建 "ops" 账户 / 添加 SSH 密钥 / 修改防火墙 / 启用代理或隧道（在野已观测）
```

> 以上为基于 CERT Polska 公告与在野痕迹的概括性复述；策略掩码变更的具体参数与触发细节官方未披露，本报告不作臆测，严禁据此实施验证。

### 3.3 `CVE-2026-67277` — MikroTik RouterOS bandwidth-test 服务未认证内存泄露与内核拒绝服务漏洞

!!! danger "高危漏洞（CVSS v4.0 8.8）"
    RouterOS bandwidth-test（btest）服务允许未认证连接进入本应登录后才可到达的测试状态：配合 `random-data=false` 模式泄露内核数据包缓冲区**未初始化内存**，另一处未校验的倒置包长区间触发**无符号整数下溢**，可产生异常巨大的分片输出并**重启 RouterOS 内核**（远程 DoS）。与 MikroTrick 链同批披露、同批修复。

#### 3.3.2 漏洞摘要

RouterOS 的带宽测试服务（bandwidth-test，用于测量设备间吞吐，服务端默认 UDP 2000 端口）在处理连接状态机时存在缺陷：**"关联"（related）的 btest 连接可在主会话完成认证之前被接受**，未认证客户端由此进入本应仅登录用户可用的测试状态并发起 IPv4 UDP 测试。测试中若置 `random-data=false`，发送方会从内核数据包缓冲区拷贝**未初始化内存**（栈/堆残留，可能含内核敏感数据）作为负载发出，构成内核内存泄露；同时另一处**包长区间校验被倒置（inverted）且未检查**，导致无符号整数下溢，产生异常巨大的分片输出，可致 RouterOS 内核重启（远程拒绝服务）。

> CERT Polska 官方描述（NVD 收录原文）："RouterOS accepts a 'related' btest connection before the corresponding primary session has completed authentication. An unauthenticated client can use this state to start an IPv4 UDP test. With 'random-data=false', the sender transmits an uninitialized tail from a kernel packet buffer. A separate unchecked, inverted packet-size interval causes unsigned integer underflow, anomalously large fragmented output, and can restart the RouterOS kernel." 影响以可用性为主（VA:H），兼有内核内存泄露（VC:L）。

#### 3.3.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | bandwidth-test 服务（默认 UDP 2000）须可达（公网暴露为高风险场景） |
| 身份认证 | 无需 | 未认证连接即可进入测试状态（本漏洞核心缺陷） |
| 用户交互 | 不需要 | 纯协议层攻击 |
| 特定配置 | 是 | 设备启用 bandwidth-test 服务（RouterOS 默认安装但服务暴露面取决于防火墙） |
| 利用复杂度 | 低 | 构造 btest 协议请求即可；无需前置权限 |

**技术原理：**

bandwidth-test 协议存在主/关联连接的状态机：关联连接本应仅在主会话认证完成后被接受，但实现未校验该顺序（CWE-306）。未认证客户端利用该状态缺陷直接发起 IPv4 UDP 测试，服务端在 `random-data=false` 模式下发送数据时拷贝了内核数据包缓冲区的未初始化尾部（含内核内存残留）——构成信息泄露；另一条缺陷路径中，包长区间上下界校验被倒置且缺失检查，攻击者提供的异常区间值经无符号算术回绕为巨大长度，导致分片输出异常放大并最终使 RouterOS 内核重启。

**核心利用链：**

```text
攻击者
  └─ 发现可达的 RouterOS bandwidth-test 服务（UDP 2000）
      └─ 未认证建立"关联"btest 连接（绕过认证状态机，CWE-306）
          ├─ 置 random-data=false 发起 IPv4 UDP 测试 → 接收含内核未初始化内存的响应（泄露）
          └─ 提交倒置的包长区间 → 无符号整数下溢 → 异常巨大分片输出 → 内核重启（DoS）
```

> 以上为基于 CERT Polska 公告文字的概括性复述，非协议级细节；严禁据此对任何系统实施验证。

### 3.4 `CVE-2026-67281` — MikroTik RouterOS WebFig `/jsproxy` 未认证任意文件读取漏洞

!!! danger "高危漏洞（CVSS v4.0 8.7）"
    RouterOS WebFig 的 `/jsproxy` 文件服务路径中，新分配的会话保留了陈旧的**未初始化 principal 指针**并用于文件授权判断：攻击者可操纵内存分配器使该指针被以足够权限解引用，再在加密 URI 中构造父目录组件逃逸 WebFig 文件命名空间，**未认证读取 root 所有文件**——包括包含凭据的配置存储。影响 WebFig（WWW/WWW-SSL）暴露于不受信网络的 RouterOS 设备。

#### 3.4.2 漏洞摘要

RouterOS WebFig（Web 管理界面）的 `/jsproxy` 路径用于向浏览器代理文件/资源请求。CERT Polska 发现该路径的文件授权逻辑存在缺陷：**新建会话时分配的文件授权对象保留了陈旧的未初始化 principal（主体）指针**，用于判断"当前请求者是否有权读取该文件"。攻击者可先操纵内存分配器（使后续分配复用含高权限指针的陈旧内存），让文件服务路径以**过高权限**解引用该指针，从而绕过授权；再于加密 URI 中提供父目录组件（`..`），逃逸 WebFig 文件命名空间，最终**未认证读取 root 拥有的任意文件**，包括含凭据的配置存储（configuration stores）。

> CERT Polska 官方描述（NVD 收录原文）："RouterOS WebFig contains an unauthenticated file-read vulnerability in the /jsproxy path where a newly allocated session retains a stale uninitialized principal pointer used for file authorization. An unauthenticated attacker can prepare the allocator so that the file-serving path dereferences this pointer with sufficient rights, then supply parent-directory components in an encrypted URI to escape the WebFig file namespace and disclose root-owned files, including configuration stores containing credentials." 读取配置存储后，攻击者可获得设备口令/密钥/隧道凭据，进一步支撑 67276 类公钥伪造或内网横向。

#### 3.4.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | WebFig（WWW/WWW-SSL，80/443）须可达（公网暴露为高危场景） |
| 身份认证 | 无需 | 未认证即可触发（本漏洞核心） |
| 用户交互 | 不需要 | 纯 HTTP 请求 |
| 特定配置 | 是 | WebFig/WWW 服务启用且文件服务路径可达；分配器状态可被攻击者预置（heaping 类条件） |
| 利用复杂度 | 低 | CERT Polska 描述中无复杂前置；需构造加密 URI 与父目录组件 |

**技术原理：**

WebFig 的 `/jsproxy` 文件服务在响应请求时，需要以"当前登录主体（principal）"的权限判定目标文件是否可读。缺陷在于新建会话时该 principal 指针取自**未初始化内存**——若攻击者预先通过一系列请求操纵分配器（使目标内存槽位残留此前高权限会话/内部主体的指针值），文件授权检查便会以该残留主体的权限执行，形成越权。随后请求 URI 中的加密父目录组件（`..` 经加密传输以绕过路径清洗）使解析逃逸出 WebFig 设计上的文件命名空间，指向 root 文件系统任意路径，未认证读出文件内容。配置存储（configuration stores）中包含管理员口令哈希/明文、SSH 密钥、VPN/隧道预共享密钥等敏感凭据，泄露后可被用于登录设备或解密流量。

**核心利用链：**

```text
攻击者
  └─ 发现 WebFig 暴露的 RouterOS（80/443）
      └─ 预置内存分配器状态（构造会话序列，使授权指针残留高权限主体值）
          └─ 向 /jsproxy 发送带加密父目录组件的未认证请求（CWE-824 未初始化指针 + CWE-22 穿越）
              └─ 以残留主体权限读取 root 文件系统任意文件
                  └─ 获取配置存储中的口令/密钥/隧道凭据 → 登录设备或支撑其他漏洞利用
```

> 以上为基于 CERT Polska 公告文字的概括性复述；加密 URI 具体格式与分配器操纵细节官方未披露，严禁据此实施验证。

## 四、其他漏洞简报

### 4.1 `CVE-2026-67278` — RouterOS X.509 畸形 RSA 签名验证缺陷（TLS 服务器仿冒，中危）

| 字段 | 内容 |
| --- | --- |
| 风险等级 | 中危（CVSS v4.0 6.3，CERT Polska/NVD） |
| CVSS评分 | 6.3（v4.0，`AV:N/AC:L/AT:P/PR:N/UI:N/VC:L/VI:L/VA:N`） |
| CWE编号 | `CWE-347`（加密签名验证不当） |
| 影响产品 | MikroTik RouterOS（X.509 证书校验 / 出站 TLS 客户端） |
| 影响版本 | `[6.0.0, 6.49.21)`、`[7.0.0, 7.23.4)`、`[7.24, 7.24.2)` |
| PoC状态 | 未公开 |
| 在野利用 | 未知 |
| 修复版本 | 6.49.21 / 7.23.4（建议 7.23.5）/ 7.24.2 / 7.25beta3（2026-09-03） |

**漏洞描述：**  
RouterOS 在 X.509 验证中接受畸形的 RSA/PKCS#1 v1.5 签名（CWE-347，与 67276 同族缺陷：签名验证不完整）。其信任库包含一个 e=3 的根 CA——攻击者控制或重定向 RouterOS 发起的出站 TLS 连接后，可利用该根证书的**公钥**（无需私钥）伪造受信中间 CA，并为任意主机名签发证书，实现 **TLS 服务器仿冒**（中间人）。触发需攻击者可拦截/重定向设备的出站 TLS 连接（AT:P），影响面为设备侧 HTTPS 客户端/自动更新/API 等出站通道的机密性。修复与缓解：升级同批次版本；临时缓解见 [CERT Polska 通告](https://cert.pl/en/posts/2026/09/vulnerabilities-in-mikrotik-routeros-actively-exploited/)建议——**不要从未打补丁设备发起 TLS 连接或使用内置 SSH 客户端访问不受信主机**，并核查出站 TLS 通道（更新源、NTP/DDNS API 等）的证书固定与源地址校验。

**修复建议：**  
升级至 `6.49.21`/`7.23.5`/`7.24.2`+；升级前避免设备经不受信网络发起 TLS/内置 SSH 客户端连接；核查设备信任库与出站通道配置。

### 4.2 `CVE-2026-67279` — RouterOS SSH rekey 流程绕过致未认证文件操作（中危）

| 字段 | 内容 |
| --- | --- |
| 风险等级 | 中危（CVSS v4.0 6.9，CERT Polska/NVD） |
| CVSS评分 | 6.9（v4.0，`AV:N/AC:L/AT:N/PR:N/UI:N/VC:L/VI:L/VA:N`） |
| CWE编号 | `CWE-841`（Improper Enforcement of Behavioral Workflow，行为工作流执行不当） |
| 影响产品 | MikroTik RouterOS（SSH 服务端连接状态机） |
| 影响版本 | `[6.0.0, 6.49.21)`、`[7.0.0, 7.23.4)`、`[7.24, 7.24.2)` |
| PoC状态 | 未公开 |
| 在野利用 | 未知 |
| 修复版本 | 6.49.21 / 7.23.4（建议 7.23.5）/ 7.24.2 / 7.25beta3（2026-09-03） |

**漏洞描述：**  
RouterOS SSH 服务端在**客户端请求 rekey 后即进入连接协议（connection protocol）阶段，即使用户认证从未进行**（CWE-841，状态机顺序校验缺失）。未认证客户端可借此打开 session channel 并发送 exec 请求，受影响版本服务端会执行该命令分发，使攻击者能在 RouterOS 托管文件命名空间中**未认证创建、覆写与重建文件**——包括含配置与诊断数据的支持文件（support files）。该漏洞与 MikroTrick 链同批修复；CVSS 6.9 反映其机密性/完整性影响有限（文件命名空间受限），但覆写配置文件可被用于破坏设备配置完整性或辅助其他漏洞利用（如篡改后诱导管理员导入恶意配置）。修复与缓解：升级同批次版本；临时缓解与 3.1/3.2 相同——收敛/禁用 SSH 服务至可信管理网段。

**修复建议：**  
升级至 `6.49.21`/`7.23.5`/`7.24.2`+；升级前限制 SSH 访问来源并核查 RouterOS 文件系统中是否有未知文件（`/file print`），发现异常文件先取证再处置。

## 五、当日处置建议

1. **MikroTik RouterOS「MikroTrick」链 `CVE-2026-67276`/`CVE-2026-86060`（P0，在野利用）**：24 小时内完成全部 RouterOS 设备（RouterBOARD/CHR）版本核查——SSH 曾暴露公网或不受信网络的设备一律**按已失陷假设处置**：先隔离并保留日志/配置证据（`/log print`、`/system history print`、`/export`），核查 "-2" 畸形用户名记录、"ops" 账户与升级后 `/system device-mode print` 的 Flagged 标记，再升级至 `6.49.21`/`7.23.5`（Long-term）或 `7.24.2`（Stable），升级后恢复出厂/重建可信配置并轮换全部口令与 SSH 密钥（不得盲目恢复旧备份）；
