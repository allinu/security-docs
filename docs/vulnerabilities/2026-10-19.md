### 1.3 今日重点关注

1. **`CVE-2026-98490`：Linux 内核 openvswitch conntrack 扩展重分配致 helper UAF（9.8）**  
   调用 helper 时把**指向 extensions 区域的裸指针**挂进 expectations 链表（`nf_ct_helper → helper->help → nf_ct_expect_related_report → nf_ct_expect_insert`），若连接尚未 confirmed，后续 `*_ext_add()` 会**重新分配 extensions 空间**，链表中留下失效指针。这是“指针跨越 realloc 存活”的经典 UAF。openvswitch 是多租户云网络与容器网络的核心数据面，**该缺陷在有 OVS+conntrack 的虚拟化环境中可被触发**，后果从内核崩溃到潜在的提权原语。

2. **`CVE-2026-111998`：Vanus 硬编码管理令牌：未认证即可拿到集群管理员（9.3）**  
   Vanus 0.8.0–0.9.0 在 `internal/primitive/constants.go` 中**硬编码了一个固定的 admin Bearer token**。攻击者把它发到 gateway 的 gRPC 代理端口即可管理命名空间、事件总线、用户、令牌与角色绑定，并读取或发布事件。事件总线往往承载业务系统间的**全部事件流**——包括订单、支付、通知，拿到它等于拿到“业务脉搏”的读写权。同类问题本期还有 `CVE-2026-111999`（同产品缺失认证）。

3. **`CVE-2026-112005`：WhoDB 经 DuckDB 文件系统函数读写宿主任意文件（9.2）**  
   WhoDB 0.104.0–0.135.0 的 DuckDB 插件允许通过查询编辑器执行 `read_text`、`read_blob`、`COPY ... TO`、`ATTACH` 等文件系统函数，**攻击者无需凭据即可登录一个 DuckDB 文件**，进而窃取 `session.key` 与已保存的数据库凭据，或覆盖任意文件。这是“数据库工具把数据库能力原样暴露给使用者”的典型：DuckDB 的文件函数本是为分析本地文件设计，一旦在服务端对外开放，就变成任意文件读写。

4. **`CVE-2026-112006`：OpenTelemetry Python 导出器：证书变量为空字符串时直接关闭 TLS 校验（8.3）**  
   `opentelemetry-exporter-otlp-proto-http` 1.5.0–1.45.0 在 `OTEL_EXPORTER_OTLP_CERTIFICATE` 等变量为**空字符串**时**关闭 TLS 校验**（而非使用系统默认 CA）。攻击者可中间人冒充 collector，读取或篡改上报的 trace／metric／log，**包括 `OTEL_EXPORTER_OTLP_HEADERS` 中的认证头**。这类“空值等于关闭安全”的实现错误在 SDK 中尤其危险，因为它在所有使用该 SDK 的服务中同时生效，且**配置里看不出异常**。

### 1.4 综合研判

本期 543 条，但 73.8% 未评分，因此本节的分析以“组件类别”而非“分数排序”为主要方法。**第一类是内核与虚拟化**：Linux 内核本期合并 6 条修复（openvswitch conntrack UAF、sctp 陈旧 cookie 路径释放传输对象、tcp skb 合并限制、RISC-V KVM hrtime 同步、smb client 的 `finish_no_open`、以及若干稳定性修复）。这些条目的共同点是“触发条件在协议栈或虚拟化路径上”，**单条看像稳定性修复，合并看是内存安全面**；对云主机与容器宿主机，内核更新应按季度节奏兜底，而不是逐条研判。**第二类是“默认凭据与默认不安全”**：Vanus 的硬编码 admin token、WhoDB 的 DuckDB 无凭据登录、Xinference 在 Windows 上用 `../..` 反斜杠穿越写 `.json`（8.3）——三者都属于“工具型产品的默认姿态过于宽松”，且在 AI／数据工具链中高频出现。**第三类是开发者与可观测性生态**：OpenTelemetry 导出器空证书变量关闭 TLS 校验（8.3）、`snac2` 的 JSON 词法器堆溢出（8.7）、FreeRDP 等前一期条目延续。总体判断：本期**没有可直接利用的爆点（无 KEV、无高 EPSS、无成熟 PoC）**，但“未评分占比过高”本身就是情报质量风险——若按分数阈值做自动筛选，会系统性漏掉内核与基础库批次。建议在流程上补充“按组件白名单兜底”的规则。

#### 3.1.2 漏洞摘要

Linux 内核修复了 openvswitch conntrack 的一处 use-after-free：在调用 helper 的过程中，代码把一个**指向 extensions 区域的裸指针**通过 `nf_ct_helper() → helper->help() → nf_ct_expect_related_report() → nf_ct_expect_insert()` 挂进 `master_help->expectations` 链表（`hlist_add_head_rcu`）。问题在于：**若该连接尚未 confirmed**，后续的 `*_ext_add()` 调用会**重新分配 extensions 空间**（realloc），使链表中保存的指针失效，形成 UAF。CVSS 9.8。openvswitch 是虚拟化与容器网络的核心数据面，conntrack 用于状态化防火墙与 NAT；在启用 OVS + conntrack 的环境中（OpenStack、Kubernetes CNI、NFV 场景），该缺陷可被网络流量触发，表现从内核崩溃到潜在的内存破坏利用。值得注意的是，本期内核批次的多条修复都标注“内存安全”性质但 NVD 未评分，**说明内核条目的实际风险不能以 NVD 分数衡量**。

**技术原理：**

conntrack 的 extensions 是一个可增长的附加数据区，`*_ext_add()` 在空间不足时会重新分配并复制内容，原地址随之失效。任何在两次 add 之间保存的裸指针都必须通过偏移或句柄重新解析，而不是直接解引用。此处的错误是“跨越 realloc 保存了地址”——链表节点里存的是绝对指针，realloc 之后即指向已释放内存。RCU 链表进一步使问题复杂：即使发现失效，也需等待 grace period 才能安全释放，期间任何遍历都会触雷。

#### 3.1.10 修复与缓解措施

**官方修复：**

1. 按发行版公告更新内核并重启宿主机（需安排维护窗口）
2. 更新后核查 `dmesg` 与 KASAN 日志
3. 对运行 OVS 的节点评估是否需临时禁用 conntrack helper
4. 复核 OVS 与内核版本清单，建立季度更新基线

#### 3.4.2 漏洞摘要

`opentelemetry-exporter-otlp-proto-http` 1.5.0 至 1.45.0 存在证书校验不当（`CWE-295`）：当 `OTEL_EXPORTER_OTLP_CERTIFICATE` 一类环境变量被设置为**空字符串**时，导出器**直接关闭 TLS 校验**，而不是回退到系统默认 CA 存储。这使中间人攻击者可冒充 OTLP collector，读取或篡改上报的 trace、metric、log，**并窃取 `OTEL_EXPORTER_OTLP_HEADERS` 中的认证头**。CVSS 8.3。这类缺陷的危险性在于“无声扩散”：OpenTelemetry SDK 被几乎所有现代服务引用，而“把环境变量设为空”在 Kubernetes ConfigMap、Helm values、CI 变量中极为常见（例如为了覆盖模板默认值而留空）。**配置里看不出任何异常，但流量已经明文。**

> 原文摘要（NVD）：OpenTelemetry opentelemetry-exporter-otlp-proto-http 1.5.0 before 1.45.0 contains an improper certificate validation vulnerability that disables TLS verification when OTEL_EXPORTER_OTLP_CERTIFICATE variables are empty strings. Man-in-the-middle attackers can impersonate the collector to read or alter exported traces, metrics, and logs, including authentication headers from OTEL_EXPORTER_OTLP_HEADERS.

**技术原理：**

正确实现应为：变量未设置 → 使用系统 CA；变量设置为路径 → 加载该 CA；变量为空字符串 → 视为“未提供”并使用系统 CA（或直接报错）。本实现把“空字符串”当作“明确要求不校验”，从而进入 `verify=False` 分支。此类“三态（未设置/空/有值）”处理错误在配置驱动的 SDK 中非常普遍。

```text

      └─ 发送畸形输入触发缺陷逻辑

              └─ 造成信息泄露、拒绝服务或状态破坏
                  └─ 横向利用或持久化（视环境）
```

## 五、当日处置建议

1. **对未评分条目建立“组件兜底”规则**：本期 73.8% 未评分，纯按 CVSS 筛选会整体漏掉内核批次。建议把 Linux 内核、OpenSSL、glibc、主要语言运行时列为“无论是否评分都要核查”的白名单组件。
2. **默认令牌专项扫描**：Vanus 的硬编码 admin token、WhoDB 的匿名 DuckDB 登录、Xinference 的反斜杠穿越，都是“内部工具默认过于宽松”。建议对内部部署的数据/AI 工具做一次枚举：是否存在默认口令、是否可匿名访问、是否有文件函数直通。
3. **把 OpenTelemetry 配置纳入基线检查**：空字符串变量导致 TLS 关闭这类问题，靠人工评审很难发现。建议在 CI 中加入“证书相关变量不得为空”的静态检查，并对 collector 启用 mTLS。
4. **内核更新按季度兜底而非逐条研判**：本期内核 6 条修复中多条未评分，逐条分析成本高、收益低。按季度合并更新 + 关注 KASAN/崩溃告警是更有效的做法。
