### 1.4 综合研判

本期风险结构呈现「**两条 KEV 今日到期的强制销项 + 一批低门槛开源组件严重漏洞**」的双线叠加，与前两期「边界设备存量收割」的形态不同，本期两条最高优先级漏洞都指向**组织内部的基础设施枢纽**：GitLab 是源码与 CI/CD 凭据的汇聚点，ConnectWise ScreenConnect 是远程运维与控制通道，两者一旦同时被利用，攻击者无需触及终端即可同时获得「源码 + 密钥 + 远程控制」，这与第 44 期 JFrog Artifactory 事件所揭示的「研发基础设施即攻击面」判断完全一致，且本期进一步被在野观测证据所证实——`CVE-2026-85706` 从披露到出现探测流量不足 24 小时，说明公开 PoC 与自动化扫描器的接入速度已远超多数组织的补丁流程。第二条线是**开源组件漏洞的质量问题**：窗口内 11 条 CVE 中 9 条来自开源项目的 CNA 披露（VulnCheck/VulDB），其中「弱熵随机数导致账号接管」「模型文件反序列化执行代码」「低权限用户拼接 shell 命令」三类问题本质都是「可信边界假设失效」，而非复杂的内存安全缺陷——它们的修复成本极低（升级版本或替换默认配置），但被忽视的概率极高，尤其在自建 AI 应用、CMS 与运维平台中。第三条线是**事件面的补充信号**：Revolut 因伪造的政府部门邮件外泄客户 KYC 数据、游戏资源站投毒黑产链条、GitHub PR 服务中断等，提醒「社工 + 供应链 + 可用性」仍是与漏洞并行的常态化威胁。综合判断本期整体风险为**较高风险**，处置重心为「GitLab 今日 KEV 销项（升级 + 日志回溯 + 凭据轮换）+ ScreenConnect 客户端同批销项 + 四条开源组件严重/高危漏洞的版本清点」。

!!! danger "研判结论：较高风险"
    今日最确定的风险是两条**修复截止日即今日（2026-09-14）的 CISA KEV 在野漏洞**——互联网暴露的自建 GitLab（`CVE-2026-85706`，CVSS 10.0，已有在野探测）与 ConnectWise ScreenConnect（`CVE-2026-84869`，CVSS 9.9）；请在 24 小时内完成这两项升级或等效隔离，并对 GitLab 实例内的密钥/令牌、ScreenConnect 的会话与安装清单执行轮换与回溯审计。同时按 P1 处置本窗口新披露的 Strapi、LangBot、Spug、ESPnet 四条开源组件漏洞（其中 ESPnet 属模型供应链风险，Offline 环境亦不可豁免）。

#### 3.1.2 漏洞摘要

该漏洞存在于 **GitLab CE/EE 的仓库 Commits API**（`/api/v4/projects/:id/repository/commits`）。由于**路径限制不当（improper path confinement）并缺失鉴权强制校验**，未经身份认证的攻击者可构造单个 HTTP 请求，令服务端以 GitLab 进程身份读取任意本地文件。GitLab 官方公告的受影响范围为「所有 18.7 起至 19.1.8 之前、19.2 至 19.2.6 之前、19.3 至 19.3.2 之前的版本」。

> 与常规路径遍历不同，该漏洞的入口位于**鉴权之前**：接口仅要求请求通过 Workhorse 校验，真正的权限校验发生在文件读取之后；配合 Workhorse 对 `.../repository/commits` 的严格正则匹配，攻击者只需在 URL 静态段做百分号编码或追加尾斜杠即可绕过 body-upload 拦截，使伪造的 `file.path` 参数(绝对路径)进入服务端文件读取逻辑。

#### 3.1.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需可达 GitLab 的 HTTP/HTTPS 接口（默认 80/443，容器环境常见 8080） |
| 身份认证 | 无需 | 未认证即可触发（漏洞核心特征） |
| 用户交互 | 不需要 | 无需受害者点击或登录 |
| 特定配置 | 是 | 需要实例内存在可被未认证请求寻址的**公开项目**（用于构造 `:id`）。私有化 GitLab 通常存在公开项目或可枚举的项目 ID |
| 利用复杂度 | 低 | 单个 HTTP 请求；公开 PoC 已给出可直接使用的请求构造 |

**技术原理：**

1. **鉴权在文件读取之后**——接口入口仅做 Workhorse 前置校验，真正的 `authenticate!` 位于文件读取与响应组装之后，导致未认证请求也能推进到读文件环节。
2. **落盘元数据取自请求参数**——服务端采信攻击者可控的 `file.path` / `file.size` 参数并将其直接用于本地文件读取（`File.read`），形成任意文件读取原语。
3. **响应回显依赖解析错误**——被读文件内容在 `application/x-www-form-urlencoded` 处理路径下进入查询字符串解析，内容中出现的非法 `%` 编码会触发 `ArgumentError: invalid %-encoding (...)` 并经 `bad_request!` 原样回显进 HTTP 400 响应体，从而把文件内容带出（回显边界见 3.1.7）。
4. **URL 编码/尾斜杠绕过 Workhorse**——Workhorse 仅对结尾精确匹配 `.../repository/commits` 的请求执行 body-upload 拦截；对静态段做百分号编码或追加尾斜杠即不命中该规则，请求体连同伪造参数被原样转发至 Rails。

**核心利用链：**

```text
攻击者（未认证）
  └─ 探测 GitLab 版本 / 枚举可寻址项目 ID
      └─ 构造 URL：对 repository/commits 静态段百分号编码，或追加尾斜杠
          └─ 绕过 Workhorse body-upload 拦截（请求携带有效内部 JWT 转发 Rails）
              └─ 通过前置校验进入 Commits API
                  └─ file.path 伪造成绝对路径（如 /etc/gitlab/gitlab.rb）
                      └─ File.read 在 authenticate! 之前执行（以 git 用户身份）
                          └─ 内容经 Rack 解析错误回显进 HTTP 400 响应体
                              └─ 获得配置、SSH 私钥、数据库口令、CI/CD 变量与部署令牌
```

#### 3.1.11 风险影响

漏洞成功利用后，可能导致：

- 以 `git` 用户身份读取 GitLab 服务器上任意可读文件；
- 泄露 `/etc/gitlab/gitlab.rb`、`gitlab-secrets.json`、`database.yml` 等配置与密钥文件；
- 泄露 SSH 私钥、云主机密钥、部署令牌、Runner 注册令牌与 CI/CD 变量；
- 以泄露的凭据横向访问代码仓库、制品库、云环境与生产主机；
- 篡改 CI/CD 流水线（投放恶意构建产物，形成软件供应链投毒）；
- 结合同一补丁批次的 `CVE-2026-87719`（EE 不安全反序列化）扩大信息泄露面；
- 为后续持久化与横向移动提供长期有效的凭据（即使漏洞本身只读）。

#### 3.1.13 修复与缓解措施

#### 官方修复

1. 将 GitLab CE/EE 升级至 `19.1.8` / `19.2.6` / `19.3.2` 或更高版本（同时覆盖同批修复的 `CVE-2026-87719`、`CVE-2026-88765`）；
2. 升级前完成配置、仓库与业务数据备份（`gitlab-backup create` + `/etc/gitlab` 配置备份）；
3. 升级前**先做日志回溯**，确认是否已存在 `file.path` 探测请求，以决定凭据轮换范围；
4. 在测试环境验证兼容性与回退方案后实施升级；
5. 升级后核验版本、组件状态（`gitlab-ctl status`）与业务运行情况；
6. **轮换**所有可能已被读取的凭据（见下）；
7. 重新执行漏洞检测并留存修复证据。

**凭据轮换清单（Security Affairs 明确建议）：**

- `/etc/gitlab/gitlab-secrets.json` / `gitlab.rb` 中涉及的密钥与密钥库；
- 个人访问令牌（PAT）与 OAuth 应用密钥；
- CI/CD 变量（含受保护变量与掩码变量）与部署令牌（Deploy Token）；
- Runner 注册令牌（必要时重新注册 Runner）；
- 实例主机 SSH 私钥与云厂商访问密钥（AK/SK）；
- 恢复令牌与激活码。

#### 临时缓解

无法立即升级时，可采取：

- **移除互联网暴露**：为自建 GitLab 增加前置身份认证（VPN / Zero Trust / mTLS），或临时关闭公网访问；
- 在 WAF / 反向代理层拦截对 `/api/v4/projects/*/repository/commits` 携带 `file.path` 参数的 POST/PUT 请求（须评估对正常 API 调用的影响）；
- 收敛公开项目范围，减少可被未认证请求寻址的项目 ID（降低利用链前置条件）；
- 限制 GitLab 主机的文件系统权限，减少 `git` 用户可读的敏感文件（如收紧 `/etc/gitlab` 权限）；
- 启用并集中收集 GitLab 审计日志与访问日志，配置针对上述检测特征的告警；
- 对高风险实例实施网络隔离并加急排期升级。

!!! danger "严重漏洞（CVSS 3.1 = 9.9，CISA KEV 修复截止 2026-09-14 即今日）"

#### 3.2.2 漏洞摘要

该漏洞存在于 **ConnectWise ScreenConnect 的客户端组件**。NVD 描述为：ScreenConnect 客户端在特定条件下，可能允许**在未经授权或主机确认（Host confirmation）**的情况下，通过活跃的远程会话完成文件传输与执行。CISA KEV 的漏洞名称为「权限管理不当与缺失授权（Improper Privilege Management and Missing Authorization）」。**服务器端（ScreenConnect 服务器）不受影响**——这决定了排查与修复的重心在**被控终端侧客户端**，而非中控服务器。

> 由于 ScreenConnect 是运维人员常用的远程控制平台，其远程会话本身具有高权限文件传输与执行能力；当「授权确认」这一约束被绕过时，**合法的运维通道即可被直接武器化为横向投放与持久化通道**，这也是该漏洞 CVSS 向量中 `S:C`（范围变更）与三高（C/I/A:H）的来源。

#### 3.2.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需与 ScreenConnect 服务器存在连接（客户端需在线并可建立会话） |
| 身份认证 | 低权限（已在会话中，`PR:L`） | 攻击者需已进入或被允许进入一个活跃远程会话；漏洞点在会话内的授权确认环节 |
| 用户交互 | 不需要 | 无需主机使用者确认（漏洞核心：可绕过 Host confirmation） |
| 特定配置 | 是 | 需存在活跃远程会话及可用的文件传输/执行通道 |
| 利用复杂度 | 低 | 向量为 `AC:L`，成功后可跨范围影响（`S:C`） |

**技术原理：**

1. **授权确认环节缺失/可绕过**——客户端在处理会话内文件传输与执行请求时，未正确强制执行「授权或主机确认」这一约束（CWE-862）；
2. **权限边界判断不当**——客户端进程在会话上下文中的权限管理未能区分「会话参与者」与「应被允许发起文件传输/执行的主体」（CWE-269）；
3. **后果放大**——ScreenConnect 的会话本就具备文件投递与远程执行能力，一旦约束被绕过，攻击者可在被控终端落地文件并执行，且该行为**在运维视角下与正常远程维护难以区分**。

**核心利用链：**

```text
攻击者（已具备低权限会话访问 / 或诱导形成会话）
  └─ 建立或劫持一个活跃的 ScreenConnect 远程会话
      └─ 构造会话内的文件传输 + 执行请求
          └─ 客户端未强制校验授权 / 主机确认（CWE-862 + CWE-269）
              └─ 文件被传输至被控终端并执行
                  └─ 获得被执行终端上的代码执行能力（范围变更为 C:H/I:H/A:H）
                      └─ 横向移动 / 投放后门 / 以合法运维通道维持持久化
```

### 3.3 `CVE-2026-90561` — Strapi 内容管理器 WYSIWYG 预览存储型 XSS 致管理员账号接管

!!! danger "严重漏洞（CVSS 4.0 = 9.3，NVD 于 2026-09-13 首次收录）"
    低权限的 Author 角色可向富文本字段写入未过滤的脚本标签，当 Editor 或 Super Admin 在内容管理器中展开预览面板时脚本在**管理员会话**中执行，可直接接管后台账号。Strapi 是被广泛用于内容/知识库/产品页搭建的开源 Headless CMS，**若该实例同时作为 API 内容源或由运营、市场等非技术人员使用，账号接管后的影响半径会迅速扩大**。

#### 3.3.2 漏洞摘要

该漏洞位于 **Strapi 内容管理器的 WYSIWYG 预览组件**（`PreviewWysiwyg`）。组件在渲染富文本字段进行预览时，未能剥离（strip）其中的 `<script>` 等脚本标签，导致具备 **Author 角色**的用户可以把恶意脚本持久化写入数据库中的富文本字段；当 **Editor 或 Super Admin** 在后台展开预览面板时，脚本在其浏览器会话中执行，进而可执行后台 API 操作、读取或篡改内容、创建管理员账号，实现**账号接管（account takeover）**。

> 该漏洞属于典型的「**低权持久化 → 高权渲染**」型存储型 XSS：攻击者无需任何管理员权限，只需一个内容编辑账号（在多数组织中由外部作者、实习生或外包代运营持有），即可等待管理员触发。此类漏洞的检测难点在于**恶意内容长期驻留在数据库中**，仅在管理员打开预览时才会触发。

#### 3.3.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需可达 Strapi 后台（通常为 `/admin`） |
| 身份认证 | 低权限（Author 角色） | 攻击者需持有可编辑内容的账号（`PR:L`） |
| 用户交互 | 需要（管理员展开预览） | `UI:P`——受害者主动展开预览面板时触发 |
| 特定配置 | 是 | 需启用/使用富文本（WYSIWYG）字段与预览面板 |
| 利用复杂度 | 低 | 只需在富文本字段中写入脚本标签，无需特殊绕过 |

**技术原理：**

1. **渲染前未做净化**——预览组件直接渲染富文本内容（等价于 `dangerouslySetInnerHTML` 式渲染），未在执行前剥离 `<script>` 等危险标签；
2. **数据持久化**——恶意内容被写入数据库并长期驻留，形成「存储型」而非「反射型」XSS；
3. **权限不对称**——写入者只需 Author 权限，而渲染发生在具备更高权限（Editor / Super Admin）的会话中，形成**权限提升型会话接管**。

**核心利用链：**

```text
攻击者（Author 角色，低权限内容账号）
  └─ 在富文本字段中写入含 <script> 的内容并保存
      └─ 恶意内容持久化进 Strapi 数据库（长期驻留）
          └─ 管理员（Editor / Super Admin）在内容管理器中打开该条目
              └─ 展开 WYSIWYG 预览面板
                  └─ 预览组件未剥离脚本标签 → 脚本在管理员会话中执行
                      └─ 以管理员身份调用后台 API / 创建管理员账号 / 窃取会话令牌
                          └─ 实现后台账号接管与内容体系完全控制
```

### 3.4 `CVE-2026-90770` — Spug 运维平台监控地址命令注入致远程代码执行

!!! danger "高危漏洞（CVSS 4.0 = 8.7，NVD 于 2026-09-13 首次收录）"
    Spug（开源运维自动化平台）的 `ping_check` 函数将用户可控的监控地址**直接拼接进 shell 命令**，具备监控权限的已认证用户可通过 `/monitor/run_test/` 接口注入 shell 元字符，以 Spug 进程身份执行任意命令。**Spug 常被授予主机资产、执行命令与发布任务的权限，其进程身份往往等价于一批服务器的运维入口。**

#### 3.4.2 漏洞摘要

该漏洞位于 **Spug 的监控模块**：`ping_check` 功能在处理用户提交的监控地址时，未经校验即将其**直接插值进 shell 命令**（等价于 `shell=True` 的命令拼接），攻击者可在监控地址中注入 shell 元字符（如 `;`、`&&`、`|`、`` ` ``、`$()`）从而执行任意命令。NVD 描述指出：**具备监控权限的已认证用户**可通过 `/monitor/run_test/` 接口实现命令注入，命令以 **Spug 进程用户**身份执行。

> 该漏洞的风险放大点不在「命令注入」本身，而在 **Spug 的平台定位**：运维自动化平台通常被授予服务器资产凭据、批量执行命令与发布权限，因此 `Spug 进程用户` 的执行上下文往往可以直接触达大量生产主机——这与第 44 期 JumpServer 越权事件的风险逻辑一致（**运维枢纽的单一漏洞可兑换为整个内网的访问能力**）。

#### 3.4.5 利用条件与技术原理

| 条件 | 状态 | 说明 |
| --- | --- | --- |
| 网络可达 | 是 | 需可达 Spug Web 控制台（默认 80/443，常见 8080 映射） |
| 身份认证 | 普通用户（需监控权限，`PR:L`） | 攻击者需已持有 Spug 账号并具备监控配置/执行权限 |
| 用户交互 | 不需要 | 接口调用即可触发 |
| 特定配置 | 是 | 需目标 Spug 部署存在可执行监测的资产与监控任务 |
| 利用复杂度 | 低 | 直接在监控地址字段注入 shell 元字符 |

**技术原理：**

1. **输入未校验直接拼命令**——`ping_check` 将用户提交的监控地址（IP/域名/URL 形态）字符串拼接进系统命令并交给 shell 执行，未做白名单校验或参数化；
2. **shell 元字符逃逸**——攻击者在地址字段中加入 `;`、`&&`、`|`、反引号或 `$()` 即可让 shell 执行额外命令；
3. **执行上下文高风险**——命令以 **Spug 进程用户**身份运行，该身份通常具备读取配置（含资产凭据）、访问内网与执行运维操作的权限。

**核心利用链：**

```text
攻击者（已认证，具备监控权限）
  └─ 在监控项中提交含 shell 元字符的「监控地址」
      └─ 调用 /monitor/run_test/ 触发测试
          └─ ping_check 将地址字符串直接拼入 shell 命令（CWE-78）
              └─ 注入的命令以 Spug 进程用户身份执行
                  └─ 读取 Spug 配置与资产凭据 / 内网探测 / 横向移动
                      └─ 借运维平台的既有权限触达生产主机
```

| 在野利用 | 未知 |

**漏洞描述：**  
MKVToolNix 捆绑的 avilib 库在解析 AVI 文件的 ODML 超级索引时，32 位算术发生整数回绕，导致分配的内存块小于实际写入需求；攻击者可构造含超大条目计数的恶意 AVI 文件，在用 `mkvmerge` 解析时触发堆缓冲区溢出（`lib/avilib-0.6.10/avilib.c`）。溢出发生在多媒体文件解析路径，**常用于媒体处理流水线、转码服务与自动化内容审核系统**，除崩溃外亦存在代码执行的理论可能。

**修复建议：**  
更新至包含修复提交 `1495126138e086080f0163bee27fafbdf956a1d0` 的版本；在媒体处理流水线中对不可信来源的 AVI 文件实施隔离解析（容器/低权限进程）并限制单文件处理资源。

## 五、当日处置建议

1. **今日内（2026-09-14）完成两条 KEV 销项**：将自建 GitLab CE/EE 升级至 `19.1.8` / `19.2.6` / `19.3.2`（`CVE-2026-85706`），并将 ConnectWise ScreenConnect 客户端升级至厂商修复版本（`CVE-2026-84869`）；无法完成升级的实例应先移除互联网暴露或实施等效隔离。
2. **GitLab 实例执行「升级 + 日志回溯 + 凭据轮换」三件套**：优先检索访问日志中带 `file.path` 参数的 `POST /api/v4/projects/*/repository/commits/` 请求；无论是否发现命中，均建议轮换 `gitlab-secrets.json` 涉及的密钥、个人访问令牌、CI/CD 变量、部署令牌与主机 SSH 私钥（回显存在边界，**不能以「未回显」判定未受影响**）。
3. **ScreenConnect 执行会话与安装清单排查**：导出会话、文件传输与执行记录，比对变更工单；检查终端上是否存在非运维部署的「流氓 ScreenConnect 安装」，并对 ScreenConnect 进程派生的命令解释器/下载工具配置 EDR 告警。
4. **按 P1 处置本窗口新披露的开源组件严重/高危漏洞**：Strapi 升级至 `5.48.1`（并清洗富文本字段中的脚本残留）、LangBot 升级至 `4.10.11`（并轮换管理员与模型 API 密钥）、Spug 更新至含修复提交 `97aebf1` 的版本、ESPnet 升级至 `v.202609`（并对不可信模型检查点执行白名单校验）。
5. **优先核查互联网暴露的研发与运维基础设施**：GitLab、制品库（Artifactory）、堡垒机/运维平台（Spug、JumpServer）、远程运维工具（ScreenConnect）应作为本轮排查的第一顺位，避免「单点失守即全链失守」。
6. **完成修复后进行复测并更新台账**：对已确认在野的漏洞保留日志、流量、进程与文件证据；对发现异常的主机开展 WebShell、恶意进程、异常账号与横向移动排查；修复后复测并更新资产台账与处置记录。
